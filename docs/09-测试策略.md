## 1. 两类"测试"必须分开

这个项目的名字叫 TestFlow，于是"测试"这个词在内部有**两个完全不同的所指**。混淆它们是本文件最需要避免的错误。

| | A. **平台自身的测试** | B. **AI 输出的评测** |
| :--- | :--- | :--- |
| 测什么 | 代码是否正确 | 生成的用例是否好 |
| 判定方式 | 通过 / 失败，**客观确定** | 与人工参照集比对，**统计量** |
| 结果性质 | 二值 | 百分比、分布 |
| 何时跑 | 每次提交 | 变更 Prompt / 模型 / 派生算法时 |
| 是否花钱 | 否 | **是**（调用真实 LLM，`02` §5.4） |
| 未达标的含义 | 代码有 bug，必须修 | 质量下降，需权衡 |
| 进常规 CI | ✅ | ❌（EN8） |

**TS1：两者用不同的方法论、不同的工具、不同的运行时机，不得混在一起。**

把它们放进同一个测试框架、同一个 CI 阶段，会导致一个具体后果：AI 评测的"分数"波动会被误当成回归（它本来就有方差，见 §5.5），而真正的代码 bug 会被淹没在统计噪声里。

## 2. 平台自身的测试

### 2.1 分层

| 层 | 位置 | 内容 |
| :--- | :--- | :--- |
| **单元** | `tests/unit/` | 纯函数：无 I/O、无数据库、无网络 |
| **集成** | `tests/integration/` | 需要 PG / Redis / Celery / fixture 服务 |
| **架构** | `tests/architecture/` | 依赖白名单（`08` §2） |
| **端到端** | `tests/integration/e2e/` | 全流程：提交 Spec → 确认 → 执行 → 报告 |

### 2.2 高价值单元测试：全是确定性算法

本项目的设计刻意把大量逻辑做成了**纯函数**——它们是最容易测、也最值得测的部分：

| 模块 | 待测的纯函数 | 为什么必须高覆盖 |
| :--- | :--- | :--- |
| `guardrail/policy.py` | 网段判定、白名单匹配、`::ffff:` 归一化 | **安全边界**。一个边界条件的漏洞就是 SSRF（`03/Guardrail.md` §4.4） |
| `execution/assertions.py` | 六类断言的求值与三态判定 | 断言结论直接进入报告，错了会让用户做出错误判断 |
| `agents/spec_parser.py` | 规范化与指纹计算 | 指纹算错会让 S2 场景误报"Spec 变了"（SP5） |
| `agents/rules/` | LogAnalyzer 的每条规则 | 规则库是确定性归因的全部依据（LA1） |
| `agents/test_case_gen.py` 的**阶段 A** | 从 schema 派生测试维度清单 | 它是覆盖率指标的分母，见 §5.2 |

**注意最后一行**：`TestCaseGen` 里真正该被单元测试覆盖的**不是 LLM 调用**，而是**阶段 A 的维度派生算法**。LLM 的行为属于 B 类评测（§5），不是单元测试的对象。

### 2.3 覆盖率策略：分层而非一刀切

PRD 的 M6 要求"平台自身单测覆盖率 ≥ 70%"。**但一个总数是有误导性的**——它无法区分"安全边界测了 95%"和"安全边界测了 40%"，而这两者的风险完全不同。

**TS2：覆盖率按模块分层设定，并优先保证安全与判定类模块。**

| 分层 | 模块 | 目标 |
| :--- | :--- | :--- |
| **必须充分** | `guardrail/policy.py`、`execution/assertions.py`、`agents/rules/` | ≥ 90% |
| **应当较高** | `agents/spec_parser.py`、`agents/test_case_gen.py`（阶段 A） | ≥ 80% |
| **整体** | 全部 | ≥ 70%（M6） |
| **可不追求** | `entrypoints/`、`graph/build.py`、`gateway/schemas.py` | — |

最后一行不是"可以不测"，而是**不为它们写凑数的测试**：装配代码的测试价值低于其维护成本，用端到端测试覆盖更划算。

## 3. 可控的被测对象：fixture 服务

### 3.1 为什么必须有

TestFlow 的端到端测试**需要一个可以打的 API**。若打真实的外部接口：

- 结果不稳定（对方随时可能改）
- 需要真实凭证
- 可能污染对方的数据
- 无法构造特定的失败场景（怎么让对方返回"200 但 body 不是 JSON"？）

**TS3：内置一个 fixture 服务，作为端到端测试的被测对象。**

### 3.2 fixture 服务的端点设计

关键原则：**每个端点对应一条已经在设计文档里写死的边界行为**——它不只是"一个测试用的 API"，而是那些设计行为的可执行规格。

| 端点 | 行为 | 验证的设计点 |
| :--- | :--- | :--- |
| `/ok` | 200 + 合法 JSON | 正常路径 |
| `/echo` | 回显请求 | 断言求值的各 operator |
| `/no-content` | 204 无 body | `json_path` 断言在空 body 上的行为 |
| **`/bad-json`** | **200 但 body 不是 JSON** | **TE2：断言级 `error` 与 `failed` 的区分** |
| `/error-500` | 500 | `server_error` 归因 |
| `/invalid-echo` | 400 + 校验错误结构 | `request_invalid` 归因规则 |
| `/slow` | 延迟超过 HTTP 超时 | TE7 的三层超时、`timeout` 状态 |
| `/redirect` | 302 指向别处 | **SR-4：不跟随重定向** |
| `/large` | 超大 body（> 256 KB） | **DM6：截断与 `truncated` 标记** |
| `/recursive` | 返回递归嵌套结构 | SP1 的 `$ref` 深度上限 |
| `/destructive` | 接受 DELETE | **SR-3：Worker 侧 Guardrail 的第二层拦截** |

`/bad-json` 值得单独强调：它验证的是 `TestExecutor.md` TE2 那个"断言三态"的设计。**如果实现偷懒把"无法求值"和"断言不符"合并，只有这个端点能让测试失败。** 没有它，这个设计点会静默失效。

### 3.3 fixture 服务与 SR-2 的关系

fixture 服务跑在 `127.0.0.1` —— **正好会被 SR-2 拦截**（`03/Guardrail.md` §4.3）。

这不是麻烦，而是**免费的验证**：测试环境必须显式配置 `guardrail.allow_private_targets`，而这正好走通了 §4.6 的例外面板。

同时这也验证了另一件重要的事：**该例外只从配置读取、不从 Spec 派生**。如果实现错误地从 Spec 的 `servers[].url` 派生例外，那么所有测试仍然会通过——因为测试用的一直是内网地址。因此需要**一条专门的负向测试**：

> 构造一个 Spec，其 `servers[].url` 指向 `127.0.0.1`，**不配置任何内网例外**，断言请求被拒绝且审计日志中出现 `deny_reason = 'private_ip'`。

`03/Guardrail.md` §4.6 明确指出"例外不可从 Spec 派生"是 SR-2 成立的关键。**这条测试就是那个论断的守门人。**

## 4. Guardrail 的对抗性测试集

Guardrail 是唯一的安全组件（`03/Guardrail.md` §1.1），它的测试策略与其余模块不同：不是"验证功能正确"，而是"**验证绕过不可行**"。

**TS4：建立一组对抗性测试，每个用例对应一种已知的绕过手法。**

| 攻击手法 | 测试输入 | 期望 |
| :--- | :--- | :--- |
| 云元数据直取 | `http://169.254.169.254/latest/meta-data/` | deny（`03/Guardrail.md` §4.5） |
| 阿里云元数据 | `http://100.100.100.200/` | deny（CGNAT 段，§4.3） |
| **IPv4 映射绕过** | `http://[::ffff:169.254.169.254]/` | deny（§4.4） |
| 6to4 封装 | `http://[2002:a9fe:a9fe::]/` | deny（§4.3） |
| NAT64 封装 | `http://[64:ff9b::a9fe:a9fe]/` | deny（§4.3） |
| **DNS rebinding** | 先用公网 IP 通过校验，再切换解析结果 | deny（§4.2 的连接后二次校验） |
| 端口扫描 | 白名单 host + `:22` | deny（GR3：三元组精确匹配） |
| 子域混淆 | 白名单含 `api.example.com`，请求 `evil.example.com` | deny（GR3：不做子域继承） |
| 重定向穿透 | 白名单 host 返回 `Location: http://169.254.169.254/` | 不跟随（SR-4） |
| 破坏性绕过 | 直接构造 `DELETE` 请求（跳过 N4 的过滤） | deny（SR-3 第二层） |

**IPv4 映射那一行是本表的核心价值**：`03/Guardrail.md` §4.4 说明它是"只写 IPv4 网段检查"的实现的必然漏洞。这类漏洞**在被利用前不会表现出任何症状**——正常测试全绿。只有专门构造的对抗性用例能发现它。

DNS rebinding 的测试需要可控的解析器（自定义 resolver 或测试用 hosts），实现成本较高，但它验证的是 §4.2 那个"先校验、再钉死"的核心理由。**值得做**。

## 5. AI 输出评测（Eval）

### 5.1 三层模型

对应 PRD §4.3，展开为可执行的定义：

| 层 | 检查什么 | 自动程度 | 频率 |
| :--- | :--- | :--- | :--- |
| **L1 结构** | Pydantic 严格校验、断言约束（A2–A4）、维度标识合法 | 全自动 | 每次生成（已内置于 `TestCaseGen` §5.1） |
| **L2 覆盖** | 派生维度是否都有对应用例、声明的 4xx 是否有用例 | 全自动 | 每次生成（`TestCaseGen` §5.2） |
| **L3 质量** | 与人工参照集比对：维度覆盖完备性、断言准确率、档位对比 | 需人工标注 | 变更触发（§5.6） |

**L1 与 L2 是运行时的自检，不是"评测"**——它们已经在生产路径上（`TestCaseGen` §5），失败会触发重试。真正需要"评测"的只有 L3。

这一点容易搞混：L1/L2 跑在每个 Run 上，L3 只在变更时跑。

### 5.2 覆盖率的两个层次（这份文档最重要的部分）

"维度覆盖率"这个指标有个**自我参照的陷阱**：

```
维度覆盖率 = 已生成维度 / 阶段 A 派生的维度清单
```

**分母是平台自己算的。** 如果阶段 A 的派生算法漏掉了 `maxLength` 约束，那么：

- 分母里没有 `boundary:name`
- 生成结果里自然也没有
- **覆盖率依然显示 100%**

指标全绿，而实际覆盖是缺失的。**没有任何一个自动指标能发现这件事**，因为指标的分母本身就是错的。

**TS5：必须有人工标注的独立基准，否则 L2 覆盖率是自我参照的、无意义的。**

因此覆盖率的验证要分两层：

| 层次 | 验证什么 | 基准来源 |
| :--- | :--- | :--- |
| **第一层：派生正确性** | 阶段 A 是否派生出了所有应测的维度 | **人工标注的维度清单** |
| **第二层：生成完整性** | 派生出的维度是否都生成了用例 | 阶段 A 的输出（自动） |

第一层只能在 L3 上做，且必须人工标注。**这是 Golden Set 最重要的用途**——它不是为了测"LLM 生成得好不好"，而是为了测"**我们的派生算法有没有系统性盲区**"。

> 这个陷阱值得记住：**任何以平台自身输出为分母的指标，都需要一个外部基准来校准。** 归因认可率（M4）同理——它的分母是平台判定的"失败"，若失败判定本身有问题，认可率再高也没意义。

### 5.3 Golden Set 设计

PRD §4.3 规定 10 个接口。选型原则是**覆盖会让算法出错的接口特征**，而不是"随便挑十个"：

| # | 接口特征 | 被检验的能力 |
| :--- | :--- | :--- |
| 1 | 仅路径参数，无请求体 | 基础路径 |
| 2 | 多个必填 + 可选参数 | `required_missing` 维度 |
| 3 | 含 `enum` 与 `pattern` | `constraint_violation` 维度 |
| 4 | 含数值 `minimum`/`maximum` | `boundary` 维度 |
| 5 | 含 `minLength`/`maxLength` | 字符串边界（**最容易漏的一类**） |
| 6 | 嵌套对象 + `$ref` 复用 | `$ref` 展开与裁剪 |
| 7 | 声明了多个 4xx 响应 | L2 的"声明的 4xx 是否有用例" |
| 8 | **响应无 schema** | `TestCaseGen` §7 的低置信度标注 |
| 9 | **无参数、无请求体、无 4xx 声明** | **TG5 的纯规则路径（不调 LLM）** |
| 10 | 含自定义 `format` | 未知语义的降级处理 |

第 5 与第 9 是刻意选的边界：
- **第 5 个**：字符串长度约束是派生算法最容易漏的一类（因为它藏在 `type: string` 的兄弟字段里，而数值边界更显眼）。**如果只测第 4 个，会误以为边界维度已经覆盖了。**
- **第 9 个**：验证 TG5——这个接口**不应该产生任何 LLM 调用**。若它出现在调用记录里，说明 TG5 没实现。

Golden Set 中每个接口需要人工标注：

| 标注项 | 用途 |
| :--- | :--- |
| **期望的维度清单** | §5.2 第一层的基准 |
| 参考答案用例（可选） | 人工判断断言准确率的参照 |
| 期望的 4xx 状态码集合 | L2 的独立基准 |

**落地（M5）**：Golden Set 在 `eval/golden/golden_set.yaml`，标注在同目录的
`golden_set.annotations.yaml`。第一层比较是纯算法（`src/testflow/eval/golden.py`），
由 `tests/unit/test_golden_set.py` 在 CI 中执行——**每次改派生算法都会立刻和
人工基准比对**，不需要有人想起来手动跑。第二层（真实调用）用
`scripts/eval_golden.py --generate`，结果写入 `eval/results/<时间>-<模型>.json`。

建立这份基准的过程本身就证明了它的价值：在手工填写 39 个维度时，
对照 §2.3 的维度表发现实现只处理了 `enum`，漏掉了 `pattern` / `format` /
`multipleOf` 三类约束。**注意发现的方式**——不是某个测试变红了，而是
"人工清单里有、代码产不出来"这个对照。修复前覆盖率仍显示 100%，
因为分母里根本没有它们。这正是 §5.2 所说"没有任何自动指标能发现"的含义。

### 5.4 指标的来源不同

有两类指标，**来源不同，不能混在一张表里比较**：

| 指标 | 来源 | 说明 |
| :--- | :--- | :--- |
| 维度覆盖完备性 | **Golden Set**（L3） | 与人工标注比对 |
| 断言准确率 | **Golden Set**（L3） | 需人工抽检标注 |
| 结构合法率 | 生产运行（自动） | L1 的通过率 |
| **用例采纳率（M1）** | **生产使用**（IP-1） | 来自 `cases.review_status`，不是在 Golden Set 上测的 |
| **归因认可率（M4）** | **生产使用**（人工纠错） | 来自 `attributions.human_verdict` |

M1 与 M4 **不能**用 Golden Set 测：Golden Set 只有 10 个接口，且标注答案已知，人工确认的意愿与真实使用完全不同。**它们是产品指标，只能在真实使用中采集。**

### 5.5 档位对比必须多轮

`02` §5.1 提到 V1.0 可能把 `LogAnalyzer` 降级到 Flash 档位，前提是"先在 Golden Set 上测量质量损失"。这里补上方法：

**TS6：档位对比必须多轮重复，单次对比没有意义。**

LLM 输出有方差——同一个 Prompt、同一个档位，两次运行的维度覆盖率可能差几个百分点。**单次对比无法区分"档位差异"与"随机波动"。**

方法：

| 项 | 做法 |
| :--- | :--- |
| 重复次数 | 每档位 ≥ 3 次（成本允许时 5 次） |
| 报告内容 | **均值 + 极差**，不是单次值 |
| 判定门槛 | 仅当低档位的**最差一次**仍达标时，才认为降级安全 |
| 成本 | 使用 Batch 调用（5 折，`02` §5.4）；这也是 EN8 让 eval 不进常规 CI 的原因 |

最后一行的门槛是本方法的关键：用**最差一次**而不是均值做决策。因为生产环境中用户遇到的是单次结果，均值好看但偶尔很差，用户体验依然糟糕。

### 5.6 触发条件

**TS7：L3 在以下变更后必须运行。**

| 变更 | 为什么必须跑 |
| :--- | :--- |
| Prompt 内容变更 | 直接影响生成质量 |
| 模型档位变更 | 这正是要评估的事 |
| 结构化输出 Schema 变更 | 可能改变模型的行为分布 |
| **阶段 A 的维度派生算法变更** | 影响覆盖率的分母，即 §5.2 的第一层 |
| 归因规则库的增删 | 影响 M4 |

**运行方式**：手动或定时（EN8）。**结果必须记录**——记录在何处见 §5.7。

### 5.7 结果的留痕

L3 的结果若不记录，就无法回答"这次改动让质量变差了吗"。

| 记录项 | 位置 |
| :--- | :--- |
| 本次运行的档位、Prompt 版本、Golden Set 版本 | `eval/results/*.json`（随代码入库） |
| 各指标的均值与极差 | 同上 |
| 与上一次的对比 | 运行器读取上一份同模型结果并打印差值；完整历史留在文件里 |

结果文件里的 `git_commit` / `golden_set_sha256` / `annotations_sha256` /
`prompt_sha256` 让"这次和上次到底比的是什么"可以被回答。只打印到终端
等于没有记录——终端会滚走。

`cases.llm_model` / `generated_by` / `confidence`（`04` §2.5）提供了生产侧的追溯；Golden Set 侧的结果则应在仓库中留一份历史，使"质量随版本的变化"可见。

## 6. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **TS1** | 平台测试与 AI 评测严格分开 | 二值结果与统计量混在一起，会把评测方差误判为回归，也会淹没真实 bug |
| **TS2** | 覆盖率按模块分层 | 一个总数无法区分"安全边界 95%"与"安全边界 40%" |
| **TS3** | 内置 fixture 服务作被测对象 | 真实外部 API 无法构造特定失败场景，且不稳定 |
| **TS4** | Guardrail 建立对抗性测试集 | 验证"绕过不可行"，而非"功能正确" |
| **TS5** | 覆盖率必须有人工独立基准 | 分母是平台自己算的，自我参照的指标永远显示 100% |
| **TS6** | 档位对比多轮重复，用最差一次做决策 | 单次对比无法区分档位差异与随机波动；用户遇到的是单次结果 |
| **TS7** | 明确 L3 的触发条件 | 否则"什么时候该跑 eval"是模糊问题，实际等于不跑 |
| **TS8** | fixture 服务与 SR-2 例外的负向测试 | 验证"内网例外不从 Spec 派生"这条安全论断 |
