## 1. 项目概述

### 1.1 项目定位

TestFlow 是一个基于多智能体编排的 API 自动化测试平台。它不是"AI 对话机器人"，而是一条**能自我闭环的工程管线**：

> 解析 OpenAPI 规范 → 生成结构化测试用例 → 沙箱化异步执行 → 失败日志归因 → 聚合出报告 → 人工确认后回流

它的技术主张是 **"AI 只负责它能负责的部分"**——凡是确定性算法能解决的问题（规范解析、状态码断言、覆盖率统计），一概不交给 LLM；LLM 只用在真正需要语义理解的三处：用例设计、错误归因、报告叙述。这一点贯穿全文，是本文档所有架构取舍的出发点。

### 1.2 目标用户与核心场景

**主用户**：后端 / 测试工程师，手上有一个已写好 OpenAPI 文档但缺乏接口测试覆盖的服务。

| 场景 | 触发时机 | 用户目标 | 当前替代方案及其痛点 |
| :--- | :--- | :--- | :--- |
| **S1 补齐存量接口覆盖** | 接口文档先行、测试滞后 | 用最少的体力拿到一批可用用例 | 手写 Postman/RestAssured，一个接口 15~30 分钟 |
| **S2 接口变更后回归** | 文档更新，旧用例失效 | 快速识别哪些用例需重写 | 人工比对文档 diff，容易漏 |
| **S3 排查线上/联调故障** | 接口返回 500 或超时 | 知道"是参数问题还是服务问题" | 逐个翻日志，依赖个人经验 |

> **S1 是 MVP 唯一必须打透的场景**。S2/S3 是 MVP 功能天然带来的收益，但不作为验收目标。

### 1.3 解决的核心痛点

| 传统痛点 | TestFlow 解决方案 | 关键设计点 |
| :--- | :--- | :--- |
| 手写用例耗时、覆盖率低 | AI 依据 Spec 生成正常/异常/边界三类用例 | 用 coverage 指标约束生成，而非让 LLM 自由发挥 |
| 测试脚本与接口文档脱节 | Spec-Driven，文档即用例事实来源 | Spec 指纹变化触发用例失效标记（S2） |
| 失败日志人工排查效率低 | LogAnalyzer 自动归类并关联历史案例 | 规则优先归因，LLM 兜底，二者可分离评估 |
| AI 生成内容不可控、易幻觉 | Pydantic 强校验 + Schema 约束 + 人工确认门 | 结构不合法直接判失败重试，不进执行队列 |

### 1.4 成功指标

指标分两类：**产品指标**衡量"是否解决了问题"，**工程指标**衡量"是否可交付"。作品集场景下，这些同时是设计目标与技术亮点。

| 编号 | 指标 | 目标值 | 度量方式 |
| :--- | :--- | :--- | :--- |
| M1 | 用例人工采纳率 | ≥ 70% | HITL 确认环节"通过/生成总数" |
| M2 | 单接口生成耗时 P95 | ≤ 30s | 从 SpecParser 完成到用例入库 |
| M3 | Spec 解析成功率 | ≥ 99% | 对符合 OpenAPI 3.0/3.1 规范的文档 |
| M4 | 归因 Top-1 人工认可率 | ≥ 60% | 抽检 50 条失败用例人工标注 |
| M5 | 端到端闭环耗时 P95 | ≤ 5min | 20 接口规模，Spec 上传 → 报告产出 |
| M6 | 平台自身单测覆盖率 | ≥ 70% | pytest-cov |
| **M7（负向）** | 破坏性用例误执行次数 | **= 0** | 见 SR-3 |
| **M8（负向）** | 单次完整任务 LLM 成本 | ≤ ¥2 | Token 用量统计 |

> M7、M8 是**硬约束而非目标**：任一违反即视为发布阻塞缺陷。M4 目标值偏低是刻意的——归因本身是开放问题，虚报指标比不报更糟。

## 2. 术语表

全文统一使用以下术语，模块设计文档不得引入同义词。

| 术语 | 含义 |
| :--- | :--- |
| **Spec** | OpenAPI 3.0/3.1 规范文档（JSON 或 YAML） |
| **Operation** | Spec 中一个具体的 `method + path` 组合，即"一个接口" |
| **Case** | 一条测试用例：一组具体的请求参数 + 期望断言 |
| **Run** | 一次测试执行批次，覆盖若干 Case |
| **归因（Attribution）** | 对失败 Case 判定失败根因类别的过程 |
| **Guardrail** | 出站请求的强制校验层，不可被业务代码绕过 |
| **HITL** | Human-in-the-Loop，LangGraph 的 `interrupt` 中断点，等待人工确认 |
| **Checkpoint** | LangGraph 图状态的持久化快照，用于中断恢复与故障续跑 |

## 3. 功能范围

### 3.1 架构蓝图与版本分期

[架构图](../imgs/TestFlow架构图.svg) 中的 15 个节点按版本分期如下。**MVP 只做 P0 列**。

| 图节点 | MVP (v0.1) | V1.0 | V2.0 | 取舍理由 |
| :--- | :--- | :--- | :--- | :--- |
| **SpecParser** | ✅ 纯算法解析 | | | 不需要 LLM（`prance` + `openapi-spec-validator`），确定性任务 |
| **TestCaseGen** | ✅ LLM 生成 + Schema 校验 | | | 核心价值点，不可省 |
| **TestExecutor** | ✅ 单机并发 | | ✅ 独立 Sandbox | MVP 只打真实测试环境，不执行用户代码 |
| **LogAnalyzer** | ✅ 规则归因 | ✅ 混合检索归因 | | MVP 先证明规则覆盖率，再引入 RAG |
| **ReportAgent** | ✅ Jinja2 模板 | ✅ LLM 叙述增强 | | 报告结构是确定性的，模板化更快更稳 |
| **LangGraph Orchestrator** | ✅ Checkpoint + Interrupt | | | 编排是整个项目的技术核心，必须 MVP 就位 |
| **FastAPI Gateway** | ✅ SSE 单通道 | ✅ Callback API | | MVP 用 SSE 长连接足够；回调是跨机部署后才需要 |
| **Celery Worker Pool** | ✅ 单队列 | ✅ 优先级队列 | | 先证明异步解耦有效，再谈调度策略 |
| **Egress Proxy / Guardrails** | ✅ 进程内库实现 | ✅ 独立代理进程 | | **安全是必需品，但 MVP 阶段进程内足够**（见 SR-1） |
| **Target API / Sandbox** | ✅ 外部测试环境 | | ✅ 本地虚拟目标 | |
| **Redis** | ✅ Checkpoint + Broker | | | 一物两用，成本最低 |
| **PostgreSQL** | ✅ 事实 + 审计 | ✅ 冷归档 | | MVP 数据量小，不做归档 |
| **Vue3 前端** | ✅ **最小可用页** | ✅ 监控视图 | | HITL 确认必须有界面；不做监控大屏 |
| **向量库 (pgvector/Milvus)** | ❌ | ✅ | | 无历史案例积累时，向量检索无意义 |
| **BM25** | ❌ | ✅ | | 同上，与向量库成对引入 |
| **对象存储** | ❌ | ✅ | | 日志直接存 PG；单条超阈值时再迁 |

**三个需要显式说明的范围判断：**

1. **为什么 Egress Proxy 在 MVP 且不可延后**——OpenAPI 文档中的 `servers[].url` 完全由用户提供，服务会照着它发起真实 HTTP 请求。这是标准的 SSRF 面：用户填入 `http://169.254.169.254/latest/meta-data/` 即可让平台代其访问云元数据服务。这不是"功能"，是**上线前提**。MVP 阶段以库形式（HTTP 客户端中间件）实现，V1.0 再抽为独立代理进程。
2. **为什么向量库/BM25 不进 MVP**——RAG 归因依赖历史失败案例积累，冷启动阶段检索出的"相似案例"质量不可信，反而污染归因结果。MVP 用规则归因，先把 M4 基线测出来。
3. **为什么 ReportAgent 不调 LLM**——报告的结构（通过率、错误分布、Top 失败接口）是确定性的集合运算。引入 LLM 只会带来不稳定输出和额外成本（违反 M8）。LLM 的价值在 V1.0 的自然语言总结，而非数据聚合。

### 3.2 MVP 功能清单（P0）

| 编号 | 功能 | 验收标准 |
| :--- | :--- | :--- |
| F1 | 上传/粘贴 OpenAPI 3.0/3.1 文档并解析 | 输出版本、Operation 清单；非法文档给出可定位的错误信息而非堆栈 |
| F2 | 针对选定的 Operation 生成 Case | 每 Operation 生成正常/异常/边界用例；输出通过 Pydantic 校验（M1） |
| F3 | HITL 确认门 | 生成后可逐条勾选确认/丢弃；未确认的 Case 不进入执行队列 |
| F4 | 异步执行 Case | 记录请求/响应/耗时/状态码；单请求超时可配，默认 10s |
| F5 | 失败 Case 自动归因 | 输出归因类别 + 依据（命中的规则或 LLM 推理）；支持人工纠错 |
| F6 | 生成测试报告 | 含通过率、错误分布、Top 失败接口；支持导出 |
| F7 | 出站请求 Guardrail | 未通过校验的请求被拒绝**且记录审计日志**（SR-1~SR-5） |
| F8 | 任务可中断可恢复 | 进程重启后，处于 HITL 中断的 Run 可从 Checkpoint 恢复 |
| F9 | 命令行入口 | `testflow run <spec-path>` 从本地路径提交 Spec；`status` / `report` 查看进度与结果；服务未启动时给出明确提示而非堆栈 |

> **关于 F9 的设计约束**：CLI 是 Gateway 的**纯客户端**，只通过 HTTP 调用同一套接口，**不重新实现**解析、生成或执行逻辑，也不内嵌"本地模式"直连内部模块。
>
> 两条理由：① 同一业务路径存在两份实现时，二者必然漂移，且这种漂移不会被测试发现（与 `02` D2「Guardrail 唯一通道」是同一原则）；② 绕过 Gateway 就绕过了统一的日志脱敏（`02` §2.2）。
>
> **HITL 确认仍在网页完成**——CLI 只负责提交与查看，不做用例确认。理由见 §4.2：确认界面需要逐条展示断言与置信度，终端不是合适的载体。

### 3.3 明确不做的事（Non-goals）

| 不做 | 理由 | 何时考虑 |
| :--- | :--- | :--- |
| UI 自动化测试 | 与 API 测试的技术栈、执行模型完全不同，会稀释核心叙事 | 不计划 |
| 性能压测 | 目标、指标体系、执行模型均不同；TestExecutor 的定位是功能验证 | 不计划 |
| 多租户与权限管理 | 单用户场景下引入租户隔离会显著复杂化数据模型与 Checkpoint 设计 | V2.0 |
| 测试代码生成（导出 pytest/RestAssured 脚本） | 看似顺手，实则需要一套完整的代码生成与模板维护体系 | V1.0 评估 |
| 定时/CI 触发与流水线集成 | 依赖稳定的对外 API 契约，MVP 契约还在演进 | V1.0 |
| 自定义断言脚本 | 等同于"在平台内执行用户代码"，与沙箱范围强耦合，风险高收益待验证 | V2.0 |
| 私有协议 / GraphQL / gRPC | 收益明确但工作量独立且巨大，OpenAPI 足以验证核心假设 | V2.0 |

### 3.4 优先级矩阵

| 优先级 | 内容 | 说明 |
| :--- | :--- | :--- |
| **P0** | F1~F9、SR-1~SR-5 | MVP 发布阻塞项 |

## 4. 关键需求说明

### 4.1 端到端主流程

参与组件与数据流向（对应架构图，但**仅 P0 节点**）：

```
用户 → [Vue3 最小前端] --HTTP/SSE--> [FastAPI Gateway]
                                          ↓ 启动
                                    [LangGraph Orchestrator]  ←── Checkpoint ──→ [Redis]
                                          ↓
                          SpecParser → TestCaseGen → ⏸ HITL 中断
                                          ↓（确认后恢复）
                                    TestExecutor ──提交──→ [Celery Worker]
                                          ↓                     ↓
                                    LogAnalyzer ←─── 结果 ──────┤
                                          ↓                     ↓
                                    ReportAgent            [Guardrail] → [Target API]
                                          ↓                     ↓
                                    [PostgreSQL] ←──────────────┘
```

**关键路径约束**：`TestExecutor` 自身不发起 HTTP 请求，只负责组装任务并投递到 Celery。所有出站请求统一由 Worker 侧的 Guardrail 中间件发出，保证 Guardrail 无法被绕过（SR-1）。

### 4.2 人与 AI 的协作边界（HITL）

这是"AI 不可控"痛点的直接落点，也是架构图中 `LangGraph Interrupt` 的设计意图。

| 决策点 | MVP 归属 | 理由 |
| :--- | :--- | :--- |
| 生成哪些用例 | **AI 提出，人确认** | 这是幻觉风险最高、且成本最低可拦截的环节 |
| 断言是否合理 | **AI 提出，人确认** | 同上，与用例确认合并为同一次中断 |
| 是否执行 | 人触发 | 未确认的 Case 绝不自动执行，避免污染目标环境 |
| 失败归因 | AI 判定，人可纠错 | 归因错了不会造成破坏，纠正成本低 |
| 报告结论 | 模板生成 | 确定性聚合，不需要 AI |

**中断点设计**：MVP 只有**一个**中断点（用例确认）。中断发生时状态写入 Redis Checkpoint，前端通过 SSE 收到事件。人工确认后恢复图执行。

**中断超时策略**：Checkpoint 长期保留（在 Redis 中默认 7 天 TTL）。超时未确认的 Run 标记为 `abandoned`，不自动执行、不报错——避免"用户离开电脑，半夜测试环境被刷"。

### 4.3 AI 输出质量与评估（Eval）

AI 生成质量若无评估机制，§1.3 中"易幻觉"那条只是口号。MVP 需内置最小评估能力：

| 层次 | 机制 | 时机 |
| :--- | :--- | :--- |
| L1 结构层 | Pydantic 强校验；不合法即判失败并重试（最多 2 次） | 每次生成 |
| L2 覆盖率层 | 校验生成结果是否覆盖声明的状态码与必填/可选字段组合 | 每次生成 |
| L3 质量层 | Golden Set 回归：人工准备 10 个接口的参考用例集，比对字段覆盖度与人工采纳率 | Prompt 变更时 |

**Golden Set 是必须产出的交付物**，与代码同目录维护（`tests/eval/golden/`）。任何 Prompt 或模型变更，必须跑一次 L3 并记录结果到变更记录中。这是"AI 项目可维护"的核心证据。

### 4.4 安全需求

TestFlow 会代替用户向外部服务发起 HTTP 请求，因此**它的威胁模型为：用户提供的 Spec 是不可信输入，目标 API 是外部系统**。

| 编号 | 需求 | MVP 实现方式 |
| :--- | :--- | :--- |
| **SR-1** | **出站白名单**：仅允许 Spec 中显式声明的 host | Guardrail 中间件比对 host 白名单，拒绝一切未声明目标 |
| **SR-2** | **禁止内网地址**：拒绝私网、环回、链路本地、云元数据地址段（`169.254.0.0/16`、`127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16` 等） | 解析域名后校验**实际 IP**，防 DNS Rebinding；每次请求重新解析 |
| **SR-3** | **破坏性方法默认禁用**：`DELETE`/`PUT`/`PATCH` 生成的用例默认不执行，需用户显式授权该 Operation | Case 携带 `is_destructive` 标记，执行器据此拦截 |
| **SR-4** | **禁止重定向**：或每跳重新执行 SR-1/SR-2 校验 | HTTP 客户端设 `follow_redirects=False` |
| **SR-5** | **出站限流与熔断**：防止平台成为 DoS 放大器 | 单目标 QPS 上限 + 连续失败熔断 |
| **SR-6** | **凭证管理**：目标 API 凭证加密存储（Fernet，密钥经环境变量注入），日志与 LLM Prompt 中一律脱敏 | 日志脱敏在 Gateway 层统一处理 |
| **SR-7** | **Spec 内容提示**：上传时提示用户 Spec 可能含内部信息，将发送给 LLM 提供商 | 上传界面 + 文档明示 |
| **SR-8** | **LLM 出站同样经过 Guardrail**：LLM 提供商 host 需在白名单中显式声明 | 复用同一套 Guardrail，不设旁路 |

> **SR-1 与 SR-8 的关系**：Guardrail 的设计原则是**唯一出站通道**。任何新增的外部调用（含新增 LLM 提供商）都必须走同一入口，否则该设计失效。这是架构层面必须写进 §2 的约束。

## 5. 非功能性需求（概要）

详细设计见 `07-非功能需求.md`，此处仅锁定 MVP 基线。

| 维度 | MVP 基线 | 备注 |
| :--- | :--- | :--- |
| 规模 | 单 Spec ≤ 200 Operations；单 Run ≤ 2000 Cases | 超出部分明确拒绝并提示，不做静默降级 |
| 并发 | 单机 4 个 Worker 进程，默认并发 8 | 可配置 |
| 部署 | 单机 Docker Compose | 不引入 K8s |
| 可观测性 | 结构化日志（JSON）+ 每次 LLM 调用的 token 与耗时记录 | 用于验证 M8 |
| 数据保留 | Run 与 Case 结果保留 90 天 | MVP 无归档，靠定期清理 |
| 幂等性 | Case 执行具备幂等键（Run ID + Case ID），重试不产生重复记录 | 与 Checkpoint 恢复配套 |

## 6. 风险与假设

### 6.1 假设

| 编号 | 假设 | 若不成立的影响 |
| :--- | :--- | :--- |
| A1 | 用户提供符合 OpenAPI 3.0/3.1 规范的文档 | M3 指标失效，需大幅增强解析容错 |
| A2 | 目标 API 有独立测试环境可供调用 | SR-3 的破坏性防护压力剧增，MVP 需重新评估 |
| A3 | 单用户、单机部署可接受 | 需提前引入多租户与分布式 Checkpoint（V2.0 提前） |

### 6.2 风险

| 编号 | 风险 | 影响 | 缓解措施 |
| :--- | :--- | :--- | :--- |
| R1 | LLM 生成"看似合理但错误"的用例 | 拉低 M1，污染目标数据 | 三层 Eval（§4.3）+ HITL 确认门 |
| R2 | Spec 质量参差（缺 example、`$ref` 循环） | 生成质量不可控 | 解析阶段显式降级：缺 example 时标注"低置信度用例"，供人工重点复核 |
| R3 | 用例污染被测环境数据 | 不可逆的数据损坏 | SR-3 默认禁用破坏性方法 + 建议指向测试环境 |
| R4 | SSRF / 平台被当作攻击跳板 | **严重安全事件** | SR-1~SR-4，且作为发布阻塞项 |
| R5 | LLM 成本或限流超预期 | 违反 M8，功能不可用 | 生成阶段限制并发；成本超阈值时降级为仅生成正常用例 |
| R6 | 范围蔓延（"顺手加个 XX"） | MVP 无法交付 | §3.3 Non-goals 作为评审依据，新增范围需先改本文档 |
