## 1. 三条排序原则

设计的顺序（模块依赖）与该先做的顺序**不是一回事**。以下三条决定了本文档的排法。

### RM1：先把端到端打通，再逐段加质量

**每个里程碑结束时，系统都必须能从一个 Spec 跑出一份报告。** 不允许"这个阶段只做了半个管线"。

理由是本项目最大的风险不在单点算法，而在**集成**：跨进程回调、Checkpoint 恢复、Guardrail 拦截、断言求值——这些问题的调试成本远高于"某个函数写错了"，而且**只有整条链路都通时才会暴露**。分段完成后一次性集成，会把所有集成问题堆到最晚、最贵的时刻。

代价是早期版本的每一段都很简陋（生成质量差、无归因、无界面）。这是刻意的：**M1 的目标是"通"，不是"好"。**

### RM2：先做最不确定的，后做最熟悉的

**IP-2（等待执行结果）排在 IP-1（人工确认）之前。**

| 中断点 | 技术复杂度 | 为什么 |
| :--- | :--- | :--- |
| **IP-2** | **高** | 跨进程回调、完成判定、竞态消除、回调丢失的兜底（`06` §6）——整个项目技术上最不确定的部分 |
| IP-1 | 低 | 等人点确认，本质是"挂起 + 恢复" |

先把 IP-2 做掉，意味着最大的技术未知在项目早期就被消解。若反过来先做 IP-1，M1 会显得进展顺利，而真正难的部分被推到后面。

### RM3：安全底线不延后

**`10` OP1 列出的六项"没有开关的行为"在 M1 就位。**

Guardrail 的 `policy.py` 是纯函数（`09` §2.2），大约百行规模、完全可单测。把它排在后面的唯一理由是"先跑通再说"——而**"以后再补安全"是最容易永远补不上的事**，尤其当系统已经"能用"之后。

### M1 — 最小闭环

**目标**：一份 Spec 进去，一份报告出来。**通路优先于质量。**

**交付**

| 交付物 | 说明 |
| :--- | :--- |
| `SpecParser` | 纯算法，`$ref` 展开、规范化、指纹（`03/SpecParser.md`） |

| `TestCaseGen` | 阶段 A（维度派生）+ 阶段 B 的**简化版**（不做重试与覆盖率校验） |
| Guardrail 同步客户端 | 白名单、SR-2、SR-3、SR-4 + 例外机制 |
| Celery Worker + `execution/runner` + 断言引擎 | `03/TestExecutor.md` |
| LangGraph 单链 + **IP-2** | 含回调唤醒、完成判定、per-Run 锁、兜底轮询 |
| `ReportAgent` 最小模板 | 只出通过率与失败清单 |

**验收**

```bash
docker compose up -d
./scripts/demo.sh   # 提交 fixture spec → 自动全批准 → 执行 → 报告
# 断言：报告存在，通过率非空且与 fixture 的实际行为一致
```

三条必须通过的专项检查：

| 检查 | 验证的设计点 |
| :--- | :--- |
| **人为丢弃一次回调**，图仍能推进 | `06` §6.4 兜底轮询 |
| 用 `/bad-json` 跑一次，断言级结果区分 `failed` 与 `error` | `03/TestExecutor.md` TE2 |
| 用 `/redirect` 跑一次，确认 3xx 被当作结果返回而非跟随 | `03/Guardrail.md` §6 |

第二条是 M1 最容易被实现偷懒的地方——把"无法求值"和"断言不符"合并，代码更短，但归因（M3）会因此无法分辨服务缺陷与响应非 JSON。

**不做什么**：不做 IP-1、不做前端、不做归因、不做覆盖率校验与重试。

**落地记录（2026-10-15）**

七个切片（低置信度标注 / IP-1 / 决策与用例端点 / 异步 Guardrail 与行为测试 / 对抗性测试集 / CLI / 前端）全部交付，CI 六步全绿，覆盖率 85%（M1 是 78%）。

但真正值得写下来的不是交付清单，而是**四个计划外的发现**——它们只在把整套服务（Gateway + Orchestrator + Worker + Beat + 前端）真的跑起来之后才暴露：

| # | 现象 | 根因 | 守门测试 |
| :-- | :--- | :--- | :--- |
| 1 | LLM 生成器**从未生效** | `QwenProvider.generate(*, prompt, schema)` 与图要的 `CaseGenerator.generate(operation, dimensions)` **同名不同契约**（前者关键字参数、后者位置参数）。每次调用抛 `TypeError`，被 `generate_for_operations` 的"部分失败不阻塞全局"接住 → Run 正常跑完、报告正常生成，只是**那个接口一条用例都没有** | `test_orchestrator_wiring.py::test_the_generator_is_callable_the_way_the_graph_calls_it`（断言失败**方式**是 `LLMError` 而不是 `TypeError`） |
| 2 | 被**人工拒绝**的用例出现在失败清单里，状态 `timeout` | `mark_unfinished_as_timeout` 只排除破坏性用例，没排除 `review_status != 'approved'` 的。补记成 timeout 等于说"我们发了请求但没等到回应"，而事实相反。报告据此凭空捏造一个系统故障结论，并把它算进通过率的分母（RA3） | `test_repositories.py::TestNonDispatchableCasesAreNeverMarkedTimeout` |
| 3 | 回调唤醒**整条路径从来没生效过**，Run 只能靠每分钟一次的兜底轮询推进（实测一次运行白等 60 秒） | `gateway/internal.py` 用 `runs.expected_case_count` 做完成判定，而那是**派生缓存**（DM5 明令禁止用于正确性判断）且没有任何节点维护它——恒为 0，于是判定永远返回 `pending` | `test_gateway_api.py::TestWakeEndpoint::test_wake_resumes_once_every_dispatchable_case_is_settled` |
| 4 | 同上（**独立的第二个原因**） | 唤醒回调发生在 `run_case` 内部，而那里只 `flush` 不 `commit`。唤醒的接收方是 Gateway 进程，它用**自己的会话**去数 `case_results`——看不到未提交的行。附带发现：回调抛异常会让 Celery 重投整个任务，即**对被测系统重复打一次请求** | `test_runner.py::TestWakeOrdering`（断言回调时 `session.in_transaction()` 为 `False`） |

**这四个 bug 有同一个形态**，而认识它比记住它们更有用：

> 不报错、不影响流程、只在数据里留下一个**安静的空白**。

1 号让"少了一个接口的用例"看起来像"这个接口没被覆盖"——而报告里本来就允许有未覆盖的接口；
2 号只在**有人拒绝过用例**时才成立（M1 没有拒绝入口，所以它是 IP-1 落地**之后才变得可达的**）；
3 号与 4 号把"应该是秒级"变成"一分钟一次"，而一个**慢但能跑完**的系统不会被任何人开成缺陷。

更麻烦的是**它们都躲过了测试**，而躲过的原因一致：**测试替换掉的恰好是被测的那一环**。

- 1 号：单测自己拼 generator，正好把"装配"那一步换掉了；集成测试注入的是规则生成器
- 3 号：网关测试的 producer 是一个假对象，不做真实的完成判定
- 4 号：第一版那条测试用**同一个会话**查库，`flush` 之后当然查得到——它验的是"同一会话可见性"，而需求是"跨进程可见性"

所以这一轮的结论不是"要写更多测试"，而是两件更具体的事：

1. **端到端真跑一遍，然后去看数据**（审计表、`case_results`、计数、日志告警），而不只是看"流程跑完了没有"。1 号靠审计表里没有 `direction='llm'` 发现，2 号靠 `case_results` 里出现一条不该有的 timeout，3/4 号靠盯时间线（62 秒 vs 3 秒）。
2. **关键接线写"真的调用一次"的测试**，而不是"断言对象存在"。`isinstance(provider, QwenProvider)` 通过了整整一个里程碑，而它是绿的、真的、也真的没用。

修完之后：同一次端到端从 **62.9 秒降到 3.2 秒**，报告里"被拒绝"回到未执行清单（`failures` 为空、`skipped=1`、`reason=rejected`）。

**另外记下一处已了结的文档与代码偏差**：`05` 的错误码写的是中划线（`run-not-awaiting-review`），而代码里历来是下划线（`spec_not_found` / `run_not_found`…）。M2 按**代码**的口径新增了 `run_not_awaiting_review` 与 `decision_incomplete`（ADR-0023：接口契约以代码为准），随后把 `05` 里**全部**错误码统一成下划线，并把拼法约定写进 §2.2。改动全在文档侧——代码一行未动。

**`spec_invalid` 的状态码（`400` vs `422`）由此一并了结**：代码返回 `400`，按 ADR-0023 以代码为准，`05` §4.1 已改为 `400`（见该文档 v0.4 变更记录第 ③ 条）。**不把代码改回 `422`。**

顺带在清点过程中发现另外两处**尚未处理**的契约偏差，记在这里以免忘掉：

| # | 偏差 | 现状 |
| :-- | :-- | :-- |
| 1 | `auth.py` 的 401 走的是 FastAPI 默认体（`{"detail": ...}`），**不是 `problem+json`**；而同文件末尾那个 `PROBLEM = PROBLEM_CONTENT_TYPE` 常量从未被使用 | §2.2 声称"错误响应**统一**为 problem+json"。落下了这一条，而它不会让任何测试失败 |
| 2 | 错误示例里曾有 `instance` 字段（RFC 9457 的标准字段之一），而 `ProblemDetail.to_payload()` 从不输出它 | 已从示例移除；若要支持需在 `problems.py` 里补 |

两条都属于"契约写了、代码没做"的同一类，而且都**不会**让测试变红——与 M2 那四个 bug 同源。

**LLM 密钥与模型**：`.env` 里那把 key 最初是占位值（长度 18），表现为 401。换成真值后 401 消失、但撞上 **403 `AllocationQuota.FreeTierOnly`**（`qwen3.5-plus` 免费额度用尽），于是改用 `qwen3.7-flash` 并在 `.env` 局部覆盖。**这不是选型变更**——理由与处置见 `02` §5.1 的偏差记录。真实模型生成链路由此第一次跑通：鉴权通过、产出通过维度契约校验、取值取自 schema 的 `example`、审计留下 `direction=llm / decision=allow`。顺带复验了"**审计写在发送之前**"这条对异步路径同样成立——请求被提供商 403 拒绝，审计里仍有一条 `allow`（放行决定早于发送，与请求最终成不成功无关）。

### M3 — 归因

**前置（已在开工前修掉）：`has_unresolved_ref` 的传播口径**

M2 验收发现"11 条用例置信度全是 `low`"。根因不在 `TestCaseGen`，在 `SpecParser`：
`$ref` 展开超限是**逐接口**发生的，但代码把 `expand_refs()` 返回的**文档级布尔值**
原样盖给了每个 `ParsedOperation`。于是一份文档里只要有一个递归结构，
其余接口生成的用例全部陪绑降级。

这条必须在 M3 之前修，因为 `LogAnalyzer` LA3 要求归因读取用例置信度：
带着这个 bug 上线，**每一条服务缺陷都会被降级成"可能是你的用例写错了"**，
报告会比不做归因更不可信。

修法（代码侧，`04` §2.2 早已写明正确口径）：`expand_refs()` 不再返回文档级布尔值，
改由 `_contains_ref()` 在展开后的**接口子树**上判断（含路径级 `parameters`）。
用 fixture 的真实文档验证：`GET /recursive` 标为不完整，其余 11 条干净。

**实现时定下的口径**（设计稿里含糊或自相矛盾之处，均回写到相应文档）：

1. 规则引擎**不产出** `assertion_mismatch`——该类别只有 LLM 能判（`LogAnalyzer` §11.5）
2. 补记的超时（`executor_stall`）**不归因、不进通过率分母**，报告单列"未完成"
3. LLM 重试次数跟随 `llm_max_retries`（原稿"1 次"与 `06` §7 / PRD §4.3 冲突）
4. 删掉"除非有额外证据"的置信度口子——没有可执行定义
5. LLM 失败/超预算 → 落 `unknown` + `NodeFailure`，**不允许失败用例没有归因行**
6. 响应体截断时归因置信度最高 `medium`
7. 人工纠错只做后端 + API；前端复核界面留到后续
8. 成本记账（token/金额）留在 M4——`attributions` 与 `audit_logs` 都没有用量字段

优先级短路 + 不该命中的边界）、`test_log_analyzer.py`（11 条）、
`test_domain_attribution.py`（置信度封顶矩阵）、
`tests/integration/test_attribution_node.py`（13 条，真库）、
`test_m3_acceptance.py`（端到端验收）。

**Golden Set 发现的三处盲区（这才是 M5 的价值）**：

1. **`pattern` 不派生维度**——`constraint_violation` 原来只认 `enum`。带正则的字段
   在分母里根本不存在，覆盖率仍然 100%。已修复（`dimensions.py`）。
2. **`format` / `multipleOf` 同样漏掉**——§2.3 的维度表写着四种约束，实现只做了一种。
   一并修复，并补了 `test_dimensions_constraints.py`。
3. **自定义 `format` 没有降级标注**——`imei` 这类格式"什么值算违法"只能靠猜，
   §7 触发 ④ 一直写在注释里但没有实现。现在该维度的用例标 `low`。

**同一配置三次运行相差 7 个百分点**（100% → 93%），单轮的最好成绩是 100%、最差是 80%。
这正是 `09` TS6 要求"每档 ≥ 3 轮、用最差一次做决策"的原因：单次对比无法区分
档位差异与随机波动。一次 100% 只能说明"这次没出错"，不能说明"质量稳定在 100%"。

**L3 输出的一个口径决定**：传输失败（超时、连接失败）**不计入首次通过率的分母**。
把它算进去会让网络抖动看起来像提示词退化，而两者的处置完全不同——一个重跑，
一个改提示词。但传输失败的次数必须单独报出来，不能悄悄丢掉；否则"27 次只跑了
25 次"就没人知道了。首轮两次超时正是这样被识别出来的，第二次运行改为 0 次超时、
1 次真正的内容失败（`ValidationError`）。

**一处刻意偏离**：`04` §5 说审计日志保留 90 天，但清理任务**不删 `audit_logs`**。
审计是"发生过什么"的唯一凭证，批量删除它的能力应当有独立的人工授权入口，
不该藏在每日定时任务里。Run 删除仍会把 `audit_logs.run_id` 置 NULL，记录保留。

**另修一个环境问题**：`redis_url` 默认值由 `localhost` 改为 `127.0.0.1`。
Windows 上 `localhost` 优先解析到 `::1`，而 Docker 只发布 IPv4 端口——
`/readyz` 因此在开发机上超时。这不是测试的偶发失败，而是"连接一个不存在
的地址直到超时"的真实配置缺陷。

**M5 之后补的一个指标（2026-10-25）：用例准确率。**
前面所有质量数字都不能回答"生成的用例本身写得对不对"——L3 首次通过率测的是
结构与覆盖，demo 的采纳率是脚本自动批准的。新增 `scripts/label_cases.py`
两步流程（生成标注表 → 人工填 `verdict` → 汇总），标注独立于生成方。
在生成第一版标注表时发现：Qwen 3.7 Flash 对自由格式 `request_body` 会输出
不合法的 JSON 片段（键名前多出冒号、出现空键），SDK 宽松解析后变成
`{': email': ...}` 或 `{}`。现已改为"模型输出 JSON 字符串 → 平台解析校验"，
解析失败走带反馈重试；回归测试见 `tests/unit/test_free_form_repair.py`。

## 4. 关键路径与风险

### 4.1 关键路径

```
PG schema ─→ SpecParser ─→ LLM Provider ─→ TestCaseGen ─┐
                                                          ├─→ 图 + IP-2 ─→ Executor ─→ Report
                        Guardrail policy ────────────────┘
```

旁支（可并行但都汇入终点）：LogAnalyzer（M3）、前端/CLI（M2）、Eval（M5）。

### 4.2 风险最高的三处

| 风险 | 为什么不确定 | 何时消解 |
| :--- | :--- | :--- |
| **LLM 生成质量能否达到 M1 ≥ 70%** | 完全未知，可能需要多轮 Prompt 迭代 | M1 出第一个数字（**哪怕很差**），M4 优化 |
| **LangGraph 的 interrupt / resume 语义** | 不同版本间有过演进（`06` §5.2 已警示"不要凭记忆写 API"） | M1 |
| **跨进程回调的正确性**（丢 / 重 / 乱序） | 设计已较完整（`06` §6），但实现细节多 | M1 |

**RM4：M1 必须产出一个生成质量数字，无论多差。**

理由：M1 的验收若只检查"链路通不通"，就不会暴露"生成质量可能根本不达标"这个最大的不确定性。哪怕只有 3 个接口、采纳率 20%，**有一个真实数字**才能判断问题出在 Prompt、Schema 约束还是模型能力。

这也意味着 M1 的验收包含一次**人工过目**——看一眼生成的用例是否离谱。

| 编号 | 问题 | 影响 | 待决 |
| :--- | :--- | :--- | :--- |

| Q4 | `05` §4.5 的错误码用中划线，代码里用下划线 | 同一份契约两种拼法，对消费者是实打实的负担 | **未处理**。收敛方向是改文档（ADR-0023：契约以代码为准），但需要通盘检查全部错误码与其引用，属一次独立改动 |

**Q1 值得留意**：临时的便利开关是典型的"临时即永久"。若 M1 引入它，必须同时引入一条**它不可被误启用的测试**，否则它会以"反正测试环境在用"的名义留到生产。

**Q1 的结果**（2026-10-15）：M1 加了它，M2 删了它——而删除的代价几乎是零，因为**它只有一个调用点**（N3）。这条经验可以推广：让临时做法**只在一处**被调用，它的"临时性"才真的可兑现。反过来说，一个被三处调用的临时开关，即使当初打算删，删的时候也会动摇。
