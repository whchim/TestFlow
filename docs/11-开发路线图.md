## 1. 三条排序原则

设计的顺序（模块依赖）与该先做的顺序**不是一回事**。以下三条决定了本文档的排法。

### RM1：先把端到端打通，再逐段加质量

**每个里程碑结束时，系统都必须能从一个 Spec 跑出一份报告。** 不允许"这个阶段只做了半个管线"。

理由是本项目最大的风险不在单点算法，而在**集成**：跨进程回调、Checkpoint 恢复、Guardrail 拦截、断言求值——这些问题的调试成本远高于"某个函数写错了"，而且**只有整条链路都通时才会暴露**。分段完成后一次性集成，会把所有集成问题堆到最晚、最贵的时刻。

代价是早期版本的每一段都很简陋（生成质量差、无归因、无界面）。这是刻意的：**M1 的目标是"通"，不是"好"。**

### RM2：先做最不确定的，后做最熟悉的

**IP-2（等待执行结果）排在 IP-1（人工确认）之前。**

| 中断点 | 技术复杂度 | 为什么 |
| :--- | :--- | :--- |
| **IP-2** | **高** | 跨进程回调、完成判定、竞态消除、回调丢失的兜底（`06` §6）——整个项目技术上最不确定的部分 |
| IP-1 | 低 | 等人点确认，本质是"挂起 + 恢复" |

先把 IP-2 做掉，意味着最大的技术未知在项目早期就被消解。若反过来先做 IP-1，M1 会显得进展顺利，而真正难的部分被推到后面。

### RM3：安全底线不延后

**`10` OP1 列出的六项"没有开关的行为"在 M1 就位。**

Guardrail 的 `policy.py` 是纯函数（`09` §2.2），大约百行规模、完全可单测。把它排在后面的唯一理由是"先跑通再说"——而**"以后再补安全"是最容易永远补不上的事**，尤其当系统已经"能用"之后。

## 2. 里程碑总览

| 里程碑 | 目标 | 规模 | 核心风险 | 状态 |
| :--- | :--- | :--- | :--- | :--- |
| **M0** 地基 | 仓库、CI、schema、配置、fixture、Guardrail 策略 | S | 低 | ✅ 已完成（2026-10-14） |
| **M1** 最小闭环 | **端到端跑通**（含 IP-2，不含 IP-1） | **L** | **高** | ✅ 已完成（2026-10-14） |

## 3. 各里程碑

### M0 — 地基

**交付**

| 交付物 | 依据 |
| :--- | :--- |
| 仓库结构与四个入口点 | `08` §1、EN1 |

**验收**

```bash
./scripts/ci.sh                                # 六步全绿（Windows 无 make，故用脚本）
uv run alembic upgrade head && uv run alembic downgrade base   # 双向可跑
uv run pytest tests/unit/test_guardrail_policy.py              # 网段与 ::ffff: 用例全过

```

**不做什么**：不接 LLM、不写图、不做前端。

### M1 — 最小闭环

**目标**：一份 Spec 进去，一份报告出来。**通路优先于质量。**

**交付**

| 交付物 | 说明 |
| :--- | :--- |
| `SpecParser` | 纯算法，`$ref` 展开、规范化、指纹（`03/SpecParser.md`） |
| LLM Provider 接口 + 百炼适配器 | **注入 Guardrail 的 http_client**（`08` §2.3） |
| `TestCaseGen` | 阶段 A（维度派生）+ 阶段 B 的**简化版**（不做重试与覆盖率校验） |
| Guardrail 同步客户端 | 白名单、SR-2、SR-3、SR-4 + 例外机制 |
| Celery Worker + `execution/runner` + 断言引擎 | `03/TestExecutor.md` |
| LangGraph 单链 + **IP-2** | 含回调唤醒、完成判定、per-Run 锁、兜底轮询 |
| `ReportAgent` 最小模板 | 只出通过率与失败清单 |

**验收**

```bash
docker compose up -d
./scripts/demo.sh   # 提交 fixture spec → 自动全批准 → 执行 → 报告
# 断言：报告存在，通过率非空且与 fixture 的实际行为一致
```

三条必须通过的专项检查：

| 检查 | 验证的设计点 |
| :--- | :--- |
| **人为丢弃一次回调**，图仍能推进 | `06` §6.4 兜底轮询 |
| 用 `/bad-json` 跑一次，断言级结果区分 `failed` 与 `error` | `03/TestExecutor.md` TE2 |
| 用 `/redirect` 跑一次，确认 3xx 被当作结果返回而非跟随 | `03/Guardrail.md` §6 |

第二条是 M1 最容易被实现偷懒的地方——把"无法求值"和"断言不符"合并，代码更短，但归因（M3）会因此无法分辨服务缺陷与响应非 JSON。

**不做什么**：不做 IP-1、不做前端、不做归因、不做覆盖率校验与重试。

| **对抗性测试集** | `09` §4 |
| 低置信度标注 + 前端按置信度排序 | `03/TestCaseGen.md` §7 |

**验收**

```bash
pytest tests/security/adversarial/    # TS4 全绿
testflow run ./specs/fixture.yaml     # CLI 端到端
```

两条必须通过的专项检查：

| 检查 | 验证的设计点 |
| :--- | :--- |
| Spec 指向内网 + **不配例外** → 请求被拒，审计含 `private_ip` | **`03/Guardrail.md` §4.6、`09` TS8** |
| 故意在 `llm/qwen.py` 里不注入 Guardrail 客户端 → 行为测试失败 | `08` §2.3 |

第一条是那个安全论断的守门人：**例外只能来自配置、永不从 Spec 派生**。若实现错误地从 Spec 派生，其余所有测试仍会通过（因为它们一直用内网地址）。

**不做什么**：不做归因、不做缓存优化。

## 4. 关键路径与风险

### 4.1 关键路径

```
PG schema ─→ SpecParser ─→ LLM Provider ─→ TestCaseGen ─┐
                                                          ├─→ 图 + IP-2 ─→ Executor ─→ Report
                        Guardrail policy ────────────────┘
```

旁支（可并行但都汇入终点）：LogAnalyzer（M3）、前端/CLI（M2）、Eval（M5）。

### 4.2 风险最高的三处

| 风险 | 为什么不确定 | 何时消解 |
| :--- | :--- | :--- |
| **LLM 生成质量能否达到 M1 ≥ 70%** | 完全未知，可能需要多轮 Prompt 迭代 | M1 出第一个数字（**哪怕很差**），M4 优化 |
| **LangGraph 的 interrupt / resume 语义** | 不同版本间有过演进（`06` §5.2 已警示"不要凭记忆写 API"） | M1 |
| **跨进程回调的正确性**（丢 / 重 / 乱序） | 设计已较完整（`06` §6），但实现细节多 | M1 |

**RM4：M1 必须产出一个生成质量数字，无论多差。**

理由：M1 的验收若只检查"链路通不通"，就不会暴露"生成质量可能根本不达标"这个最大的不确定性。哪怕只有 3 个接口、采纳率 20%，**有一个真实数字**才能判断问题出在 Prompt、Schema 约束还是模型能力。

这也意味着 M1 的验收包含一次**人工过目**——看一眼生成的用例是否离谱。

## 5. 明确不在路线图内

以下属于 V1.0 及以后（PRD §3.1 / §3.4），**在 M5 完成前不启动**：

| 功能项 | 依据 |
| :--- | :--- |
| 向量库 + BM25 混合检索归因 | `02` §3.1、`03/LogAnalyzer.md` §10 |
| Callback API（跨机部署） | `02` §1.2 |
| 对象存储（大日志） | `02` §3.1 |
| 独立 Egress Proxy 进程 | `02` D2 |
| 破坏性用例的授权入口 | `03/TestExecutor.md` TE3 |
| CI 集成 / 脚本导出 / 趋势对比 | `01-PRD` §3.3 / §3.4 |
| 多租户 | `01-PRD` §3.3 |

**RM5：这份清单的作用是挡需求，不是待办。**

PRD §3.3 已经把"不做的事"写下来了，但在实际开发中，"顺手加个 XX"的诱惑出现在每一个里程碑。这份清单的用途是在那时能被引用——**新增范围前先改 PRD，而不是先写代码**。

## 6. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **RM1** | 每个里程碑都必须端到端可跑 | 集成问题比单点问题难得多，分段完成后一次性集成会把问题堆到最晚最贵的时刻 |
| **RM2** | IP-2 排在 IP-1 之前 | 先消解最不确定的技术未知，而不是先让进度好看 |
| **RM3** | 安全底线在 M1 就位 | "以后再补安全"是最容易永远补不上的事；且 policy 是纯函数，成本低 |
| **RM4** | M1 必须产出生成质量数字 | 否则最大的不确定性不会被暴露 |
| **RM5** | 非 MVP 清单用于挡需求 | 新增范围前先改 PRD，而不是先写代码 |

## 7. 开放问题

| 编号 | 问题 | 影响 | 待决 |
| :--- | :--- | :--- | :--- |
| Q1 | M1 是否需要一个"自动全批准"的临时开关（跳过 IP-1） | 影响 M1 的实现量；该开关必须在 M2 移除，否则会成为绕过确认门的后门 | 实现时定；**若加，必须同时加一条测试断言它在生产配置下不可用** |
| Q2 | 各里程碑的绝对工期 | 影响排期 | 取决于可投入工时；本文档只给相对规模 |
| Q3 | 是否需要在 M2 前做出可用界面，或先用 curl 验证 | 影响 M2 的范围 | 倾向 M2 一次做掉——curl 验证无法覆盖置信度排序等界面逻辑 |

**Q1 值得留意**：临时的便利开关是典型的"临时即永久"。若 M1 引入它，必须同时引入一条**它不可被误启用的测试**，否则它会以"反正测试环境在用"的名义留到生产。
