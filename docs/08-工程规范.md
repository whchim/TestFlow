## 2. 依赖约束

### 2.1 三条已经在别处承诺、但没有承载体的约束

| 约束 | 出处 | 若不强制会怎样 |
| :--- | :--- | :--- |
| Guardrail 是服务端唯一出站通道 | `02` D2、`03/Guardrail.md` GR7 | 某天有人为图省事直接 `import httpx`，白名单对这部分流量失效，**且没有任何测试会发现** |
| LLM 调用收敛在 Provider 接口之后 | `02` D7 | Qwen 的调用细节渗进业务代码，换档位或换厂商时改动面失控 |
| CLI 不重复实现业务逻辑 | `01-PRD` F9 | CLI 内嵌一套"本地直连"路径，绕过 Gateway 的统一日志脱敏 |

三条的共同点是：**它们都是靠自觉维持的约定，而没有强制的失败点**。所以必须落成 CI 可检测的规则。

### 2.2 依赖白名单

**EN2：用静态检查强制以下 import 规则。**

| 模块 | 允许的 HTTP/SDK 依赖 | 理由 |
| :--- | :--- | :--- |
| `guardrail/` | `httpx` / `httpx2` / `httpcore` / `httpcore2` | 服务端唯一出站通道 |
| `llm/` | `openai` / `dashscope` | 唯一允许接触 LLM SDK 的地方（D7） |
| `client/` | `httpx` | 控制面专用，只访问配置里的固定地址 |
| **其余所有服务端模块** | **禁止以上全部** | |

**⚠️ M1 实现回写——禁令名单原本漏了 `httpx2` / `httpcore2`。**

初稿的名单是 `{httpx, requests, aiohttp, urllib3, httpcore}`。**而 `openai` 3.x 依赖的是 `httpx2`——一个独立于 `httpx` 的包**（内含自己的 `httpcore2`）：

```
$ python -c "import importlib.metadata as m; print(m.requires('openai'))"
['httpx2<3,>=2.12.0', ...]
```

它同样能发起出站请求，因此必须同等禁止——否则"Guardrail 是唯一出站通道"就**多了一条没人看着的路径**。已补入名单，并加了三条参数化用例与一条"`llm/` 可以 import SDK 但不能 import HTTP 客户端"的结构性测试。

**⚠️ M1 实现回写——`client/` 的定位从「CLI 专用」扩为「控制面」。**

原文写的是"CLI 专用 HTTP 客户端"。M1 需要 Worker 调用 Gateway 的内部唤醒端点（`06` §6.1），而那也是一次**进程间通信**：

| | Guardrail 管的 | `client/` 管的 |
| :--- | :--- | :--- |
| 打谁 | **被测目标**（地址来自用户上传的 Spec，不可信） | **我们自己**（地址来自应用配置） |
| 信任级别 | 低 | 高（需要内部令牌） |

把它塞进 Guardrail 会造成两处混淆：白名单被一个与被测系统无关的地址污染，以及两种信任级别混同。

**但扩展是有界的**：`client/` 里只有打固定地址的客户端，没有任何接收 URL 参数的方法。要再扩大引用范围，得先改这一行——而**改一行需要写的理由，就是这条规则的价值所在**。

**范围界定**：约束针对**服务端代码**（`gateway/` `graph/` `agents/` `execution/` `storage/` `llm/`）。`client/` 属于客户端工具，它访问的是用户自己配置的一个地址，不是任意用户可控的 host，因此不适用"唯一出站通道"这条（该约束的存在理由是防 SSRF，而 CLI 不接收来自 Spec 的 URL）。

补充规则：`client/` **只能被进程入口点引用**（M1：`entrypoints/cli.py` 与 `entrypoints/worker.py`），防止服务端代码借道它绕过 Guardrail。

### 2.3 一条静态检查不到、必须用测试守住的约束

`llm/qwen.py` 使用 OpenAI 兼容模式的 SDK 时，SDK 会**自己创建 HTTP 传输**——若直接构造，它的流量就绕过了 Guardrail。

正确做法是**把 Guardrail 的 `httpx` 客户端注入进 SDK**：

```python
# llm/qwen.py 的形态（示意）
client = OpenAI(
    base_url=config.llm_base_url,
    http_client=guardrail.async_client(),  # ★ 注入，而非让它自己建
)
```

这条**无法用 import 规则检测**——`llm/` 允许 import SDK，而"是否注入了 guardrail 客户端"是运行期事实。

因此需要一条**行为测试**（放在 `tests/integration/`）：

> 构造 LLM 适配器 → 发起一次真实调用（指向本地 mock）→ 断言 Guardrail 的审计日志中出现了该请求。

**这条测试比 import 检查更重要**：它验证的是"约束在运行期确实成立"，而不是"代码看起来符合规范"。

### 2.4 静态检查的实现

用 `import-linter` 的契约式配置，或一个基于 AST 的自定义检查脚本。二者都可接受，选型不敏感——**关键是它必须跑在 CI 里，且违规时构建失败**。

检查脚本放在 `tests/architecture/`，与规则本身同目录，便于阅读时对照。

## 3. 配置管理

**EN3：环境变量只在 `config.py` 读取一次，其余模块接收配置对象。**

```python
# config.py
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="TESTFLOW_")
    ...
```

| 规则 | 理由 |
| :--- | :--- |
| 不 `os.environ` 散落各处 | 测试时无法覆盖；配置项无处可查 |
| 不在模块导入时实例化配置 | 导入即读环境变量会让测试无法注入 |
| 配置项在 `config.py` 集中声明并带默认值 | 它是配置的**唯一清单**，同时服务于 `10-部署运维.md` |

`05` §2.1 的"非环回地址时强制要求 Token"就是一项启动期校验，实现位置在 `config.py`——**非法配置应在启动时失败，而非运行时**。

## 6. CI 流水线

顺序即依赖关系，任一步失败即中止：

```
① lint              ruff format --check && ruff check
② type              mypy
③ architecture      依赖白名单检查（§2.2）
④ contract & schema openapi.json 快照校验（05 §1.2）+ alembic check（§7）
⑤ test              unit + integration
⑥ build             镜像构建
```

实现见 `scripts/ci.sh`（**不是 Makefile**：Windows 默认无 `make`，装它是多余的依赖；而 bash 脚本在 Git Bash 与 GitHub Actions 上行为一致）。

### 6.1 为什么 `architecture` 排在 `test` 之前

依赖违规是**结构性缺陷**，修起来影响面大；测试失败通常是局部问题。先跑便宜且结论明确的检查，能让开发者在最短时间内收到最有价值的反馈。

### 6.2 `contract` 检查的做法

```
启动应用 → 导出 /openapi.json → 与仓库中的快照比对 → 不一致则失败
```

失败时的正确反应是**运行生成命令并提交**，而不是手动编辑 `openapi.json`——后者会让快照与代码脱节，而 CI 也会立刻再拒绝一次。

### 6.3 为什么 `alembic check` 与 `contract` 合并为一步

两者都是**"派生物与源头是否脱节"**的检查：`contract` 查"代码 ↔ 接口快照"，`alembic check` 查"模型 ↔ 迁移"。性质相同、代价相同，合并成一步能少一次进程启动。

**`alembic check` 是比行覆盖率更有力的检查。** 声明式模型没有可执行逻辑——给它算覆盖率是噪声（类体被执行一次就"满分"，而这说明不了任何事）。`alembic check` 能发现"模型改了但没生成迁移"，而那正是 §7 EN7 要防的漂移。因此覆盖率配置里**刻意排除**了 `storage/models.py`，把验证责任交给这一步。

### 6.4 未实现的步骤应"明确跳过"而非报错

M0 阶段 Gateway 与 Dockerfile 都不存在，④⑥ 两步会自行判断并输出 `⊘ 跳过`。

**这一点很重要**：一个因为"后续里程碑还没做"而长期变红的 CI，**等于没有 CI**——你无法从红色里区分"真有错"和"还没写到"。让检查在还不该生效时**明确地跳过去**，比让它报一个假错有用得多。

## 7. 数据迁移

**EN7：Alembic migration 是数据库结构的唯一事实来源**（`04-数据模型.md` 开头已声明）。

| 规则 | 说明 |
| :--- | :--- |
| 每次 schema 变更必须带 migration | 不允许手工改库 |
| 变更须同步更新 `04-数据模型.md` | 文档与 migration 的差异必须显式解决，不允许长期并存 |
| migration 必须可重入 | 与 `06` §5.3 对节点的要求同理 |

`04` v0.2~v0.5 累计新增了 4 个字段（`cases.dimension`、`cases.requires_auth`、`case_results.assertion_outcomes`、`attributions.human_category`），这些是**设计阶段**的收敛，实现时都属于**首个** migration 的内容，不是增量迁移。

### 7.1 一个实际踩到的坑：`alembic.ini` 必须是纯 ASCII

**Alembic 用 `encoding="locale"` 读取 `alembic.ini`**，而中文版 Windows 的 locale 是 GBK。文件里只要有非 ASCII 字符（哪怕只是中文注释），启动时就是 `UnicodeDecodeError`。

**关键点：`PYTHONUTF8=1` 救不了这个。** 它影响的是 Python 的默认 I/O 编码，管不到一个显式传了 `encoding="locale"` 的调用。这个坑的迷惑性就在这里——`ci.sh` 已经导出了 `PYTHONUTF8=1`，看起来"编码问题应该解决了"，但它对 Alembic 读配置这件事无效。

因此：**`alembic.ini` 保持纯 ASCII**，中文说明放到 `migrations/env.py`（Python 源文件，编码可控）。

> 更一般的教训：**一个文件"能不能写非 ASCII"，取决于读取它的那一方用什么编码打开它，而不是取决于我们这边的默认编码。** 遇到 `UnicodeDecodeError` 时，先看是谁在读、用什么编码读，而不是先去改环境变量。

## 8. 测试组织

| 目录 | 内容 | 是否进常规 CI |
| :--- | :--- | :--- |
| `tests/unit/` | 纯函数：Guardrail 的网段判定与白名单、断言求值引擎、SpecParser 的规范化与指纹、LogAnalyzer 的规则库 | ✅ |
| `tests/integration/` | 需要 DB / Redis / Celery 的场景；含 §2.3 的行为测试 | ✅ |
| `tests/architecture/` | 依赖白名单检查 | ✅（在 §6 的第 ③ 步） |
| `tests/eval/` | L3 Golden Set 回归（PRD §4.3） | ❌ **默认不进** |

**EN8：Eval 不进常规 CI。**

理由：它调用真实的 LLM，**每次运行都花钱**（`02` §5.4），且 Prompt 未变时结果稳定、重复跑没有新信息。触发方式：手动、或按需的定时任务。

`tests/eval/golden/` 是 PRD §4.3 指定的 Golden Set 存放位置，**与代码同目录维护**——这样 Prompt 变更与 Golden Set 调整出现在同一个 PR 里。

## 9. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **EN1** | 单包多入口，一个镜像 | **五个入口点**（gateway / orchestrator / worker / beat / cli，M1 补 beat）；Compose 中跑**四个长驻应用服务**（gateway / orchestrator / worker / beat，见 `10-部署运维.md` §7）。单机部署下最简，共享领域代码，不需要多包与私有源 |
| **EN2** | 用静态检查强制依赖白名单 | GR7 / D7 / F9 三条承诺若无 CI 强制，只是自觉 |
| **EN3** | 环境变量只在 `config.py` 读取 | 可测试性；配置项有唯一清单 |
| **EN4** | MVP 前端由 Gateway 静态托管 | 省一个容器，且免去 CORS 配置 |
| **EN5** | 日志禁记凭证与正文 | 写入容易，彻底清除困难 |
| **EN6** | `openapi.json` 快照进 CI | 防止"实现改了契约没更新"静默发生 |
| **EN7** | migration 是 schema 唯一事实来源 | 文档与 migration 的漂移必须显式解决 |
| **EN8** | Eval 默认不进常规 CI | 每次运行都花钱，且 Prompt 未变时无新信息 |
