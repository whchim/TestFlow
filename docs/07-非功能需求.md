## 1. 基线声明

**NF1：本项目的非功能数值**（性能目标、容量上限）**是设计目标，不是实测承诺。**

它们来自架构推演与量级估算，用于**驱动设计取舍**（例如 Qwen 的 128K 阶梯计费决定了逐 Operation 调用，`02` §5.1）与**划定 MVP 边界**（例如单 Spec ≤ 200 Operations 决定了不做游标分页，`05` §2.3）。

实现后必须用实测数据校准，并把校准结果回写到本文档。**未经验证的目标值若被当成承诺，会让后续的技术决策建立在错误的前提上。**

## 2. 性能

### 2.1 目标

| 编号 | 目标 | 说明 |
| :--- | :--- | :--- |
| M2 | 单接口用例生成 P95 ≤ 30s | 从 SpecParser 完成到用例入库 |
| M5 | 端到端闭环 P95 ≤ 5min | 20 接口规模，Spec 上传 → 报告产出 |

### 2.2 这两个目标由什么决定

**M2 几乎完全由 LLM 调用耗时决定**——它是唯一的外部依赖，且不在我们的控制内（模型档位、服务端排队、思考模式的深度）。因此：

- 该目标的价值不在"能否达到"，而在**定义了可接受的等待上限**
- 若实测显著超出，可动的杠杆是**降低 `enable_thinking` 的使用范围**（`02` §5.3 已对 `LogAnalyzer` 关闭），而非换更小的模型——质量优先（`02` §5.1）

**M5 由 M2 × 接口数 ÷ 并发度决定**（外加 HITL 等待，不计入——用户在确认环节的耗时不是平台性能）。20 接口 × 30s ÷ 4 并发 ≈ 2.5 分钟，加执行与归因，5 分钟的上限是合理的。

### 2.3 不计入性能目标的等待

| 环节 | 为何不计入 |
| :--- | :--- |
| IP-1 人工确认 | 用户离开去开会是常态（`06` §5.1 允许挂起 7 天） |
| IP-2 执行等待 | 取决于目标 API 的响应速度，不是平台的性能 |
| Celery 排队 | 队列积压属于容量问题（§3），不是单次延迟 |

**把用户思考和目标服务响应的时间算进"平台性能"，会让指标失去意义**——它无法反映任何一方的真实状况。

## 3. 规模与容量

### 3.1 硬上限

| 项 | 上限 | 超出时的行为 |
| :--- | :--- | :--- |
| 单个 Spec 的 Operation 数 | 200 | **明确拒绝并提示**，不静默降级（PRD §5） |
| 单个 Run 的 Case 数 | 2000 | 同上 |
| Spec 文件大小 | 10 MB | `413 Payload Too Large`（NF4） |
| 单条响应体 | 256 KB | 截断 + 标记（`04` DM6） |
| 并发 Worker | 4 进程 × 并发 8 | 可配置（`02` §5） |

**NF2：超限一律明确拒绝，不做静默降级。**

静默降级（例如"超过 200 个接口只取前 200"）会让用户以为全部测过了——这比直接失败危险得多。**用户宁可看到"你的 Spec 太大了"，也不愿看到一份不完整的报告。**

### 3.2 存储增长

PG 体积的主要变量是**响应体**（`case_results.response_body`，上限 256 KB）：

| 场景 | 单 Run 体积 | 90 天保留（每天 10 Run） |
| :--- | :--- | :--- |
| 典型（100 case × 平均 5 KB） | ≈ 0.5 MB | ≈ 450 MB |
| 最坏（2000 case × 256 KB） | ≈ 512 MB | 无法承受 |

两个场景差三个数量级。**NF3：必须监控 PG 体积，并把响应体大小分布作为已采指标。**

`04` DM6 选择 256 KB 是基于"归因所需信息集中在前几 KB"的判断——这个判断需要实测验证。**一旦响应体成为体积主因，正确的反应是把它迁到对象存储（`02` §3.1 的 V1.0 项），而不是简单调低下限**（那会损害归因质量）。

### 3.3 冗余与横向扩展

| 组件 | 可横向扩展 | 约束 |
| :--- | :--- | :--- |
| Celery Worker | ✅ 无状态 | 受 Guardrail 限流阈值约束（`03/Guardrail.md` GR9），加副本前需先调阈值 |
| Gateway | ✅ 无状态 | SSE 连接是有状态的，需粘性会话或改造 |
| Orchestrator | ⚠️ **受限** | per-Run 分布式锁保证串行（`06` G9）；多副本安全，但同一 Run 的推进仍串行 |
| PostgreSQL / Redis | ❌ 单实例 | MVP 不做主从 |

**MVP 不做高可用**（PRD §5 部署基线），但上述约束表明**架构不阻止横向扩展**——需要做的改造是 Gateway 的 SSE 会话粘性。

## 4. 可靠性

### 4.1 数据

**NF5：PostgreSQL 必须配置备份。**

理由直接来自 `02` §7 的核心原则：**PG 是唯一事实来源，Redis 只是进度指针。**

| 存储 | 丢失的后果 | MVP 态度 |
| :--- | :--- | :--- |
| Redis 全丢 | 未完成的 Run 标记失败，可从 PG 已有结果重跑 | **可接受**（`02` §7 明确） |
| PG 全丢 | **所有 Spec、用例、结果、审计日志、凭证全部不可恢复** | **不可接受** |

`02` §7 对 Redis 的容忍态度容易让人顺带对 PG 也放松——**两者的性质完全不同**。备份的具体方式（`pg_dump` 定时 + 保留策略）见 `10-部署运维.md`。

### 4.2 运行中断

| 中断 | 恢复方式 | 依据 |
| :--- | :--- | :--- |
| 任一进程重启 | 从 Checkpoint 恢复，无需人工介入 | `06` §5.3 |
| Redis 不可用 | Run 停滞；恢复后由兜底轮询接管 | `06` §6.4 |
| 目标 API 长时间不可用 | 熔断（`03/Guardrail.md` §7）；Run 按部分失败推进 | `06` §6.4 |

### 4.3 无 SLA 承诺

MVP 是单机自用工具，**不承诺可用性指标**。这一点应显式记录，以免后续把"单机部署"当成一个未达成的 HA 目标去追。

## 5. 可观测性

本节把散落在各处的指标采集方式收敛到一处。

### 5.1 三类信号与各自的用途

| 信号 | 存储 | 保留 | 用途 |
| :--- | :--- | :--- | :--- |
| **应用日志** | stdout（结构化 JSON） | 由部署决定 | 排障 |
| **审计日志** | PG `audit_logs` | 90 天（`04` §5） | **安全追溯** |
| **指标** | 随报告落库 + 日志埋点 | 同 Run | 质量与成本的度量 |

三者不合并：审计日志需要事务与长期保留，应用日志需要低开销与可检索，指标需要可聚合。**用一套机制承载三种需求，必然在某一方面妥协。**

### 5.2 M1 至 M8 的采集落点

| 指标 | 采集方式 | 来源 |
| :--- | :--- | :--- |
| **M1** 用例采纳率 | `cases.review_status = 'approved'` / 总数 | PG 聚合 |
| **M2** 单接口生成耗时 | 节点耗时埋点 | 日志埋点 |
| **M3** Spec 解析成功率 | N1 成功/失败计数 | 日志埋点（跨 Run 聚合） |
| **M4** 归因认可率 | `attributions.human_verdict = 'agree'` 比例 | PG 聚合 |
| **M5** 端到端耗时 | `runs.created_at` → `finished_at` | PG |
| **M6** 平台单测覆盖率 | CI 产出的覆盖率报告 | CI（`09` §2.3） |
| **M7** 破坏性用例误执行 | `audit_logs` 中 `deny_reason = 'destructive'` 的 `allow` 计数 | **审计日志 + 告警** |
| **M8** LLM 成本 | 每次调用的 token 用量 × 单价 | 日志埋点 + 报告 |

**M1 与 M4 的分母需要注意**（`09` §5.2 的同一原则）：

- M1 的分母是"生成了的用例"，若生成阶段就有系统性缺陷，采纳率反映不出
- M4 的分母是"平台判定的失败"，**若失败判定本身有问题，认可率再高也没有意义**

### 5.3 先行指标与滞后统计

**NF6：区分两类指标，只有先行指标需要告警。**

| 类别 | 指标 | 为什么 |
| :--- | :--- | :--- |
| **先行**（要盯） | **M7** 破坏性误执行 | 目标值 **0**。见下 |
| **先行** | 规则覆盖率（`03/LogAnalyzer.md` §2.2） | 下滑时成本将随之上升，但**问题还没体现在账单上** |
| **先行** | LLM 缓存命中率（`03/TestCaseGen.md` §8.3） | 长期为 0 是缺陷，而**失效不产生任何报错** |
| **先行** | Run 技术失败率（区别于测试失败） | 与 `03/TestExecutor.md` §7 的"系统失败 vs 测试失败"对应 |
| **滞后**（定期看） | M1 采纳率、M4 认可率、M8 成本 | 用于趋势与复盘，不需要实时反应 |
| **滞后** | M2 / M3 / M5 耗时类 | 波动是常态，看分位数趋势即可 |
| **滞后** | M6 覆盖率 | 由 CI 把关，不需要运行时监控 |

**为什么 M7 必须是告警而非统计**（`04` §9 已说明理由，此处强调其实现形态）：

它的目标值是 **0**，任何一次非零都是事故。而从报表里事后看到一个非零值——那时可能已经有生产数据被删了。**目标值为 0 的指标必须是实时的**，否则它的存在意义只剩"事后追认"。

### 5.4 三条"静默失效"的指标

上面三个先行指标有一个共同点值得单独指出：**它们失效时不产生任何报错**。

| 指标 | 失效时的表象 |
| :--- | :--- |
| 缓存命中率 | 一切正常，只是账单变贵（输入成本 ×10，`02` §5.4） |
| 规则覆盖率 | 一切正常，只是 LLM 调用变多 |
| M7 | 一切正常，直到数据被删 |

**这类指标如果不主动监控，就等于没有。** 它们不会自己浮出来——这与 HTTP 500、断连、超时那类"会自己叫"的故障有本质区别。

### 5.5 日志规范

**NF7：脱敏是全局输出过滤器，不是某个进程的职责。**

> **⚠️ 对 `02-架构设计.md` §2.2 的修正**：该处把"日志脱敏"列为 Gateway 的职责之一。但系统有三个进程（`06` §1.3），Worker 与 Orchestrator 的日志**不经过 Gateway**——若脱敏只在 Gateway 实现，这两个进程的日志就没有任何保护。
>
> 正确的划分：**脱敏是 `observability/logging.py` 的输出过滤器，三个进程共用**；Gateway 的"统一出口"作用体现在**对外响应体与 SSE 事件**的脱敏上。两者的对象不同，不应混为一谈。

日志的必含字段：

| 字段 | 用途 |
| :--- | :--- |
| `timestamp`（带时区） | `08` §4.3 的硬性约定 |
| `level` | |
| `component` | 进程与模块 |
| `trace_id` | 串起一次 Run 内的所有日志 |
| `run_id` / `node` | 有则填 |

**禁止写入**（`03/Guardrail.md` §10、`08` §4.3）：凭证、请求体与响应体正文、`target_url` 中 query 参数的值。

### 6.2 补充的安全需求

以下三项此前没有落点：

| 编号 | 需求 | 说明 |
| :--- | :--- | :--- |
| **NF4** | **上传大小上限 10 MB** | 无上限的上传会让解析进程内存耗尽。10 MB 远超正常 Spec（几十 KB 至数 MB），不会误伤合法用例 |
| **NF8** | **依赖漏洞扫描进 CI** | `pip-audit` 或等价工具。本项目的依赖包含 HTTP 客户端与序列化库，属于高风险面；扫描成本低而收益明确 |
| **NF9** | **凭证解密密钥不经由应用进程传递** | 密钥从环境变量注入（`01-PRD` SR-6 已定），需确保它不进入日志、不随进程信息泄露（`/proc`、异常堆栈） |

### 6.3 威胁模型中"不需要防"的部分

明确边界同样重要（避免过度设计）：

| 不防 | 理由 |
| :--- | :--- |
| 多用户越权 | MVP 单用户（PRD §3.3） |
| 平台自身的 XSS / CSRF | 前端由 Gateway 同源托管（`08` EN4），没有跨站场景；V1.0 分离时重新评估 |
| 被测服务对平台的攻击 | 平台只读取响应，不执行其内容（不解析 HTML、不执行脚本） |
| 目标 API 的凭证泄露给 LLM | Case 不含凭证（`04` §2.5），凭证仅在 Worker 执行时注入——**结构上不可能进入 Prompt** |

最后一条值得强调：**它不是靠"记得不要发"来保证的，而是靠数据模型保证的**——凭证根本不在会被序列化给 LLM 的对象里。

## 7. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **NF1** | 非功能数值是设计目标，非实测承诺 | 实现后必须校准并回写；未验证的目标被当成承诺会让后续决策建立在错误前提上 |
| **NF2** | 超限一律明确拒绝，不静默降级 | 静默降级会让用户以为全部测过了 |
| **NF3** | 监控 PG 体积，响应体大小分布为已采指标 | 典型与最坏场景差三个数量级；256 KB 的判断需要实测验证 |
| **NF4** | 上传大小上限 10 MB | 无上限会让解析进程 OOM |
| **NF5** | PostgreSQL 必须备份 | PG 是唯一事实来源；对 Redis 的容忍态度不应顺延到 PG |
| **NF6** | 区分先行指标与滞后统计 | 先行指标失效时**不产生任何报错**，不主动监控就等于没有 |
| **NF7** | 脱敏是全局日志过滤器 | 修正 `02` §2.2——Worker 与 Orchestrator 的日志不经过 Gateway |
| **NF8** | 依赖漏洞扫描进 CI | 成本低、收益明确 |
| **NF9** | 凭证密钥不经由应用进程传递 | 防 `/proc` 与异常堆栈泄露 |
