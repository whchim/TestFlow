## 1. 编排模型总览

### 1.1 为什么是状态机而不是链式调用

一个 Run 的生命周期包含**两次不确定长度的外部等待**：等人工确认、等测试执行完成。链式调用（`await` 到底）在这两处会让进程长期驻留内存，且无法抵御重启。

状态机的价值是把"等待"变成**可持久化的状态**，而非**占用的资源**。这也是 PRD F8（可中断可恢复）的实现基础。

### 1.2 执行模型：短跳推进

图**不是**一个长驻运行的过程，而是被事件反复唤醒、每次只前进到下一个中断点：

```
触发（启动 / 人工确认 / 执行完成）
   ↓
推进图：逐节点执行 → 直到命中 interrupt 或 END
   ↓
停止，进程释放
   ↓
（等待下一次触发）
```

因此**任何一次图推进都是短时的**，最长不超过单个节点内的 LLM 调用或分发耗时。这个性质决定了：

- Gateway 可以立即返回 `202`，不必等待图跑完
- 进程重启只会打断"当前这一跳"，下一次触发从 Checkpoint 继续
- 不存在"图跑了一半进程没了"导致的状态丢失

**⚠️ M1 实现回写——"短时"不代表"可以每次重建事件循环"：**

编排层的节点是异步的（`02` D1），而 Celery 的任务体是同步的，所以任务里需要一个"把协程跑起来"的动作。第一版用的是 `asyncio.run()`——**每个任务建一个新事件循环**。

**这是错的。** 编排层持有需要长期存在的异步资源：Redis 连接池、Checkpoint 的存储连接。**这些连接绑定在"创建它的那个循环"上**，换循环就会得到：

```
RuntimeError: Event loop is closed
```

而且它**只在第二个任务开始才出现**——第一个任务永远正常。

**正确做法是进程内跑一个长期存活的事件循环**（一个后台线程 + `run_coroutine_threadsafe`），所有任务都提交到它上面。代价是多一个线程；收益是图只编译一次、连接被复用、以及"连接绑错循环"这一类问题从根上消失。

> 这个坑在写测试时踩过一次（`asyncio.run` 反复建循环 vs 共享循环），当时改的是测试代码。**生产代码里有同样的问题而没有意识到**——只有真的把服务跑起来、连跑两次才暴露。这是"测试通过"与"实际工作"之间的一个典型缝隙。

编排层用 `--pool=solo --concurrency=1`，所以这个共享循环不需要额外的并发保护——per-Run 的串行由 §6.3 的锁保证。

### 1.3 进程拓扑

三个进程，两条队列（队列名示意，实际配置见 `10-部署运维.md`）：

```
┌─────────────┐  提交"推进"指令   ┌──────────────────┐
│   Gateway   │ ───────────────→ │  queue: orchestrate│
│  (FastAPI)  │                  └─────────┬────────┘
└─────────────┘                            ↓
       ↑                          ┌──────────────────┐
       │ 内部唤醒端点              │   Orchestrator   │  推进 LangGraph
       │ /internal/runs/{id}/wake  │  (消费 orchestrate)│  到下一个中断点
       │                          └─────────┬────────┘
       │                                    │ 分发 Case
       │                          ┌─────────┴────────┐
       │                          ↓                  │
┌──────┴──────┐  完成回调   ┌──────────────────┐    │
│  queue: exec │ ←───────── │  Celery Worker    │ ←──┘
└──────────────┘            │  经 Guardrail 出站 │
                            └──────────────────┘
```

**G1：编排层独立进程**。图推进不在 Gateway 进程内执行，而是投递到 `orchestrate` 队列由独立进程消费。理由：与 02 §1.1 的分层一致（Gateway 是薄层）；图推进与 HTTP 请求生命周期解耦，Gateway 重启不影响推进中的图。

**G2：复用 Celery 作为编排指令的传输**。不引入新组件，只是多一个队列名。代价是"Celery Worker 向 Celery 投递任务"这种看起来绕的结构——但两个队列的语义完全不同（编排指令 vs. 出站请求），混用同一队列会互相饿死。

## 2. 图状态（GraphState）

### 2.1 核心原则：存引用，不存大对象

State 会被序列化进 Redis Checkpoint。一个 Run 可能涉及 200 个 Operation、2000 个 Case，若把实体内容放进 State：

- Checkpoint 体积膨胀到 MB 级，每次节点转换都要全量读写
- 大对象（Spec 原文、响应体、日志正文）本就在 PostgreSQL，复制一份会产生**第二事实来源**

**G3：State 只存轻量引用与聚合值**。所有实体（Spec、Operation、Case 明细、执行结果、日志）只存 PG，State 中仅保留 ID 与计数。

### 2.2 状态结构

```python
class RunPhase(str, Enum):
    INIT = "init"
    PARSING = "parsing"
    GENERATING = "generating"
    AWAITING_REVIEW = "awaiting_review"  # IP-1 挂起态
    DISPATCHING = "dispatching"
    AWAITING_RESULTS = "awaiting_results"  # IP-2 挂起态
    ANALYZING = "analyzing"
    REPORTING = "reporting"
    DONE = "done"
    FAILED = "failed"


class RunPhase(StrEnum):
    INIT = "init"
    PARSING = "parsing"
    GENERATING = "generating"
    AWAITING_REVIEW = "awaiting_review"  # IP-1 挂起态
    DISPATCHING = "dispatching"
    AWAITING_RESULTS = "awaiting_results"  # IP-2 挂起态
    ANALYZING = "analyzing"
    REPORTING = "reporting"
    DONE = "done"
    FAILED = "failed"
    ABANDONED = "abandoned"  # IP-1 超时未处理（`04` §2.3 的 CHECK 约束里有它）


class GraphState(TypedDict, total=False):
    run_id: str
    phase: str

    # —— 引用（实体在 PG）——
    spec_id: str
    spec_fingerprint: str  # 用于 S2 场景的用例失效判定（上游 Q3）
    target_operation_ids: list[str]
    case_ids: list[str]
    approved_case_ids: list[str]  # HITL 通过、允许执行的
    attribution_ids: list[str]
    report_id: str | None

    # —— 聚合值（仅用于展示与快速判断，权威判定以 PG 为准）——
    generated_case_count: int  # N2 生成了多少条（不是"应当有结果多少条"）
    settled_case_count: int

    # —— 错误累积 ——
    node_failures: list[NodeFailure]
    retry_counts: dict[str, int]
```

**⚠️ M1 实现回写——本节的类型与初稿有三处不同：**

| 项 | 原稿 | 实现 | 理由 |
| :--- | :--- | :--- | :--- |
| 结构的基类 | `BaseModel` | **`TypedDict`** | 见下 |
| 字段类型 | `UUID` / `RunPhase` | **`str`** | 同上；`TypedDict` 不做强制转换，统一用字符串避免序列化时出现两种表示 |
| `updated_at` | 有 | **删掉** | 见下 |

**为什么改用 `TypedDict`：**

1. **Pydantic 状态每一步都要重新校验**——而这个状态的字段全是 ID 与计数（G3 明确要求"实体只在 PG 里"）。校验它们得不到任何保护，却要在每次状态合并时付一遍代价。
2. **中断载荷的序列化会更复杂**。`Command(resume=...)` 的载荷要经过 Checkpoint 的序列化器，混入 Pydantic 模型会让那条路径多出一层需要单独验证的转换。

字段与本节原稿**逐一对应，一个都没少**——改的只是表示形式。

**为什么删掉 `updated_at`：**

`runs.updated_at`（PG）才是权威——兜底轮询的扫描依据就是它（§6.4）。在 State 里再存一份，等于凭空多出一个需要同步的副本，而它唯一的作用是"展示"，代价却是每次节点转换都要序列化一次。

**⚠️ 所有字段都必须是可序列化的。** 状态会进 Checkpoint（Redis）。放一个数据库连接或 HTTP 客户端进去，要到第一次保存 Checkpoint 时才会报错——而那时图已经跑到一半了。

> **`phase` 的双重身份**：它既是给前端展示的状态，也是**条件路由的输入**。为降低二者不一致的风险，路由判断优先使用**显式字段**（如 `approved_case_ids` 是否为空），`phase` 只作为兜底与可观测性用途。理由见 G4。

**G4：不依赖 `phase` 做路由**。`phase` 是派生信息，若路由逻辑依赖它，任何一处忘记更新 `phase` 都会造成静默的错误跳转。条件边一律基于**业务字段**判断；`phase` 由图在各节点出口统一派生，仅供展示。

## 3. 节点定义

| 节点 | 职责 | 读 State | 写 State | LLM | 幂等键 |
| :--- | :--- | :--- | :--- | :--: | :--- |
| **N1** `parse_spec` | 解析 Spec，产出 Operation 清单 | `spec_id` | `target_operation_ids`、`spec_fingerprint` | ❌ | `spec_fingerprint`（同指纹重解析结果一致，直接复用） |
| **N2** `generate_cases` | 为每个目标 Operation 生成用例 | `target_operation_ids` | `case_ids`、`generated_case_count` | ✅ | `(run_id, operation_id)`，**已成功则跳过**，见 §5.3 |
| **IP-1** | 人工确认门 | — | —（等待外部输入） | — | — |
| **N3** `apply_decisions` | 落库人工决策，计算可执行集合 | `case_ids`、决策载荷 | `approved_case_ids` | ❌ | `(run_id, case_id)` |
| **N4** `dispatch_cases` | 组装并在投递前过滤，分发到 `exec` 队列 | `approved_case_ids` | `settled_case_count`（初始 0） | ❌ | `(run_id, case_id)` |
| **IP-2** | 等待执行结果 | — | — | — | — |
| **N5** `collect_results` | 校验结果完整性，判定部分失败 | —（分母查 PG，见 §6.2） | `settled_case_count`、`node_failures` | ❌ | 只读，天然幂等 |
| **N6** `analyze_failures` | 对失败 Case 归因（规则优先，LLM 兜底） | `case_ids` | `attribution_ids` | ✅（兜底） | `(run_id, case_id)` |
| **N7** `build_report` | 聚合指标，渲染报告 | `attribution_ids` | `report_id` | ❌ | `run_id` |

**与 02 §2.4 的对应与细化**：02 列出的五个 Agent 中，`TestExecutor` 在本文档拆为 **N4 `dispatch_cases`** 与 **N5 `collect_results`**（分发与汇集分离，因为它们被 IP-2 隔开）；另新增 **N3 `apply_decisions`**，用于承载 HITL 决策的落库与过滤。`SpecParser`/`TestCaseGen`/`LogAnalyzer`/`ReportAgent` 与 02 一一对应。

**破坏性用例的过滤位置**（对应 SR-3）：在 **N4 投递前**过滤，而非在 Worker 侧拦截。理由是"不投递"比"投递后拒绝"更安全——任务不进队列就不存在被误执行的可能；Worker 侧的 Guardrail 作为**第二道防线**保留。

**⚠️ M1 实现回写——N4 有一项文档没写的必要条件：**

> **N4 必须在投递之前 `commit` 数据库事务。**

N1~N4 运行在**同一个事务**里，而那个事务要到图跑完（`advance()` 返回）才提交。但 N4 一旦把任务投进队列，Worker 就是**另一个进程**——它会立刻按 `case_id` 去查库，而那时数据还没提交。

症状是**一部分任务报 `用例不存在`**，出现与否取决于 Worker 有没有抢在提交之前查到。

```
orchestrator：生成用例（在自己的事务里）→ 投递 → 挂起 → …… → 最后才提交
                                    ↑
                            Worker 已经捡到任务去查库了
```

**这条边界有确切的位置**：每当我们要把数据的引用交给另一个进程时，它必须已经持久化。

> 这个问题**集成测试发现不了**：那边投递和读取用的是同一个 Session，而未提交的数据对它自己是可见的。只有真的把编排器与 Worker 分成两个进程跑起来才会撞上。

## 4. 路由与条件边

主链：

```
START → N1 → N2 → IP-1 → N3 → N4 → IP-2 → N5 → N6 → N7 → END
```

**⚠️ M1 实现回写——M1 的图里没有 IP-1：**

```
START → N1 → N2 → [N3] → N4 → IP-2 → N5 → N6 → N7 → END
                  ↑
        N3 无条件批准全部待审用例
```

路线图明确 M1"含 IP-2，不含 IP-1"。**注意这不是"加了一个可以打开的自动批准开关"，而是"这个门此刻还不存在"**——一个根本不存在的东西，没有"被误设、被复制到生产、被临时关掉后遗忘"的问题。

M2 会把 IP-1 插进 `N2` 与 `N3` 之间。**届时 `N3` 的内容变成"读已落库的人工决策"，而下游一行都不用改**——路由依据一直是 `approved_case_ids` 是否为空，不是"有没有人审过"。

**这是一次图结构变更**：旧 Checkpoint 无法在新图上恢复。`10` §8 允许停机升级，所以 M1→M2 的升级是一次停机操作。

条件边（**全部基于业务字段，不基于 `phase`**，见 G4）：

| 位置 | 条件 | 去向 | 说明 |
| :--- | :--- | :--- | :--- |
| N1 出口 | `target_operation_ids` 为空 | END(`FAILED`) | Spec 无可用接口，硬失败并返回可定位原因 |
| N1 出口 | `node_failures` 含解析错误 | END(`FAILED`) | 非法 Spec 不进入后续流程 |
| N1 出口 | 否则 | N2 | |
| N2 出口 | `case_ids` 为空（重试后仍无有效用例） | END(`FAILED`) | 全量生成失败 |
| N2 出口 | 否则（**含部分成功**） | IP-1（M1：N3） | 部分 Operation 生成失败不阻塞全局，失败的记入 `node_failures` |
| N3 出口 | `approved_case_ids` 为空（用户全部丢弃） | END(`DONE`) | 正常终止，非错误；报告标注"无用例被执行"。**M1 走不到这条边**（N3 无条件批准），保留它是为 M2 的确认门预留 |
| N3 出口 | 否则 | N4 | |
| N5 出口 | 无失败 Case | N7 | 跳过归因，直接出报告。**M1 走不到这条边**——见下 |
| N5 出口 | 有失败 Case | N6 | |
| N6 出口 | 否则 | N7 | |

**⚠️ M1 实现回写——"N5 出口无失败则跳过归因"在 M1 无法判断：**

"有没有失败的用例"在 `case_results` 里，而结果**不在 State 中**（G3 要求实体只在 PG 里）。要让条件边知道它，就得在 N5 里把计数写回 State——那多了一个"两个事实来源"的问题。

M1 的做法是**一律走 N6**，而 N6 本身是空操作（归因属于 M3）。这个短路在 M1 看着没什么用（省一个空函数调用），但它是 M3 的前提——**归因要花 LLM 调用，而"零失败"的 Run 不该为此付钱**。到 M3 时再决定是补一个 State 字段，还是让 N6 自己短路。

**⚠️ M3 实现回写——选了"让 N6 自己短路"，图拓扑未变。**

N6 在读到 `case_results` 之后判断：过滤掉通过用例与补记超时
（`executor_stall`）后若为空，就直接返回，不构造 LLM 客户端、不写归因行。

选这条而不是"补 State 字段 + 改条件边"，是因为后者要在 N5 里多算一个计数
写回 State，而那个计数是**派生值**——G3/G4 的同一条理由：路由依据业务实体，
不依据缓存。N6 已经要读 `case_results` 了，顺带判空是零成本的。

**G5：MVP 图内无并行分支**。扇出（fan-out）全部下沉到 Celery（N4 一次投递 N 个任务）。因此 State 不需要 reducer——节点间是严格串行的。若 V1.0 引入图内并行（例如按 Operation 并行生成），再为 `case_ids` 等字段引入合并函数。**当前不引入，是因为它会让"部分失败"的路由判断复杂化，而收益（生成提速）在 MVP 规模下不明显。**

## 5. 中断与恢复

### 5.1 两个中断点

| | IP-1 人工确认 | IP-2 等待执行结果 |
| :--- | :--- | :--- |
| **挂起态** | `AWAITING_REVIEW` | `AWAITING_RESULTS` |
| **唤醒源** | 人在前端提交决策 | Celery Worker 完成回调 |
| **等待时长** | 分钟～天（用户可能离开） | 秒～分钟 |
| **超时行为** | 7 天后标记 `abandoned`，不执行（PRD §4.2） | 2× 单请求超时后强制推进，按部分失败处理（§6.4） |
| **谁触发恢复** | Gateway（收到人工决策） | Gateway 的内部唤醒端点 |

### 5.2 为什么两者用同一套机制

**G6：两个中断点统一使用 LangGraph 的 interrupt 机制**，不混用"节点内轮询等待"。

| 方案 | 问题 |
| :--- | :--- |
| 节点内 `while` 轮询等待结果 | 进程被占用；重启即丢失；IP-1 场景下甚至可能等几天——完全不可接受 |
| IP-1 用 interrupt，IP-2 用轮询 | 两套恢复语义，两套错误处理，Checkpoint 的语义边界模糊 |
| **两点都用 interrupt（选定）** | 恢复路径唯一：都是"从 Checkpoint 恢复 + 传入载荷"。IP-1 的载荷是人工决策，IP-2 的载荷是"结果已就绪"的信号 |

> **实现提示**：LangGraph 的中断/恢复 API 在不同版本间有过演进（`interrupt_before` 与节点内 `interrupt()` 并存）。本文档只约定**语义**（挂起在 Checkpoint、由外部载荷唤醒）；具体调用形式须以项目锁定的 LangGraph 版本为准，落地时在 `03/` 或代码注释中记录。**不要在实现时凭记忆写 API。**

### 5.3 恢复语义与幂等要求

恢复意味着**从 Checkpoint 之后重新执行**。因此每个节点都必须满足：

1. **可重入**：节点可能被执行多次（恢复、重试、人工重跑），结果必须一致
2. **不假设"只执行一次"**：不要用"首次执行"这类隐式前提做业务判断
3. **写操作幂等**：一律按 §3 表格中的幂等键 upsert，不依赖自增 ID 或时间戳去重

**⚠️ M1 实现回写——恢复的粒度是"节点"，不是"节点内的某一行"：**

实测确认（`langgraph` 1.2.15）：**中断的节点在恢复时会从头重跑整个函数体**，而不是从 `interrupt()` 调用处继续。

```
执行轨迹: ['a', 'wait', 'wait', 'b']
                          ↑
                    "wait" 出现了两次
```

这条对图的结构有直接影响：

> **`interrupt()` 必须独占一个节点。** 若把它写在别的节点中间，那个节点的前半段会在每次恢复时重跑一遍——而"投递 12 条用例"这类动作重跑一次就是给目标服务凭空多打一轮请求。

所以 M1 的 `wait_for_results` 整个函数体只有三件事：写 `phase`、`interrupt()`、返回。

> **⚠️ 例外：N2 的幂等语义是"跳过"而非"重放"。** LLM 输出**非确定性**——重跑同一 Operation 会得到不同用例。若恢复时重新生成，用户已经确认过的用例会被静默替换，这比直接报错严重。因此 N2 必须持久化"该 Operation 是否已生成成功"，已成功则跳过。§3 表格中 N2 的幂等键用于**判定是否已完成**，不用于判定"结果是否相同"。持久化位置见 `04-数据模型.md` 的 `run_operations` 表与 DM4。

**最关键的幂等点**：N4 `dispatch_cases` 在恢复时必须**跳过已有终态结果的 Case**。否则 IP-2 恢复失败一次，就会把已执行的用例重跑一遍——对被测环境是二次污染（对应 PRD R3）。

## 6. 回调唤醒机制（解答上游 Q1）

### 6.1 唤醒路径

**G7：Worker 完成后调用 Gateway 的内部端点**，不用 Redis 事件。

```
每个 Case 执行完成
   ↓
Worker 写结果到 PG（幂等键 run_id + case_id）   ← 先落库，见 02 D4
   ↓
Worker 调用 POST /internal/runs/{run_id}/wake
   ↓
Gateway：快速判定所有 Case 是否已到终态
   ├─ 否 → 直接返回 200，不做任何事
   └─ 是 → 投递"推进"指令到 orchestrate 队列，返回 202
   ↓
Orchestrator：持锁 → 从 Checkpoint 恢复 → 图推进到下一个中断点
```

选 HTTP 端点而非 Redis 发布订阅的理由：

| 考量 | HTTP 内部端点 | Redis pub/sub |
| :--- | :--- | :--- |
| 失败可见性 | 有状态码，Worker 可重试 | fire-and-forget，静默丢失 |
| 需要新进程/端口 | 否（复用 Gateway，仅内网） | 否 |
| 需要消费者循环 | 否 | 是（Orchestrator 需常驻订阅） |
| 调试 | 可以直接 curl 复现 | 需要订阅工具 |

> **与 02 §1.2 的关系**：02 中标记为 V1.0 的 "Callback API" 指的是**面向外部系统的回调能力**（跨机部署时需要公网可达）。本文档的 `/internal/runs/{id}/wake` 是**系统内部的 IPC**，与外部回调是两件事，不构成对 02 分期结论的修改。

该端点必须：仅监听内网、要求内部 token（SR-6）、**幂等**。

**⚠️ M2 实现回写——上图的"先落库"指的是 `commit`，不是 `flush`：**

流程图里"Worker 写结果到 PG（先落库，见 02 D4）"这一步，在**跨进程**的意义上
只能是 `commit`。M1 的实现把它做成了 `flush`：

```
run_case 内部 flush（结果只对本事务可见）
  → 调唤醒端点
    → Gateway 用**自己的**会话查 case_results → 数不到这一条
      → 判定"还没到齐" → pending
```

于是**每一次回调都被判成"还没到齐"**，唤醒路径彻底失效（与 §6.2 那个分母
缺陷是**两个独立原因**，修掉任意一个，观察到的现象不会有任何变化——
"改了一处却毫无变化"很容易让人得出"改了也没用"的错误结论）。

由此得出两条硬约束：

1. **唤醒必须由持有事务边界的调用方发出**，且在 `commit()` 之后。
   `run_case` 只 flush、不 commit（它不认识事务边界），所以它**不该**负责唤醒。
2. **唤醒失败必须吞掉，只记日志**。M1 里它往上冒，于是 Gateway 一次抖动会让
   Celery 任务失败；而 `acks_late=True` 下任务失败会被**重投**，意味着
   **把这个用例再执行一遍——对被测系统多打一次请求**。
   "通知发不出去"本来是不影响正确性的问题（结果已落库，兜底轮询会补上），
   却被放大成了"对用户系统多一份流量"。**代价的方向反了：通知可以丢，事实不能重复。**

这条缺陷躲过测试的原因值得单独记一笔：第一版有一条测试断言"回调触发时结果
已经可查"，而它用的是**同一个会话**——`flush` 之后当然查得到。
**它验的是"同一会话可见性"，而需求是"跨进程可见性"。** 正确的判据是
"回调触发时事务已经结束"（`session.in_transaction()` 为 `False`）。

### 6.2 完成判定（barrier）

**G8：完成判定由 Gateway 查询 PG，不由"最后一个"任务触发。**

朴素做法是让最后完成的 Case 触发唤醒——但它有竞态：两个任务可能同时认为自己"是最后一个"（或都不认为）。因此：

- 每个 Case 完成后**都**调用唤醒端点（幂等，重复无害）
- 端点自行查询：`SELECT count(*) FROM case_results WHERE run_id=?`，与**应当有结果的用例数**比较
- 只有判定为"全部到终态"时才投递推进指令

这样，无论回调丢失、重复还是乱序，只要**最终有一次**到达且 PG 状态已完整，图就会被正确唤醒。代价是 N 次多余的 HTTP 调用（N = Case 数），可通过"每完成 K 个或每 T 秒聚合一次"优化——但**先做对，再做快**。

**⚠️ M2 实现回写——分母必须是"应当有结果的用例数"，且两个数都要查 PG：**

原文写的是"与 `expected_case_count` 比较"，那**正是缺陷本身**。两处要改：

**① 分母不是"生成了多少条"，而是"应当有结果多少条"。** N4 只投递
`review_status = 'approved'` 且非破坏性的用例，其余（被拒绝的、破坏性的）
**永远不会**有结果。用生成条数当分母，`settled < expected` 就**永远成立**：
每一次运行都会记下一条 `partial_results` 失败，并去补记缺失的那些为 timeout。

**② 分子分母都不能读 `runs.expected_case_count` / `settled_case_count`。**
它们是**派生缓存**（`04` DM5），而 DM5 把话说得很直白："任何正确性判断
**一律以 `SELECT count(*)` 查询 `case_results` 为准**"。M1 在这里违反了它，
后果是**回调唤醒整条路径从来没有生效过**：

```
该缓存没有任何节点维护 → 恒为 0
  → 判定 expected == 0 → 永远返回 pending
    → 每条用例完成时的唤醒全部空转
      → Run 只能靠 §6.4 的兜底轮询往前挪（每分钟一次）
```

**这个缺陷的表现是"慢"，不是"错"**——Run 最终仍然会完成，只是每次唤醒都
白跑一趟。没有测试会因为"慢了 60 秒"变红，而一个正常工作的系统看起来
就是这样：有点慢，但能跑完。M2 实测：修之前一次端到端 **62.9 秒**，
修之后 **3.2 秒**，而中间没有任何行为差异可供断言。

配套：两个派生缓存仍需在节点出口维护（N4 写 `expected`，N5 写 `settled`），
但那是**给前端与 CLI 看的**，不参与这里任何判断。M1 里它们从未被写过，
于是 `GET /api/runs/{id}` 一直返回 `0/0` —— 而"缓存没人维护"与"有人拿缓存
做判断"这两件事叠在一起，才构成了上面那个功能性失效。**两个各自看起来
无害的决定，合起来是一次静默的失效**。

### 6.3 并发保护

**G9：同一个 Run 的图推进必须串行化。**

可能同时出现多个唤醒源：用户提交决策、Worker 回调、兜底轮询——它们可能并发地投递推进指令。若两次推进并发执行同一 Run：

- 两个进程同时从 Checkpoint 恢复 → 状态竞争
- 都执行 N4 → Case 被双重投递

解决：**per-Run 分布式锁**（Redis `SET run_id NX EX <ttl>`）。Orchestrator 消费到推进指令时先抢锁，抢不到则直接丢弃——因为"已经有人在推进它"等价于"这次唤醒是多余的"。

> 锁必须设 TTL 且**不自动续期**：若持锁进程崩溃，TTL 到期后下一次唤醒仍能接管。宁可偶发重复推进（幂等保证安全），不可永久死锁。

### 6.4 兜底轮询

回调可能全丢（Gateway 重启期间 Worker 集中完成）。因此需要一个**周期性扫描**：查询所有 `phase = AWAITING_RESULTS` 且 `updated_at` 超过 `2 × 单请求超时` 的 Run，重新走一次 §6.2 的完成判定。

- 若已全部到终态 → 正常推进
- 若仍有 Case 未到终态 → 标记这些 Case 为 `TIMEOUT`，**按部分失败推进**（不无限等待）
- 部分失败的处理与正常失败一致：进入 N5 → N6 → N7，报告中显式标注"部分用例未完成"

**这个扫描是幂等的**，与正常唤醒路径不冲突（有 §6.3 的锁保护）。

**⚠️ M1 实现回写——扫描能扫到，前提是挂起前把 `phase` 写对：**

扫描条件是 `phase = AWAITING_RESULTS`。而 `phase` 是由**节点自己写进 `runs` 表**的（G4 说它只用于展示，但轮询用的正是它）。

于是有一个必须显式处理的顺序问题：

```
IP-2 挂起之前，必须先把 runs.phase 写成 awaiting_results
```

少了这一步，`phase` 会停在上一步 N4 写的 `dispatching`——**而轮询扫的是 `awaiting_results`，于是它永远扫不到这个 Run。**

**这道安全网会彻底失效，且没有任何提示**：症状是"回调丢了的 Run 永远转圈"，而日志里一切正常。M1 的实现里这条是实测撞出来的（集成测试断言"挂在 IP-2"时发现 `phase` 还是 `dispatching`）。

这个写入发生在 `interrupt()` **之前**，所以节点在恢复重跑时会再写一次。无害——写的是同一个值，而"中断的节点从头重跑"是必然语义（见 §5.3）。

**⚠️ M1 实现回写——补记超时时必须排除破坏性用例：**

N4 会主动跳过破坏性用例（TE3：MVP 不执行、也没有授权入口），于是它们**永远不会有结果**。补记逻辑若不排除它们，就会把它们标成 `timeout`——**而那是在说"我们发了请求但没等到回应"，与事实（我们故意没发）相反**。

后果不只是报告失真：一份"12 条超时"的报告会让用户去查目标服务为什么慢，而真相是那些用例按设计就不该被执行。

判据是 `cases.is_destructive = false`。

**⚠️ M2 实现回写——同一条规则必须扩展到"被人工拒绝"的用例：**

IP-1 落地之后，"永远不会有结果"的用例多了一类：用户在确认界面上**拒绝**
（`review_status = 'rejected'`）的那些。N4 只投递 `approved` 的。

理由与上一条**逐字相同**——而且这次连"后果"都一模一样：补记成 `timeout`
等于在报告里写下"我们发了请求但没等到回应"，与事实（**用户看过并决定不跑**）
相反。后果有三层，一层比一层难发现：

1. 报告把"用户主动跳过"说成"目标接口超时"——**一个凭空捏造的系统故障结论**，
   用户会照着它去查一个不存在的问题
2. 它进了通过率的分母（`03/ReportAgent.md` RA3 要求分母**只含已执行**用例），
   真实的失败率被稀释
3. RA2 要求报告显式列出"没测什么"，而它转而出现在**失败清单**里

这个洞在 M1 是不可能触发的（那时没有拒绝入口，`review_status` 恒为
`approved`）——它是 **IP-1 落地之后才变得可达的**。判据因此从
`is_destructive = false` 变成一条更完整的口径：

```
review_status = 'approved' AND is_destructive = false
```

**这个口径必须与 N4 的投递条件逐条对齐**（见 §6.2 的"应当有结果的用例数"）——
两处不一致时，一边多算一边少算，完成判定就永远差那么几条。

## 7. 错误处理与重试

| 错误类型 | 出现位置 | 处理 | 是否影响 Run |
| :--- | :--- | :--- | :--- |
| Spec 解析失败 | N1 | **硬失败**，终止 Run，返回可定位错误 | 终止 |
| LLM 调用失败 | N2 / N6 | 指数退避重试最多 2 次（PRD §4.3 L1）；仍失败则该 Operation / Case 记入 `node_failures` | 不终止（部分失败） |
| 结构化输出校验失败 | N2 / N6 | 带校验错误信息重试，计入上述 2 次上限 | 不终止 |
| 投递失败（队列不可用） | N4 | 节点级重试；恢复时按幂等键跳过已投递的 Case | 不终止 |
| Case 执行超时 | Worker | 记为 `TIMEOUT` 终态，属**测试结果**而非系统错误 | 不终止 |
| Worker 崩溃 | Worker | Celery `acks_late` 重投；幂等键保证不重复落库 | 不终止 |
| 节点未知异常 | 任意 | LangGraph 节点级重试策略；超限后终止 Run 并置 `FAILED` | 终止 |

**区分两类失败**（贯穿本表的原则）：

- **系统失败** → 记入 `node_failures`，可能终止 Run，需人工介入
- **测试失败** → 是产品输出，进入归因与报告流程，**永不终止 Run**

把 HTTP 500 当成系统错误去重试或告警，是这个系统最容易犯的语义错误。

## 8. 编排设计决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **G1** | 编排层独立进程 | 图推进投递到 `orchestrate` 队列，不在 Gateway 进程内执行 |
| **G2** | 复用 Celery 作编排传输 | 多一个队列名，不引入新组件；编排队列与执行队列必须分开 |
| **G3** | State 存引用不存大对象 | Checkpoint 保持轻量；实体只在 PG，避免第二事实来源 |
| **G4** | 路由不依赖 `phase` | `phase` 是派生值，路由一律基于业务字段，防止静默错误跳转 |
| **G5** | MVP 图内无并行 | 扇出下沉到 Celery，State 不需要 reducer |
| **G6** | 两个中断点统一用 interrupt | 恢复路径唯一；禁止节点内轮询等待 |
| **G7** | 唤醒走内部 HTTP 端点 | 有失败可见性，可重试可调试 |
| **G8** | 完成判定查 PG，不由"最后一个"触发 | 消除竞态；唤醒幂等 |
| **G9** | per-Run 分布式锁 | 同一 Run 的推进串行化；锁设 TTL 不续期 |
