## 1. 部署形态

**单机 Docker Compose**（PRD §5 部署基线）。不引入 Kubernetes。

理由：MVP 是单用户自用工具（PRD §1.2 的场景 S1），**K8s 的编排能力在这里没有消费方**——没有多租户、没有弹性伸缩需求、没有多环境编排。引入它只会增加运维负担与故障面。

`07` §3.3 已说明架构**不阻止**横向扩展，但那是 V1.0 之后的事。

## 2. 服务清单

### 2.1 四个长驻应用服务 + 按需 CLI + 两个基础设施

```
┌─────────────────────────────────────────────────┐
│  同一个镜像，不同入口点（08 EN1）                 │
│  ┌──────────┐ ┌──────────────┐ ┌─────────────┐  │
│  │ gateway  │ │ orchestrator │ │   worker    │  │
│  └──────────┘ └──────────────┘ └─────────────┘  │
│  ┌──────────┐                                   │
│  │   beat   │                                   │
│  └──────────┘                                   │
└─────────────────────────────────────────────────┘
┌──────────────┐  ┌──────────────┐
│ postgres     │  │   redis      │
└──────────────┘  └──────────────┘
```

> **⚠️ 对 `08-工程规范.md` EN1 的补充**：该处写的是"一个镜像，四个服务"。**漏了一个**——定时任务需要一个调度器（§7）。准确表述是：**一个镜像、四个入口点（gateway / orchestrator / worker / cli）；Compose 中跑四个长驻应用服务（gateway / orchestrator / worker / beat），CLI 不进长驻服务**。见 `08` v0.2。

| 服务 | 入口点 | 说明 |
| :--- | :--- | :--- |
| `gateway` | `testflow-gateway` | 唯一对外暴露端口的服务 |
| `orchestrator` | `testflow-orchestrator` | 消费 `orchestrate` 队列 |
| `worker` | `testflow-worker` | 消费 `exec` 队列；可 `--scale` |
| `beat` | Celery Beat | 只投递定时任务，不执行（§7） |
| `cli` | `testflow` | **非长驻**，按需 `docker compose run --rm cli ...` |
| `postgres` | — | |
| `redis` | — | |

### 2.2 为什么 `worker` 可扩展而 `orchestrator` 不必

`worker` 执行无状态的 HTTP 请求，加副本直接提升吞吐——**但受 Guardrail 限流约束**（`03/Guardrail.md` GR9），加副本前需先调整阈值。

`orchestrator` 的并发受 per-Run 分布式锁限制（`06` G9）：同一 Run 的推进必须串行。单副本足够——图推进是短跳操作（`06` §1.2），不是持续负载。

## 3. 配置项

### 3.1 两类配置必须分开

**OP1：安全底线不做成配置项。**

这是一个刻意的约束。若「是否拒绝云元数据地址」是一个可配置开关，那么**留存在配置里的那个开关本身就是漏洞**——它会被误设、被复制到生产、被"临时"关掉后忘记打开。

| 类别 | 处理 |
| :--- | :--- |
| **安全底线** | **硬编码，不可配置**。无从关闭 |
| **可调参数** | 配置项，带默认值与说明 |

### 3.2 不可配置的安全底线

| 行为 | 依据 |
| :--- | :--- |
| 云元数据地址一律拒绝（含配置了内网例外时） | `03/Guardrail.md` GR4 / §4.5 |
| 不跟随重定向 | `03/Guardrail.md` GR5 / §6 |
| 破坏性方法（DELETE / PUT / PATCH）未被授权时拒绝 | `03/Guardrail.md` §5 |
| 白名单为 `scheme + host + port` 精确匹配，不通配、不继承子域 | `03/Guardrail.md` GR3 |
| 校验作用于解析后的 IP 并钉死连接目标 | `03/Guardrail.md` GR1 / GR2 |
| 日志不写入凭证与请求/响应正文 | `07` §5.5 / `08` §4.3 |

**这些不是"默认值"，是没有开关的行为。** 实现时它们不应出现在 `Settings` 里。

### 3.4 关于 `guardrail_qps_per_host` 默认值的推导

`03/Guardrail.md` GR9 说"限流阈值必须低于 Worker 并发度能产生的 QPS，否则限流形同虚设"。这句话需要精确化——**它描述的是节流场景，而本项目的默认场景不是节流**。

区分两种用途：

| 用途 | 手段 |
| :--- | :--- |
| **保护目标服务**（常规） | `worker_concurrency` 本身——它天然限制了在途请求数 |
| **防止异常放大**（兜底） | QPS 上限——应对重试风暴、并发配置错误等情况 |

因此默认值应设在**略高于正常并发产生的吞吐**处，使其只在异常时生效，而不是持续压制自己：

```
正常吞吐 ≈ worker_concurrency / 平均请求耗时
        ≈ 8 / 0.5s ≈ 16 QPS
默认上限 = 20 QPS   （留出余量，仅在异常时触发）
```

> **默认值需要实测校准**（`07` NF1）：0.5s 是按常规 API 估的。目标 API 响应很慢时，正常吞吐会低得多，20 QPS 的兜底就失去了意义；响应极快时则可能误触发。**这两个参数必须在同一个配置块里联合调整**，不能分散配置（GR9 的本意）。

## 4. 网络与端口

**OP2：所有端口绑定必须显式限定到 `127.0.0.1`，绝不出现 `0.0.0.0`。**

| 服务 | 宿主机端口 | 说明 |
| :--- | :--- | :--- |
| `gateway` | `127.0.0.1:3000:3000` | 绑定环回（`05` §2.1） |
| `postgres` | `127.0.0.1:5432:5432` | 绑定环回。**M0 细化**，见下 |
| `redis` | `127.0.0.1:6379:6379` | 同上 |
| `orchestrator` / `worker` / `beat` | 无 | 不监听端口 |
| 内部端点 `/internal/*` | 不经宿主机 | 仅容器网络可达（`05` §5.3） |

**M0 对 OP2 的细化（原表述为 PG/Redis「不发布」）**

原文要求 PostgreSQL 与 Redis 完全不发布端口，理由是防 `0.0.0.0` 把这两个服务暴露出去——它们存着**全部用例、结果、审计日志与加密凭证**。

M0 改为绑定 `127.0.0.1` 发布，理由有两条，第二条是决定性的：

1. **风险面不同**。`127.0.0.1:5432:5432` 只有本机能连，局域网连不上——OP2 要防的局域网暴露并不存在。而它换来的是开发期的实际便利：`alembic`、`psql`、集成测试都可以直接在宿主机上跑，不必每次 `docker compose exec`。
2. **CI 要求宿主机可达**。`./scripts/ci.sh` 第 ④ 步的 `alembic check` 在宿主机执行，它必须连上 PG 才能比对模型与迁移。若 PG 完全不发布端口，这一步无法运行。

**仍然禁止的**（这条是硬线，没有例外）：任何形如 `0.0.0.0:5432:5432` 或裸 `5432:5432`（等价于 `0.0.0.0`）的写法。多机部署时 PG/Redis 必须走容器网络或私有网络，不得靠端口映射。

> **残余风险**：同机上的其他用户/进程可以连到 `127.0.0.1:5432`。开发库的凭据是弱口令（`testflow/testflow`），因此**本机若不可信，这条就不成立**。生产部署的凭据必须另行注入，不得沿用 compose 中的开发默认值。

## 5. 启动顺序与健康检查

```yaml
postgres / redis          → healthcheck 就绪
        ↓
gateway                   → 依赖上述就绪；启动期校验配置（§3.3）
        ↓
orchestrator / worker / beat
```

| 依赖 | 说明 |
| :--- | :--- |
| 应用服务依赖 PG 与 Redis 就绪 | 用 `depends_on: condition: service_healthy` |
| `gateway` **不自建表** | schema 由 Alembic migration 管理（`EN7`），不在应用启动时自动建表 |

**为什么不在启动时自动建表**（例如 `create_all`）：那会让 schema 的变更绕过 migration，`04` 与 `10` 中的 schema 描述与真实库结构逐渐分叉，而**没有任何机制会察觉**。migration 是唯一路径。

**启动期配置校验**（`08` §3）：非法配置应在启动时失败，而非运行时。例如绑定了非环回地址却没配 `api_token` → 拒绝启动。

## 6. 数据持久化与备份

### 6.1 卷

| 卷 | 内容 | 丢失后果 |
| :--- | :--- | :--- |
| `pgdata` | 全部持久数据 | **不可恢复**（`07` NF5） |
| `redisdata` | Checkpoint、Broker | 可接受——未完成的 Run 标记失败后可从 PG 重跑（`02` §7） |

Redis 卷可以不做持久化配置。这不是疏忽，是**刻意不为可丢失的数据付出持久化成本**。

### 6.2 备份（`07` NF5 的落点）

**OP3：`pg_dump` 定时备份 + 定期恢复验证。**

| 项 | 方案 |
| :--- | :--- |
| 频率 | 每日一次 |
| 保留 | 日备 7 份 + 周备 4 份 |
| 位置 | 挂载卷（**宿主机之外的介质更佳**） |
| 验证 | **定期做一次恢复演练** |

**OP4：备份必须验证可恢复。**

只备份不验证，在需要恢复的那天才知道备份是坏的——而这个项目的场景恰好是"PG 全丢"，那时没有第二次机会。最低限度是定期 `pg_restore --list` 校验完整性；更可靠的是恢复到临时库并做一次查询。

代价很低，收益是"备份到底能不能用"这个问题的答案从"希望可以"变成"确认可以"。

## 7. 定时任务（`beat` 服务）

`06` 定义了三类需要周期性执行的工作，这也是 `08` EN1 漏掉 `beat` 的原因——它们分散在三份文档里，没有一处汇总过：

| 任务 | 频率 | 依据 | 做什么 |
| :--- | :--- | :--- | :--- |
| **兜底轮询** | 每 1 分钟 | `06` §6.4 | 扫描 `AWAITING_RESULTS` 超时的 Run，标记未完成用例并按其推进 |
| **IP-1 超时标记** | 每小时 | `06` §5.1 | `AWAITING_REVIEW` 超 7 天的 Run 标记 `abandoned`，不执行 |
| **数据清理** | 每日 | `04` §5 | 删除超过 90 天的 Run（级联）与孤儿 Spec |

**三个任务都必须幂等且可重入**（`04` §5、`06` §5.3 的同一要求）：它们可能因进程重启而被重复触发，重复执行不应产生副作用。

`beat` 只负责**投递**，不执行任务内容——否则调度与执行耦合，`beat` 重启就会中断正在跑的任务。

## 8. 升级与回滚

MVP 是单机自用，**允许停机升级**。

```
① 备份 PG                        ← 不可跳过
② 停止应用服务（保留 postgres）
③ 执行 migration（alembic upgrade head）
④ 启动新版本应用
⑤ 健康检查（/readyz）
⑥ 失败 → 回滚：alembic downgrade + 镜像回滚 + 必要时 restore 备份
```

**OP5：每个 migration 必须实现 `downgrade`。**

Alembic 生成 migration 时 `downgrade` 常是空的（尤其自动生成时）。若不补上，第 ⑥ 步的回滚就无法执行——**升级变成了一条单行道**。

注意 `08` §7 已说明：`04` v0.2~v0.5 累积的 4 个字段属于**首个** migration 的内容，不是增量迁移。

## 9. 资源估算

| 服务 | 内存 | 说明 |
| :--- | :--- | :--- |
| `postgres` | 512 MB | 受 `07` §3.2 的容量估算约束 |
| `redis` | 256 MB | Checkpoint 与队列，数据量小 |
| `gateway` | 256 MB | 薄层 |
| `orchestrator` | 512 MB | 持有 GraphState，但只存引用（`06` G3） |
| `worker` | 512 MB × 副本数 | 需容纳 256 KB 的响应体（`04` DM6） |
| `beat` | 128 MB | 只投递任务 |

**`orchestrator` 的内存之所以可控，直接来自 G3**（State 只存引用不存大对象）。若状态里塞了 2000 条用例的完整内容，这个数字要翻一个量级。

**磁盘**：主要变量是 PG，见 `07` §3.2。

## 10. 关闭的开放问题

| 来源 | 问题 | 结论 |
| :--- | :--- | :--- |
| `03/Guardrail.md` Q1 | QPS 上限与熔断阈值 | §3.4：默认 20 QPS，**作为异常兜底而非常规节流**；与 `worker_concurrency` 联合调整 |
| `05-API契约.md` Q2 | `Idempotency-Key` 的存储 | Redis，key 为 `idem:{sha256(key)}` → `run_id`，TTL 24 小时。**不新建 PG 表**——它是短期去重，不是业务事实 |
| `07-非功能需求.md` Q1 | 指标的暴露方式 | MVP 仅结构化日志；**不引入 Prometheus**（那是一个额外服务，单机自用没有消费方）。M7 的告警形态见下 |
| `07-非功能需求.md` Q2 | PG 备份方案 | §6.2 / §6.3 |

### 10.1 M7 的告警形态

`07` §5.3 要求 M7（破坏性用例误执行）**必须实时告警**，因为它目标值为 0。但单机自用场景下没有告警通道（没有 PagerDuty、没有值班群）。

MVP 的做法：

| 层 | 实现 |
| :--- | :--- |
| 日志 | 以 `ERROR` 级别输出，含完整的请求上下文 |
| 界面 | **下次打开界面时显示醒目横幅**，且在 Run 详情中永久标注 |
| 审计 | `audit_logs` 中记为 `allow` + `destructive` |

**"下次打开时横幅提示"在单机场景下是可接受的**：用户与操作在同一台机器上，不存在"人不在现场"的延迟。V1.0 若引入多用户或常驻部署，需要换成真正的推送告警。

这一点必须记录清楚，因为它是**一个明知不完美的方案**——目标值为 0 的指标配一个"下次打开才看到"的告警，只有在单机自用的前提下才成立。

## 11. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **OP1** | 安全底线不做成配置项 | 可关闭的安全开关本身就是漏洞：会被误设、被复制、被"临时"关掉后遗忘 |
| **OP2** | 所有端口只绑 `127.0.0.1`，绝不出现 `0.0.0.0` | M0 细化：PG/Redis 允许发布到环回（CI 需宿主机可达），硬线是绑定地址 |
| **OP3** | `pg_dump` 定时备份 | PG 是唯一事实来源（`07` NF5） |
| **OP4** | 备份必须验证可恢复 | 只备份不验证，要恢复的那天才知道备份是坏的 |
| **OP5** | 每个 migration 必须实现 `downgrade` | 否则升级是单行道 |
| **OP6** | 启动时不自动建表 | 绕过 migration 会让 schema 与文档静默分叉 |
| **OP7** | Redis 卷不做持久化 | 不为可丢失的数据付出持久化成本 |
| **OP8** | 不引入 Prometheus（MVP） | 单机自用没有消费方；M7 的告警用日志 + 界面横幅 |
| **OP9** | `beat` 只投递不执行 | 调度与执行耦合会让 beat 重启中断正在跑的任务 |
