# ADR-0010：幂等由数据库唯一约束保证

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `04-数据模型.md` DM1 |
| 相关文档 | `04-数据模型.md` §2.6、`03/TestExecutor.md` §7 |

## 背景

系统中"重试"不是例外，而是常态：

| 场景 | 机制 |
| :--- | :--- |
| Worker 崩溃 | Celery `acks_late` 重投任务 |
| IP-2 恢复 | 从 Checkpoint 后重放节点 |
| 并发 | 多个 Worker 可能同时处理同一 Run |

因此**关键写操作必须幂等**：同一逻辑操作执行多次，结果与执行一次相同。

最典型的场景是 `case_results`（执行结果）：`(run_id, case_id)` 组合应当只有一条记录。

## 决策

**在数据库层面声明唯一约束，写操作使用 `INSERT ... ON CONFLICT DO UPDATE`。**

```sql
INSERT INTO case_results (run_id, case_id, ...)
VALUES (...)
ON CONFLICT (run_id, case_id) DO UPDATE SET ...
```

即：`case_results` 上设 `UNIQUE (run_id, case_id)`。

## 被否决的备选

### 备选一：应用层判断（`SELECT` 后 `INSERT`）

```python
if not exists(run_id, case_id):
    insert(...)
```

**否决理由：竞态。**

两个进程可能**同时**执行到 `exists` 判断，都得到"不存在"，然后**都执行插入**。

**关键在于：这段代码在绝大多数情况下是正确的。** 竞争窗口极窄，只有在精确的时序下才会触发——因此无法通过常规测试发现，且线上表现为"偶发重复数据"。

> **通用规律**：任何"先检查、再根据检查结果行动"的两步模式，在并发下都不可靠。

### 备选二：用应用层分布式锁串行化

在写之前获取 `(run_id, case_id)` 粒度的锁。

**否决理由：**

- 引入一个**新的故障点**（锁服务不可用则写不进去）
- 每个用例多两次 Redis 往返
- **数据库本身已经提供了这个能力**，无需在应用层重新实现一遍

### 备选三：依赖"不重试"来避免重复

**否决理由：**

不可能做到。崩溃重投、IP-2 恢复重放都是**设计要求的**行为（`06` §5.3），不是可以取消的。

## 后果

**正面：**

- 幂等性由数据库的原子保证提供，**不受并发与时序影响**
- 应用代码无需关心"是否已存在"
- 与 ADR-0009 一致——数据库是事实的最终裁决者

**代价：**

- 并发写同一 `(run_id, case_id)` 时，后者覆盖前者。由于同一用例不应被并发执行，这是可接受的
- 需要为冲突路径设计 `DO UPDATE` 的行为（例如 `attempt` 计数递增）

**适用范围：**

本决策适用于所有"同一逻辑键只能有一条记录"的场景。具体到本项目：

| 表 | 唯一约束 |
| :--- | :--- |
| `case_results` | `UNIQUE (run_id, case_id)` |
| `attributions` | `UNIQUE (run_id, case_id)` |
| `reports` | `UNIQUE (run_id)` |

**不适用**：`cases` 表。它是**生成**的产物而非**重放**的产物，其幂等语义不同——见 ADR-0011。
