# ADR-0002：Guardrail 作为唯一出站通道

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `02-架构设计.md` D2、`03/Guardrail.md` GR7、`08-工程规范.md` EN2 |
| 相关文档 | `03/Guardrail.md` 全篇、`07-非功能需求.md` §6.1 |

## 背景

系统的威胁模型是：**用户提供的 Spec 不可信，目标 API 是外部系统。**

具体地，`servers[].url` 完全由 Spec 内容决定，而平台会照着它发起真实 HTTP 请求。攻击者填入 `http://169.254.169.254/` 即可让平台代其访问云元数据服务——一次成功的 SSRF 可能获取实例凭证。

防御方式是在出站前校验（白名单、内网地址阻断、破坏性方法拦截等）。**但校验的有效性取决于它覆盖了多少流量。**

若系统中存在第二条出站路径，校验就只保护了一部分流量，而且**这种失效不会被察觉**——主路径一切正常，测试全绿。

## 决策

**所有出站 HTTP 请求必须经 Guardrail 发出，包括对 LLM 提供商的调用。**

该约束用三重手段保证：

| 手段 | 说明 |
| :--- | :--- |
| **依赖白名单** | 静态检查：HTTP 客户端库与 LLM SDK 只允许在 `guardrail/` 与 `llm/` 中 import，其他模块 import 即构建失败 |
| **行为测试** | LLM 适配器必须注入 Guardrail 的 `http_client`，这条断言无法静态检查，用集成测试验证 |
| **架构测试位置** | 检查脚本放在 `tests/architecture/`，与规则本身同目录，便于对照阅读 |

## 被否决的备选

### 备选一：网络层隔离

用防火墙规则或独立 egress proxy 限制出网，使"无法绕过"成为**部署层面的事实**。

**否决理由（针对 MVP）：**

- 单机 Docker Compose 部署下难以可靠实现，且配置无法纳入 CI 验证
- 该方案被保留为 **V1.0 的演进方向**（`02` §1.2：独立 Egress Proxy 进程）——届时"唯一通道"由代码约定升级为网络拓扑约束

这是一个**分期**决策，不是否决。

### 备选二：靠开发者约定

在文档和代码评审中约定"新增出站调用必须走 Guardrail"。

**否决理由：**

- 约定在今天是生效的，在下个月新同事为图省事 `import httpx` 时失效
- **失效时不会有任何信号**：代码能跑、测试能过，直到某次恶意 Spec 被上传
- 把"大家记得"变成"想违规就构建失败"，成本极低而收益确定

### 备选三：只约束"打目标 API"的路径，LLM 调用豁免

理由看起来是：LLM 提供商的地址来自应用配置，不是用户可控，风险较低。

**否决理由：**

- 架构约束一旦有例外，就退化为"约定"——而例外会逐渐增多
- SR-8 明确要求 LLM 出站同样受保护，覆盖 DNS 层面的异常（如配置错误指向内网）
- 统一的出站口使审计日志的覆盖面完整（`03/Guardrail.md` GR6：`allow` 与 `deny` 都记录）

## 后果

**正面：**

- 白名单与内网阻断覆盖**全部**出站流量，无盲区
- 架构约束成为**构建期可验证的事实**，而非依赖记忆
- 审计日志能够回答"这个 Run 访问了哪些 host"（`03/Guardrail.md` §10）

**代价：**

- 新增任何出站依赖都必须走 Guardrail，灵活性下降
- LLM SDK 必须支持注入外部 HTTP 客户端（`08` §2.3），这限制了可选的 SDK
- 需要维护一套架构测试，且新增模块时要同步更新白名单配置

**已知的验证缺口：**

"是否注入了 Guardrail 客户端"是运行期事实，静态检查无法覆盖，只能靠 §决策 表中的行为测试。该测试失败时的表现是"审计日志中缺少该请求"，而非任何异常——因此在新增 LLM 调用路径时，必须同步扩展该测试。
