# ADR-0005：LLM 调用收敛到 Provider 接口

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `02-架构设计.md` D7 |
| 相关文档 | `02-架构设计.md` §5、`08-工程规范.md` §2.2 |

## 背景

调用 LLM 的环节有两个：`TestCaseGen`（用例生成）与 `LogAnalyzer`（归因兜底）。

业务代码如何调用 LLM，有三种做法（见备选）。选择的关键事实是：

**本项目的 LLM 选型在早期就已变更过一次**——设计文档最初基于 Claude 撰写，后改为阿里云百炼的 Qwen3.5-Plus。

此外，不同 Provider 的**结构化输出机制语义不同**：

| Provider | 机制 |
| :--- | :--- |
| Claude | `output_config: {format: ...}` + `messages.parse()` |
| Qwen（百炼） | `response_format: {"type": "json_schema", ...}` + `strict` |

若不隔离，这种差异会渗入业务代码，且**混在业务逻辑中难以辨认**。

## 决策

**`TestCaseGen` 与 `LogAnalyzer` 不直接调用任何 LLM SDK，只依赖一个内部接口：**

```python
LLMClient.generate(prompt, schema) -> BaseModel
```

百炼只是该接口的一个适配器实现（`llm/qwen.py`）。

**接口面必须窄**：只暴露"提示 + Schema → 结构化对象"。Provider 特有参数（百炼的 `enable_thinking`、`result_format` 等）在适配器内部映射，不进入接口签名。

## 被否决的备选

### 备选一：业务代码直接调用 SDK

**否决理由：**

- 换 Provider 时改动面失控（本项目已经历过一次选型变更）
- 每新增一个模型档位，业务代码中就要增加分支判断
- Provider 差异与业务逻辑混杂，重构时无法分辨某一行属于哪一类

### 备选二：使用 LangChain 的模型抽象层

项目已经使用 LangGraph（LangChain 生态的一部分），复用其抽象层看起来顺理成章。

**否决理由：**

- 引入一个大依赖来换取一个薄接口，收益与成本不匹配
- LangChain 自身的抽象层也在版本间演进，等于把"跟随 Provider 变更"换成"跟随框架变更"
- 该抽象覆盖的 Provider 特性是**最广的公约数**，而本项目只需要"结构化生成"一项能力

### 备选三：定义接口，但允许业务代码在需要时绕过

**否决理由：**

有例外的抽象等于没有抽象。绕过一旦发生，被绕过的调用就不会经过 Guardrail 的注入路径（`08` §2.3），同时破坏 ADR-0002 与本次决策。

## 后果

**正面：**

- 换 Provider 或换档位时，改动限定在适配器内
- **单测可注入假实现，不消耗真实配额**——这是 L3 评测（`09` §5.5）能够对多个档位并行评测的前提
- Provider 差异被隔离在一处，可辨认、可测试

**代价：**

- **无法使用 Provider 的最高阶特性**（若某特性无对应抽象）。MVP 阶段可接受，因为所需能力只有"结构化生成"一项
- 适配器需要维护 Provider 特有的参数映射

**约束：**

- LLM SDK 只允许在 `llm/` 中 import（`08` §2.2）
- 适配器构造 SDK 客户端时**必须注入 Guardrail 的 `http_client`**（`08` §2.3），否则其流量绕过 ADR-0002 的约束。该约束无法静态检查，用行为测试验证
