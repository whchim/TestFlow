# ADR-0019：校验解析后的 IP 并钉死连接目标

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/Guardrail.md` GR1、GR2 |
| 相关文档 | `03/Guardrail.md` §4、`09-测试策略.md` §4 |

## 背景

SR-2 要求阻断对内网地址的请求。实现时需要决定：**校验的对象是什么，以及校验与连接之间的关系。**

最直觉的实现是"解析域名 → 检查 IP 是否属于内网 → 通过则发请求"。该实现存在一个根本性的缺陷。

## 决策

处理一个出站目标时分三步：

**① 主动解析域名，得到全部 IP。**

**② 校验列表中每一个 IP 都不在禁止网段。**

**③ 用已校验的 IP 直接建立连接（钉死目标），手动设置 `Host` 头。**

**④ 连接建立后，二次校验 socket 的对端地址作为兜底。**

## 被否决的备选

### 备选一：只校验域名（不解析）

例如按域名后缀判断、或只比对白名单。

**否决理由：**

- 域名不能反映实际连接的目标。`evil.com` 可以解析到任何 IP
- SR-2 的目的正是防止"域名看起来正常但指向内网"

### 备选二：解析并校验，但仍让 HTTP 客户端自行解析

即"校验一次、连接时再解析一次"。

**否决理由：DNS Rebinding（TOCTOU）。**

```
① 解析 evil.com → 8.8.8.8（公网）→ 校验通过 ✅
② 攻击者把 evil.com 的解析改为 169.254.169.254
③ HTTP 客户端重新解析 → 连到内网 ❌
```

**只要"校验"与"连接"是两次独立的解析，中间就存在窗口。** 校验的是旧的，连的是新的。

### 备选三：只校验第一个解析结果

**否决理由：**

一个域名可能返回多个 A 记录。若只校验第一个，而客户端实际选中了未校验的第二个（内网地址），防护失效。

### 备选四：依赖网络层隔离替代应用层校验

见 ADR-0002 的讨论。**该方向被保留为 V1.0 的演进**，但即使有网络层隔离，应用层校验仍有价值（纵深防御）。

## 两个必须显式处理的实现陷阱

### 陷阱一：IPv4 映射的 IPv6 地址

以下两个地址**语义上完全相同**：

```
::ffff:127.0.0.1     ==     127.0.0.1
```

若实现只检查 IPv4 网段：

```python
if ip in PRIVATE_V4_NETWORKS:  # ❌ 会被 ::ffff:169.254.169.254 绕过
    deny()
```

攻击者传入 `http://[::ffff:169.254.169.254]/` 即可直取云元数据。

**正确做法**：先用 `IPv4Address.ipv4_mapped` 归一化后校验，或对 IPv6 显式检查映射网段。

同类问题还有 6to4（`2002::/16`）与 NAT64（`64:ff9b::/96`）——它们都封装 IPv4，构成绕过路径。

### 陷阱二：这类漏洞在被利用前没有任何症状

正常测试**全部通过**。没有任何报错、没有性能异常、没有日志异常。

**因此本决策必须配套对抗性测试集**（`09` §4）：为每一种已知绕过手法构造一个测试用例。

## 后果

**正面：**

- 消除 TOCTOU：即便校验与连接之间存在时间窗口，第 ④ 步会在**已连接但尚未发送数据**时发现异常并断开
- 多 A 记录场景下不会被绕过

**代价：**

- 需要自定义 HTTP 传输层（`httpx` 的 transport 层），实现复杂度高于"直接发请求"
- **HTTPS 场景下需手动处理 SNI 与证书主机名校验**——钉死 IP 后，主机名需显式传递。这是 `03/Guardrail.md` Q3 的开放问题，实现时需确认

**测试要求：**

| 用例 | 期望 |
| :--- | :--- |
| `http://169.254.169.254/` | deny |
| `http://[::ffff:169.254.169.254]/` | deny |
| `http://[2002:a9fe:a9fe::]/` | deny |
| `http://[64:ff9b::a9fe:a9fe]/` | deny |
| DNS rebinding（校验后切换解析） | deny |
| 多 A 记录中包含内网地址 | deny |
