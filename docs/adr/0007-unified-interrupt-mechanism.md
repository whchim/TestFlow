# ADR-0007：两个中断点统一使用 interrupt 机制

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `06-Agent编排.md` G6 |
| 相关文档 | `06-Agent编排.md` §5、`01-TestFlow_PRD.md` §4.2 |

## 背景

流程中有两处需要暂停，它们的形态差异明显：

| 中断点 | 等待对象 | 典型时长 | 唤醒源 |
| :--- | :--- | :--- | :--- |
| **IP-1** 用例确认 | **人** | 分钟 ~ 天 | 用户在前端提交决策 |
| **IP-2** 等待执行结果 | **机器** | 秒 ~ 分钟 | Celery Worker 完成回调 |

看起来是两类不同的问题，容易写成两套实现。

## 决策

**两个中断点统一使用 LangGraph 的 interrupt 机制**，不混用"节点内轮询等待"。

恢复路径因此唯一：**从 Checkpoint 恢复 + 传入一个载荷**。

| 中断点 | 载荷内容 |
| :--- | :--- |
| IP-1 | 用户的人工决策（哪些用例通过、哪些否决） |
| IP-2 | "结果已就绪"的信号 |

## 被否决的备选

### 备选一：IP-2 在节点内循环轮询等待

在 `dispatch_cases` 节点内写循环，周期性查询"是否全部完成"，完成后返回。

这个写法在 IP-2 的场景下看起来完全合理——等待时间只有几秒到几分钟。

**否决理由：**

- **进程被占用**。节点持有执行线程直到结果返回，Worker 并发度被无效消耗
- **重启即丢失**。图执行不在 Checkpoint 中挂起，进程重启后无法恢复
- **无法处理部分失败的超时场景**（`06` §6.4 要求超时后按部分失败推进）

### 备选二：IP-1 用 interrupt，IP-2 用轮询

按"哪个方便用哪个"的思路混合。

**否决理由：**

- **两套恢复语义**。Checkpoint 的语义边界变得模糊：有些挂起状态可从 Checkpoint 恢复，有些不能
- **两套错误处理**。轮询路径的超时、取消、异常行为需要独立设计
- **IP-1 场景直接排除轮询**——用户可能离开数小时甚至数天（`06` §5.1 允许挂起 7 天），进程不可能挂那么久。一旦发现"轮询在 IP-1 走不通"，就会被迫改造 IP-2，不如一开始统一

## 后果

**正面：**

- 恢复路径唯一，实现与测试都只有一条
- 两类挂起状态都可由 Checkpoint 恢复，`02` §7 的故障恢复表因此成立
- IP-1 的 7 天挂起与 IP-2 的秒级等待用同一机制表达，无需区分

**代价：**

- IP-2 的唤醒必须走 `06` §6 的完整路径（内部 HTTP 端点 + 完成判定 + per-Run 锁），比轮询复杂
- 该复杂度是必要的，见 ADR-0008

**实现注意事项：**

LangGraph 的中断/恢复 API 在不同版本间有过演进（`interrupt_before` 与节点内 `interrupt()` 并存）。

**本决策只约定语义**（挂起于 Checkpoint、由外部载荷唤醒）；具体调用形式须以项目锁定的 LangGraph 版本为准，落地时在代码注释或 `03/` 中记录。

> 不要在实现时凭记忆写 API——这是 `06` §5.2 明确写入文档的警示。
