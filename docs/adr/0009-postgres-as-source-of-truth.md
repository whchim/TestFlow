# ADR-0009：PostgreSQL 是唯一事实来源

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `02-架构设计.md` D4、`04-数据模型.md` DM5 |
| 相关文档 | `02-架构设计.md` §6、§7、`06-Agent编排.md` §2 |

## 背景

系统使用两种存储，它们的特性互补：

| 存储 | 特性 | 承担 |
| :--- | :--- | :--- |
| **Redis** | 快，可丢弃 | 图执行的 Checkpoint、Celery Broker |
| **PostgreSQL** | 事务、持久、可查询 | Spec、用例、执行结果、审计日志、凭证 |

两者同时持有部分相关信息（例如"已完成多少用例"既在状态对象中，也可从结果表统计）。

**当两者矛盾时听谁的**，必须在架构层面一次性规定，否则每个开发者会各自决定。

## 决策

**PostgreSQL 是唯一事实来源；Redis 只是进度指针与加速层。**

具体落为两条不可违反的约束：

**① 写入顺序：先落库，后推进。**

Celery 任务完成时，先写结果到 PostgreSQL（带幂等键），成功后再触发回调唤醒图（ADR-0008）。图恢复时**从 PostgreSQL 读取结果**，不依赖回调载荷中的内容。

**② 计数字段是缓存。**

`runs.expected_case_count` / `settled_case_count` 等字段为**派生缓存**。任何正确性判定（如"是否全部完成"）一律以 `SELECT count(*)` 查询 `case_results` 为准。

## 被否决的备选

### 备选一：Redis 也参与事实判定

把 Checkpoint 中的状态视为权威，或者从回调载荷中直接读取结果。

**否决理由：**

- **回调可能丢失或重复**。载荷内容不可信，把它当作事实来源等于把正确性建立在不可靠的通道上
- **Checkpoint 可能过期**。它是"某个时刻的快照"，不是"当前真相"
- 若顺序颠倒（先推进后落库），图可能在结果尚未持久化时被唤醒，读到空结果——**而这是一个时序相关的 bug，多数情况下不会发生**

### 备选二：只用 PostgreSQL，不用 Redis

减少一个组件，消除一致性问题。

**否决理由：**

- Checkpoint 是高频读写且生命周期短的（`02` §6：7 天 TTL），放进关系库会带来不必要的写入压力
- Celery 的 Broker 需要低延迟的消息原语，PostgreSQL 不适合承担该角色
- Redis 丢失的后果是可接受的（未完成的 Run 标记失败后可从 PG 已有结果重跑），因此**不必为它付持久化成本**（`10-部署运维.md` OP7）

## 后果

**正面：**

- 一致性判定有唯一依据，不受时序与通知可靠性影响
- Redis 可以安全地丢弃数据，运维简化
- 幂等（ADR-0010）与唤醒（ADR-0008）都以 PG 为基础，三者相互支撑

**代价：**

- 每次任务完成多一次 PostgreSQL 写入
- 图恢复时多一次查询
- 计数字段需要额外的对账机制（见下）

**运维影响：**

该决策直接导致 PostgreSQL **必须配置备份**（`07` NF5）：

| 存储 | 丢失后果 | 态度 |
| :--- | :--- | :--- |
| Redis | 未完成的 Run 重跑 | **可接受** |
| PostgreSQL | 所有测试资产不可恢复 | **不可接受** |

> 对本决策的常见误读是把"Redis 可丢"的态度顺延到 PG。两者性质完全不同，`07` §4.1 专门澄清了这一点。

**对账机制：**

计数字段是缓存，就有漂移风险。因此设一个定期对账任务，比对缓存值与真实统计，漂移即告警——这是发现幂等逻辑缺陷的早期信号（`04` DM5）。
