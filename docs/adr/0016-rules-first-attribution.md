# ADR-0016：归因规则优先、LLM 兜底

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/LogAnalyzer.md` LA1 |
| 相关文档 | `03/LogAnalyzer.md` §2、§4、§5 |

## 背景

**归因**是判断"测试失败是谁的锅"——是服务端缺陷、用例写错、测试数据缺失，还是环境问题。

既然系统已经使用 LLM，最直接的做法是**把失败信息交给 LLM，让它判断原因**。

但大多数失败其实**一眼可判**：

| 现象 | 原因 |
| :--- | :--- |
| 返回 500 | 服务端出错 |
| 返回 401 | 凭证问题 |
| 返回 404 | 资源不存在（可能是测试数据未准备） |
| 连不上 / 超时 | 网络或环境 |

这些用几行条件判断即可确定，不需要 LLM。

## 决策

**规则优先：先用确定性规则判断；规则未命中的，才调用 LLM 兜底。**

**并将「规则覆盖率」作为一等指标采集与展示：**

```
规则覆盖率 = 被规则确定性归因的失败数 ÷ 总失败数
```

该指标随报告输出，并出现在监控的**先行指标**列表中（`07` §5.3）。

## 被否决的备选

### 备选一：全部交给 LLM 归因

**否决理由：**

| 维度 | 规则 | LLM |
| :--- | :--- | :--- |
| 确定性 | 同输入必得同输出 | 有随机性 |
| 可解释 | 能指出命中了哪条规则 | "模型认为" |
| **可测试** | 可写单测（输入 → 期望归因） | **无法写断言测试** |
| 成本与延迟 | 零 | 每次调用 |

其中**"可测试"是最关键的一条**：规则库是代码，可以评审、版本化、写单测；而 LLM 的归因行为无法写成回归测试，只能靠统计评估。

此外，本项目的归因结论会被用来排查生产问题——**一个无法解释来源的结论，价值有限**。

### 备选二：全部用规则，不用 LLM

**否决理由：**

存在规则无法判定的一类失败：**HTTP 状态码为 2xx（成功），但响应内容与预期不符。**

这可能是：
- 服务端行为与 Spec 不符——**真缺陷**
- 用例的断言本身写错了——**用例缺陷**

区分这两者需要理解语义。规则写不出来，而这类失败在实际使用中相当常见。

## 「规则覆盖率」为何是一等指标

这不是一个附带统计，而是一个**决定成本与质量的先行指标**：

| 作用 | 说明 |
| :--- | :--- |
| **决定成本** | 规则的 `02` §5.4 成本测算建立在"仅约 20% 的失败需调用 LLM"这一假设上。若覆盖率远低于预期，M8 会被击穿——**而成本报表上只表现为"数字变大了"，看不出根因** |
| **衡量规则库质量** | 没有它，"要不要补规则"只能凭感觉 |
| **决定 V1.0 是否引入检索** | 见 ADR-0017 |

**立场：规则覆盖率长期偏低时，正确的反应是补规则，而不是"反正 LLM 能判"就放任。**

放任的后果是成本随失败数线性增长，且归因质量从确定性滑向概率性。

## 后果

**正面：**

- 归因结论确定、可解释、可回归测试
- 成本可控且可预测
- `attributions.method` 字段使**两条路径的准确率可分别评估**（PRD M4 的分母来源）

**代价：**

- 需要维护规则库，且规则需按优先级排序、短路匹配
- 每条规则都应可单测

**实现约束：**

| 约束 | 依据 |
| :--- | :--- |
| LLM 兜底的类别必须是**封闭枚举** | `03/LogAnalyzer.md` LA2——自由生成的类别会漂移为同义词，使按类别聚合的统计失效 |
| 归因须读取用例的 `confidence` | LA3——低置信度用例的断言本身可能是错的 |
| `unknown` 不重试且需监控 | LA7——重试对"信息不足"无效；占比升高是规则库缺口的信号 |
| 拒绝类归因由规则直接判定，不走 LLM | `03/Guardrail.md` GR10 |
