# ADR-0004：MVP 采用单队列，不做长短任务分流

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `02-架构设计.md` D6 |

## 背景

项目的终态架构蓝图（`imgs/TestFlow架构图.svg`）中，`TestExecutor → Celery` 这条边上标注着：

> **短任务 await / 长任务提交**

即按任务耗时分流——短任务原地等待结果，长任务提交到队列异步执行。

实现 MVP 时，需要决定是否现在就实现这个双路径。

## 决策

**MVP 收敛为单路径：所有测试任务统一提交到 Celery 队列，不做长短分流。**

**这是对自身架构蓝图的主动偏离，而非实现简化。** 该偏离已登记在 `01-TestFlow_PRD.md` §3.1 的版本分期表中：双路径列为 V1.0 项。

## 被否决的备选

### 备选一：按蓝图实现双路径

**否决理由：**

核心论据是本项目的流程特征——**存在人工确认环节（IP-1）**。

用户需要审阅 AI 生成的用例并勾选确认，这个过程可能持续数分钟到数天（`06` §5.1 允许挂起 7 天）。在这个前提下：

> **不存在需要"立刻返回"的短任务——用户本来就在等待。**

双路径要解决的问题（让短任务不等队列）在本项目的实际流程中不存在。

而引入双路径的代价是具体的：两套错误处理、两套超时语义、两套重试策略。这是为**不存在的收益**支付双倍的复杂度与缺陷面。

### 备选二：完全取消 Celery，改为同步执行

**否决理由：**

- 失去对目标 API 的并发控制手段（`03/TestExecutor.md` §8：并发度直接决定对目标服务的压力）
- `acks_late` 提供的崩溃重投能力是 `02` §7 故障恢复表的基础
- 与终态蓝图差异过大

## 后果

**正面：**

- 编排层与执行层的接口只有一条路径，错误处理与超时语义唯一
- 减少了 `06` §4 路由表的条件分支

**代价：**

- 若将来出现延迟敏感的任务类型（例如 Spec 变更后的增量探测），需要重新引入分流逻辑

**必须在文档中标注的事项：**

这次决策是**主动偏离自己画的架构图**。将来读代码的人很可能发现"架构图上有两条路，代码里只有一条"，并判断为实现偷懒，进而"修正"回去。

因此：

| 措施 | 位置 |
| :--- | :--- |
| 偏离登记 | `01-TestFlow_PRD.md` §3.1 版本分期表 |
| 理由记录 | 本 ADR |
| 架构图定位声明 | `02-架构设计.md` 文首："架构图描述 V2.0 终态，非 MVP 范围" |

## 引入分流条件的时机

V1.0 出现**明确的、延迟敏感的**任务类型时再引入，并需先回答：该任务的等待时间是否真的值得为它维持第二条路径？
