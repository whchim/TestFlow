# ADR-0020：不跟随重定向

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/Guardrail.md` GR5 |
| 相关文档 | `03/Guardrail.md` §6、`01-TestFlow_PRD.md` SR-4 |

## 背景

HTTP 的重定向机制：客户端请求 A 地址，服务器返回 `3xx` 状态码与 `Location` 头，客户端自动转到新地址取内容。

**"跟随重定向"是 HTTP 客户端的默认行为**——不特意关闭，它就会跟随。

这构成了一个安全缺口：`Location` 由服务器控制，可以指向任何地址。

## 决策

**不跟随任何重定向**（`follow_redirects = False`）。

`3xx` 响应作为**测试结果**返回，不继续请求 `Location` 指向的地址。

## 被否决的备选

### 备选一：跟随，但每次跳转重新执行全部校验

**否决理由：**

```
第 1 步  请求白名单内的 api.example.com        ✅ 校验通过
第 2 步  返回 Location: http://169.254.169.254/
第 3 步  若跟随 → 直接到了内网                 ❌
```

**一次跳转就绕过了白名单与内网阻断。**

"每跳重新校验"在逻辑上可以修补这一点，但：

- **每一次跳转都是一个新增的攻击面**
- 跳转可以链式（A→B→C→D…），**只要有一跳漏检即全盘失守**
- 该实现比"禁止跟随"复杂得多，而它要覆盖的场景在本项目中并不常见

**为不常见的情况引入一长串风险，不划算。**

### 备选二：跟随，但限制最大跳转次数

**否决理由：**

限制次数不能修复根本问题——**第一次跳转就已经越过了白名单**。

次数限制只防御无限跳转（DoW），与 SSRF 无关。

### 备选三：只允许跳转到同源地址

比"完全禁止"更宽松，同时似乎限制了风险。

**否决理由：**

- "同源"的判断本身依赖校验逻辑的正确性，与备选一共享同样的复杂度
- 同源跳转在 API 测试中同样罕见，收益不足以支撑实现成本
- MVP 阶段的取舍应偏向简单

## 后果

**正面：**

- 消除了通过重定向绕过白名单与内网阻断的路径
- 不引入"每跳校验"这一实现复杂点

**代价：**

- **若被测接口存在合法的规范化重定向**（如 301 跳转到带结尾斜杠的地址），用例将收到 `3xx` 而非最终响应内容
- 用户需要用最终地址重新生成用例

**该代价小于放行重定向带来的风险。** 且 API 测试场景中的重定向并不常见。

**行为说明（3xx 如何处理）：**

`3xx` 不是错误，而是一个**有价值的测试发现**——用户会知道该接口存在重定向行为。因此：

- 请求正常完成，`case_results.status` 正常判定
- 断言由用例自身决定（若用例期望 200 而收到 302，则该用例如实失败）

**审计影响：**

每次请求的 `allow` / `deny` 均记录（`03/Guardrail.md` GR6）。重定向产生的 `Location` 头**不触发新的请求，因此不产生新的审计记录**——这是"不跟随"策略的一个可观测特征。
