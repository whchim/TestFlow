# ADR-0014：断言必须可确定性求值

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/TestCaseGen.md` TG2 |
| 相关文档 | `03/TestCaseGen.md` §3.2、`03/LogAnalyzer.md` §1 |

## 背景

**断言**是测试用例中的"预期"——例如"预期返回 200"、"预期响应 JSON 中存在 `data.id` 字段"。运行时逐条求值，全部成立才算用例通过。

有些检查天然难以用代码表达，例如：

> "这个错误信息对用户是否友好？"

于是出现一个看起来合理的方案：**也交给 LLM 判断**——让模型读一遍响应，回答"这个错误信息友好吗"。

## 决策

**断言必须是可确定性求值的表达式。禁止引入由 LLM 判定的断言类型。**

具体地，断言的类型限定为：`status_code`、`json_path`、`header`、`schema_valid`、`body_contains`、`response_time`（`03/TestCaseGen.md` §3.1）。

断言禁止的典型形态：

```python
# ❌ 禁止
{"type": "llm_judge", "prompt": "这个错误信息是否友好？"}
```

**需要语义判断的需求归入「归因」，而非「断言」。**

## 被否决的备选

### 备选一：引入 `llm_judge` 型断言

**否决理由：**

核心原则是：**"测试通过与否"是一个必须确定的事实。**

| 问题 | 后果 |
| :--- | :--- |
| **不可复现** | 同一响应，今天判过、明天判不过（LLM 有随机性） |
| **报告失去可信度** | 用户发现"同一个东西跑两次结果不同"，就不再相信任何一次 |
| **无法排查争议** | **你无法向他人证明这个断言确实成立**——它取决于模型当天的输出 |

第三条最为致命：一个**不可论证**的判定，无法作为缺陷报告的依据，也无法在评审中被质询。

### 备选二：LLM 判定 + 人工复核

**否决理由：**

- 人工复核的成本高于直接把这类检查交给人工——**等于绕了一圈回到人工**
- 且被否决的仍是"通过与否不确定"这一根本问题，复核只是在事后的补救

### 备选三：把语义检查改写成规则

例如用关键词匹配判断"错误信息是否包含字段名"。这是**可行且被鼓励的**方向。

**但它的地位是「改写为可判定形式」，不是本决策的备选**——若某个语义检查能被改写成确定性规则，那它就变成了普通断言，正是本决策期望的结果。

## 断言的边界划在哪里

| | 断言 | 归因 |
| :--- | :--- | :--- |
| 回答的问题 | 这个测试**通过了吗** | 失败**是什么原因** |
| 判定要求 | **必须确定** | 允许概率判断 |
| 出错后果 | 报告不可信 | 排查方向偏差 |
| 可否人工纠正 | 不需要（客观事实） | ✅ 可以（`attributions.human_verdict`） |

**归因之所以可以允许不确定性**，是因为它有人工纠正机制：人可以标记"这条归因判错了"并给出正确类别（`03/LogAnalyzer.md` §8.2）。断言没有这个兜底——它的结论就是最终结论。

## 后果

**正面：**

- 测试结论客观、可复现、可论证
- 断言求值引擎是纯函数，可独立单测（`09` §2.2 将其列为"必须充分覆盖"的模块）
- 报告的数字具有确定性，可作为决策依据

**代价：**

- 部分语义级检查无法直接表达，需要改写成规则或放弃
- 需要明确区分"断言"与"归因"的职责边界，并在实现与评审中保持

**实现要求：**

- 结构化输出的 Schema 中**不定义** `llm_judge` 类型，使模型无法生成
- `03/TestCaseGen.md` §5.1 的 L1 校验包含"断言类型在允许集合内"的检查
