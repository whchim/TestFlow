# ADR-0017：不引入检索式归因

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/LogAnalyzer.md` LA5 |
| 相关文档 | `03/LogAnalyzer.md` §10、`02-架构设计.md` §3.1 |

## 背景

"检索式归因"（RAG）的思路是：把历史失败案例存入向量库，新的失败到来时先检索"这个错误以前见过吗？当时的结论是什么？"，用检索到的历史结论辅助或替代 LLM 判断。

这是一种成熟且常见的技术组合，终态架构蓝图（`imgs/TestFlow架构图.svg`）中也画了向量库与 BM25 两个节点。

问题在于：**是否应该在 MVP 阶段就实现它。**

## 决策

**MVP 不引入检索式归因。向量库与 BM25 列为 V1.0 项。**

**这不是"技术做不到"，而是"现在做没有意义"。**

## 被否决的备选

### 备选一：MVP 就实现检索式归因

**否决理由——核心推理是一句话：**

> **检索只能复用已知的，不能解决未知的。**

| 阶段 | 大多数失败的性质 | 有效手段 |
| :--- | :--- | :--- |
| **冷启动（MVP）** | **第一次遇到**的问题 | 规则（确定）+ LLM（理解语义） |
| **运行数月后** | 相当比例是**以前见过的** | **检索历史结论** |

**冷启动阶段的检索不只是"没用"，而是有害：**

- 检索库中没有可复用的历史——检索出的"最相似案例"本身参考价值有限
- **检索结果会污染判断**：LLM 看到一个并不真正相似的历史案例，可能被带偏，给出错误结论

**此外，该组件的质量无法评估。** 没有历史数据，就无法回答"它检索得准不准""引入它后准确率提升了吗"。这意味着 MVP 阶段会投入大量精力维护一个**结果不可验证**的组件。

### 备选二：实现检索，但只在检索结果置信度高时使用

**否决理由：**

- "置信度高"的阈值本身无法在冷启动阶段标定——没有数据来判断什么算高
- 引入了一个需要调参的环节，而调参的依据同样缺失

## 正确的顺序

```
先让规则 + LLM 跑起来
      ↓
积累归因数据 + 人工纠错记录（attributions.human_verdict）
      ↓
检索才有物料可用
```

**人工纠错记录是关键前提**——它提供了"经过人工确认的正确归因"，这正是检索库所需的优质内容。没有它，检索库中只有平台自己的（可能有错的）判断，复用它等于放大错误。

## 引入时机与验证方式

满足两个条件时再引入：

1. **历史归因样本量足够**
2. **规则覆盖率进入平台期**（补规则不再能提升覆盖，ADR-0016）

届时用 Golden Set（`09` §5.3）验证，并回答两个问题：

| 问题 | 期望 |
| :--- | :--- |
| LLM 调用量下降了吗？ | 是（这是检索的主要收益） |
| 准确率下降了吗？ | 否（若下降超过阈值，则检索引入的是噪声） |

**两个问题必须同时回答。** 只降成本不降质量才是收益；若成本降了但质量也降了，需要权衡而非默认接受。

## 后果

**正面：**

- MVP 少维护一个组件（向量库、embedding 流程、检索调参）
- 不需要在质量无法评估的情况下做技术选型（pgvector vs Milvus 等）
- 存储层保持简单（`02` §3.1）

**代价：**

- 已知失败模式的重复出现无法被复用，每次都要走 LLM 兜底
- 该代价在 MVP 阶段很小（失败多为首次出现），但会随运行时间增长

**与终态蓝图的关系：**

架构图中确实画了向量库与 BM25。**这属于"终态蓝图"而非"MVP 范围"**，与 ADR-0004 同属一类偏离——`02` §1.2 的差异表中已登记。

## 一条可复用的判断

> **"加一个更强的技术"不一定是对的；"现在的阶段需要它吗"才是问题。**

RAG 是热门技术，容易条件反射地加上。但它的价值前提是"有东西可检"，**这个前提在冷启动阶段不成立**。

顺序错了，好技术也会变成负担。
