# ADR-0024：SSE 只发信号，不发数据

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `05-API契约.md` API7 |
| 相关文档 | `05-API契约.md` §4.4、§5.1、`01-TestFlow_PRD.md` F8 |

## 背景

用户需要实时看到运行进展（阶段变化、进入待确认、执行进度、完成）。SSE 提供了"服务器主动推送"的能力，比轮询更实时。

实现时有一个看似优化的选择：**推送消息时把数据本身也带上**。

理由听起来合理——"反正都要推一次，把用例内容一起带过去，网页就不用再请求一次，能省一次网络往返"。

## 决策

**SSE 只发送轻量信号（阶段变化、中断、进度、完成），客户端收到信号后通过 REST 拉取实际数据。**

事件类型与载荷仅限：

| 事件 | 载荷 |
| :--- | :--- |
| `run.phase` | `{"phase": "..."}` |
| `run.interrupted` | `{"type": "hitl_review"}` |
| `run.progress` | `{"settled": N, "expected": M}` |
| `run.completed` / `run.failed` | 少量元信息 |
| `heartbeat` | 空 |

**任何状态的权威来源都是 REST。**

## 被否决的备选

### 备选一：SSE 事件携带完整数据

**否决理由：**

**这会让 SSE 成为第二个数据源。**

系统随即拥有两条数据通道：

```
通道一：客户端调用 REST 拉取数据
通道二：SSE 推送数据
```

**两条通道必然带来一致性问题**：SSE 推送的是某一时刻的快照，客户端随后通过 REST 拉到的可能是更新的版本。**哪个是权威？** 这个问题一旦存在，就必须在每一处消费数据的地方回答它。

**此外，实现成本会显著上升：**

| 需求 | 说明 |
| :--- | :--- |
| **事件回放** | 断线重连后需补推丢失的事件，需维护事件序号与缓冲 |
| 乱序处理 | 网络抖动导致的事件乱序需处理 |
| 载荷版本 | 推送的数据结构与 REST 的不一致时需协调 |

### 备选二：不用 SSE，客户端定时轮询

**否决理由：**

- 实时性差（轮询间隔与响应延迟直接耦合）
- 空转浪费——运行期间大部分时间没有变化
- 用户体验上，"确认"这类需要及时提示的事件会延迟

**该方案的部分优点（简单性）已被本决策吸收**：既然 SSE 只发信号，其实现复杂度已大幅下降。

## 后果

**正面：**

| 收益 | 说明 |
| :--- | :--- |
| **单一数据源** | 状态永远来自 REST，不存在权威性问题 |
| **断线重连天然正确** | 重连后 REST 拉一次当前状态即可，**无需事件回放机制** |
| 客户端不做状态推断 | 与 `02` §2.1 的原则一致：所有状态由服务端持有 |
| SSE 实现简单 | 无需序号、缓冲、载荷版本管理 |

**代价：**

- 每次变化多一次 REST 调用

**该代价可忽略**：一次运行的持续时间为数分钟、事件数为数十条（`06` §1.2 的短跳推进模型），多几十次请求无实质影响。

## 一条可复用的判断

> **"顺便多传点数据"看起来是优化，实际往往引入了第二个事实来源。**

只要同一份数据存在两个存放处，就迟早会不一致，就需要为其设计一致性处理。

**有时"多一次请求"反而是更简单的设计**——因为简单性体现在"只有一条路径需要保证正确"，而不是"网络往返次数少"。

## 与其他决策的一致性

本决策与 ADR-0006（GraphState 只存引用）、ADR-0009（PostgreSQL 是唯一事实来源）共享同一条原则：**同一份事实只在一个地方是权威的。**

| 决策 | 权威来源 | 其他位置的角色 |
| :--- | :--- | :--- |
| ADR-0009 | PostgreSQL | Redis 是进度指针 |
| ADR-0006 | PostgreSQL | GraphState 是引用集合 |
| **ADR-0024** | **REST** | **SSE 是变更通知** |
