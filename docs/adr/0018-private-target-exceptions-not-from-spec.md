# ADR-0018：内网例外只能来自配置，永不从 Spec 派生

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/Guardrail.md` §4.6 |
| 相关文档 | `03/Guardrail.md` §4、`10-部署运维.md` §3.3 |

## 背景

两个真实需求直接冲突：

| 需求 | 来源 |
| :--- | :--- |
| **安全**：禁止向内网地址发出请求（防 SSRF） | PRD SR-2 |
| **实用**：开发者的 Spec 中写 `http://localhost:8000` 或 `http://192.168.1.10:8080` 是常态 | 测试环境本来就在内网 |

两种极端都不可行：

- **一律禁止** → 绝大多数真实 Spec 无法使用
- **一律放行** → SR-2 形同虚设

因此必须有"例外"机制。**问题不在于要不要允许例外，而在于例外从哪来。**

## 决策

**例外只能来自显式的应用配置（`guardrail_allow_private_targets`），任何情况下都不从 Spec 派生。**

| 层级 | 行为 |
| :--- | :--- |
| 默认 | 内网地址一律拒绝 |
| 例外来源 | **仅配置文件 / 环境变量** |
| 从 Spec 派生 | **禁止** |
| 云元数据地址 | **即使配置了例外也拒绝**（`03/Guardrail.md` §4.5） |
| 界面提示 | 配置了内网例外时显著提示当前已放行内网目标 |

## 被否决的备选

### 备选一：由 Spec 声明即视为授权

> "用户在 Spec 里写了这个地址，说明他想测它，那就等于他授权了。"

这个方案**看起来完全合理**，且实现最简单——不需要额外的配置项。

**否决理由（本决策的核心）：**

**攻击者只需在 Spec 中写入 `http://169.254.169.254/`，就自动获得了授权。**

这样一来，SR-2 退化为"**检查 Spec 是否声明了自己要访问的地址**"——**而 Spec 正是不可信输入**。等于没有防护。

> **类比：门禁**
> ❌ "只要你说你是这栋楼的人，门就开。"
> ✅ "只有管理员在系统里录入过的人，门才开。"
>
> 区别在于"授权"是一个**独立的、需要主动完成的动作**，还是**上传文件时自动获得的副产品**。

### 备选二：不提供任何例外

**否决理由：**

使绝大多数真实 Spec 无法使用。**一个用户第一件事就撞墙的安全设计，会被绕过而不是被遵守**——例如用户为绕过它而把测试服务暴露到公网。

安全设计必须考虑可用性，否则它会被用户自行拆掉。

### 备选三：要求用户把 Spec 中的地址改成公网地址

**否决理由：**

- 用户无法改变测试环境的内网属性
- 迫使用户修改 Spec 会破坏"Spec 是事实来源"的原则——用户提交的应与实际部署一致

## 后果

**正面：**

- SR-2 的核心防护得以成立：**授权动作与不可信输入彻底分离**
- 内网例外成为一项**显式的、可审计的、需要主动输入的动作**
- 配置项的存在使"当前放行了哪些内网目标"可查

**代价：**

- 用户多一步配置操作
- 需要在界面上显著提示，避免用户忘记自己开过例外

**验证要求（关键，不可省略）：**

如果实现错误地从 Spec 派生例外，**其余所有测试仍会通过**——因为测试环境本来就一直使用内网地址（fixture 服务跑在 `127.0.0.1`），错误实现下它们"正常工作"。

因此必须有一条专门的**负向测试**：

> 构造一个 Spec，其 `servers[].url` 指向 `127.0.0.1`，**不配置任何内网例外**，断言请求被拒绝且审计日志中出现 `deny_reason = 'private_ip'`。

**这条测试是上述安全论断的守门人。** 没有它，本决策在实现层面无法被验证。

## 一条可复用的原则

> **高风险的授权不能搭便车。**

若某个动作的后果严重（访问内网、删除数据、对外发消息），那么"同意执行它"必须是**独立的、需要额外注意力的**步骤，不能混在用户已经习惯性完成的操作中。

同一原则的另一处应用见 ADR-0021（破坏性用例的授权）。
