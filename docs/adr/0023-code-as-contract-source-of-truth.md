# ADR-0023：契约以代码为唯一事实来源

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `05-API契约.md` API1、`08-工程规范.md` EN6 |
| 相关文档 | `05-API契约.md` §1、`08-工程规范.md` §6.2 |

## 背景

API 契约的维护有两种业界做法：

| 做法 | 流程 |
| :--- | :--- |
| **设计优先** | 手写 `openapi.yaml` 描述接口 → 据此生成服务端骨架或校验实现 |
| **代码优先** | 编写代码 → 框架自动从代码生成 `openapi.json` |

项目已选择 FastAPI，它天然是代码优先框架（从 Pydantic 模型与路由生成 OpenAPI 文档）。

## 决策

**契约的唯一事实来源是 FastAPI 的路由与 Pydantic 模型；`openapi.json` 是它的产物。**

配套的治理措施：

| 环节 | 做法 |
| :--- | :--- |
| 生成 | 从运行中的应用导出，落到**仓库根目录** `openapi.json` |
| 提交 | 与代码**一同提交**，使契约变更出现在评审 diff 中 |
| CI 校验 | 重新生成并与仓库快照比对，不一致则构建失败 |
| 修正方式 | 运行生成命令并提交，**不允许手动编辑快照** |

## 被否决的备选

### 备选一：设计优先（手写 `openapi.yaml`）

**否决理由：**

> **手写一份 yaml 再让代码去迎合它，会立刻产生两份需要同步的契约。**

```
代码改了 → 忘了改 yaml → yaml 过期
                            ↓
        读 yaml 的消费者（前端、CLI、未来的外部集成）拿到的是错的
```

这正是本项目从第一份文档起就在避免的问题：**同一个事实不写两遍**（`01-PRD` §7 的"单一事实来源原则"）。

FastAPI 的自动生成能力是选用它的主要理由之一，主动放弃它去换取"设计先行"，收益不明确而代价确定。

### 备选二：代码优先，但不提交生成的快照

**否决理由：**

契约变更将**不可见**。评审者看到的 diff 里只有实现代码，无法判断"接口对外的形状是否改变了"。

对于本项目，消费者包括前端与 CLI（`02` §2.1），它们与后端同仓库发布——契约变更若不被显式呈现，前端可能在下一次构建时才发现不兼容。

### 备选三：不生成文档，手写一份 Wiki 说明接口

**否决理由：**

- 与备选一同源——手工维护的第二份描述必然与代码漂移
- 且不具备可机器消费性（无法用于生成客户端、无法做契约测试）

## 为什么 CI 校验是必需的

如果只提交快照而不校验，仍然会发生"实现改了但契约没更新"：

| 缺失环节 | 后果 |
| :--- | :--- |
| 生成 | 无契约产物 |
| 提交 | 契约变更不在 diff 中 |
| **校验** | **代码与快照可以静默分叉** |

校验使"快照过期"成为一个**构建期可检测的事实**，而不是一个需要靠自觉维持的约定。

## 后果

**正面：**

- 契约与实现**不可能不一致**（CI 强制）
- 契约变更出现在评审 diff 中，可被人工审查
- 无手工同步成本

**代价：**

- 每次接口变更都需要**多提交一个文件**（`openapi.json`）
- 若某次修正在快照上手动编辑，CI 会立即再次拒绝——**失败时的正确反应是运行生成命令，而非编辑快照**
- 契约的可读性低于精心撰写的手写文档（缺少叙述性的说明段落）

**关于可读性代价的缓解：**

`05-API契约.md` 承担"设计意图、通用约定、端点清单"的叙述职责，**但它不复制字段定义**——字段的权威定义在生成的 `openapi.json` 中。两者职责分离，不发生重叠（`05` 文首的边界声明）。

## 一次相关的修正

PRD §7 最初写的是：

> `openapi.yaml`（**FastAPI 据此生成**，为唯一事实来源）

**方向写反了。** FastAPI 是从代码生成 OpenAPI，不能反向接收手写 yaml 来生成服务端。

该表述已在 `01-TestFlow_PRD.md` v0.4 中修正。

**这个错误的性质值得记录**：它是凭印象写出的"听起来对"的陈述，未核对框架的实际行为。**技术文档中凡是"某工具会做什么"的断言，都应核对后再写。**
