# ADR-0011：LLM 生成节点的幂等是「跳过」而非「重放」

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `04-数据模型.md` DM4 |
| 相关文档 | `06-Agent编排.md` §5.3、`04-数据模型.md` §2.4 |

## 背景

`06` §5.3 对节点恢复提出了一条通用要求：

> 恢复意味着从 Checkpoint 之后重新执行。因此每个节点都必须可重入——节点可能被执行多次，结果必须一致。

对绝大多数节点，这条要求可以满足为"**重放**"：重新执行一次，得到相同结果。

**但对调用 LLM 的节点（N2 `generate_cases`），这条要求不能这样满足。**

原因：**LLM 输出是非确定性的。**同样的输入，两次调用得到不同的结果。

具体场景（这是理解本决策的关键）：

```
第 1 步  AI 为"创建用户"接口生成 8 条用例
第 2 步  用户人工确认，勾选 5 条、否决 3 条          ← 有价值的人工投入
第 3 步  进程崩溃
第 4 步  从 Checkpoint 恢复
         └─ 若按"重放"语义 ─→ 重新调用 LLM
         └─ LLM 这次生成了 9 条【不同的】用例
第 5 步  用户确认过的 5 条被替换（或与新用例混杂）
```

## 决策

**N2 的幂等语义是「已完成则跳过」，不是「重放」。**

实现上：持久化"该 Operation 是否已生成成功"这一事实，恢复时查询并跳过 `gen_status = 'succeeded'` 的 Operation。

持久化位置：`run_operations.gen_status`（`04` §2.4）。**这张关联表存在的唯一理由就是承载这个语义。**

`06` §3 表格中 N2 的幂等键 `(run_id, operation_id)`，其用途是**判定"是否已完成"，不是判定"结果是否相同"**。

## 被否决的备选

### 备选一：按幂等键 upsert 重放

与其他节点保持一致——恢复时重新生成，用 `ON CONFLICT DO UPDATE` 覆盖。

**否决理由（本决策的核心）：**

- **会静默替换用户已确认的用例**。用户在 IP-1 的人工投入被无声抹除
- **不报错**。用户下次查看时会发现执行的内容与当初确认的不一致，但无法定位是何时改变的
- **这比直接失败严重得多**——失败至少是可见的

### 备选二：重新生成，并将旧用例标记为作废

保留历史，生成新版本，两者都存。

**否决理由：**

- 用户仍需重新确认一遍，**人工投入同样被浪费**
- "哪一版是当前有效的"这一问题被引入状态管理，复杂度显著上升
- 恢复的语义从"继续"变成"重做"，与 ADR-0007 的统一恢复路径冲突

### 备选三：把 LLM 的随机性降到零（如 `temperature: 0`）

使其成为"确定性的"，从而可以安全重放。

**否决理由：**

- **降低温度不等于确定性**。相同的输入在不同时间、不同服务端负载下仍可能产生不同输出
- 而对本项目而言，生成多样性是有价值的——**把用例生成做成完全固定，等于放弃了 LLM 的主要优势**
- 即便如此，仍需要"是否已完成"的记录（重放会产生额外成本），本决策依然成立

## 后果

**正面：**

- 用户的确认结果在恢复、重试、任意崩溃场景下**都不会被破坏**
- 与 `02` 路由表中的"部分 Operation 生成失败不阻塞全局"自然衔接——只有 `pending` / `failed` 的 Operation 会被（重新）生成

**代价：**

- 本节点的幂等语义与其余节点不一致，**这是必需的例外**
- 需要额外的关联表与状态字段

**必须在文档中标注的事项：**

这是全项目最反直觉的一条决策：**"重放"在其他所有节点都是对的，只有这里错。**

将来有人重构，看到"其他节点都重放、这个节点特殊"，很可能出于"统一"的考虑改掉它——**而后果是静默丢失用户的人工确认**。
