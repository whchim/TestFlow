# ADR-0025：平台测试与 AI 评测严格分开

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `09-测试策略.md` TS1 |

## 背景

本项目的名字是 TestFlow——**它本身就是一个测试平台**。因此"测试"一词在项目内部有两个完全不同的所指：

| | A. 平台自身的测试 | B. AI 输出的评测 |
| :--- | :--- | :--- |
| 测什么 | **代码**是否正确 | **AI 生成的用例**是否好 |
| 判定 | 通过 / 失败，客观确定 | 与人工参照集比对，统计量 |
| 结果性质 | 二值 | 百分比、分布 |
| 何时跑 | 每次提交 | 变更 Prompt / 模型 / 派生算法时 |
| **是否花钱** | 否 | **是**（调用真实 LLM） |
| 未达标的含义 | 有 bug，必须修 | 质量下降，需权衡 |

## 决策

**两者使用不同的方法论、不同的工具、不同的运行时机，不得合并。**

| | A | B |
| :--- | :--- | :--- |
| 存放 | `tests/unit`、`tests/integration`、`tests/architecture` | `tests/eval` |
| 运行时机 | 每次提交 | 手动或定时 |
| **进常规 CI** | ✅ | ❌ **不进** |

## 被否决的备选

### 备选一：放进同一个测试框架、同一个 CI 阶段

从"统一入口"的角度看起来很合理——一个命令跑完所有检查。

**否决理由——两个具体的后果：**

**后果一：评测的正常波动被误判为回归。**

AI 输出有方差：同一个 Prompt、同一个模型，两次运行的维度覆盖率可能相差数个百分点。若与普通测试混在一起：

```
"覆盖率从 82% 掉到 79% 了，是不是我改坏了？"
                ↓
        实际只是随机波动
```

这会消耗大量排查时间，**并使团队对指标脱敏**——当真正的回归出现时，习惯性地认为是噪声。

**后果二：真正的 bug 被淹没。**

一旦团队习惯了"有些测试会莫名其妙变红又变绿"，就会倾向于忽略失败。此时一个真正由代码缺陷导致的失败，也会被归入"噪声"。

### 备选二：放进同一框架，但用标签区分

即"标记为 `@eval` 的测试在 CI 中跳过"。

**否决理由：**

- 依赖标签维护正确——**漏标一个就是一次意外扣费**
- 两者的**失败处理逻辑不同**（见下），共用框架意味着共用一套断言与报告机制，而它们不适用

### 备选三：AI 评测也进 CI，但只在特定文件变更时触发

**否决理由：**

比备选二更复杂（需要路径过滤规则），而收益是"自动化程度更高"。

但评测的价值在于**人看结果并做判断**，而不是"跑完自动通过"——它的输出是统计量，需要人解读。自动触发只会在无人查看时产生一份没人看的报告。

## 为什么两者的"失败处理"必须不同

| | A. 平台测试 | B. AI 评测 |
| :--- | :--- | :--- |
| 失败时的动作 | **阻塞合并** | **记录并对比，人工判断** |
| 合理反应 | 修复 bug | 决定是否接受质量变化 |

**"变红就阻塞"对 B 不成立**——因为 B 的结果本身有波动，且"质量略降但成本大降"可能是一个合理的选择（`02` §5.1 的档位评估正是这种权衡）。

## 后果

**正面：**

- 评测的统计性质被正确对待，不会污染回归信号
- CI 不会因评测产生意外费用
- 评测结果需要人工解读，这与其性质相符

**代价：**

- 需要维护两套测试基础设施
- 评测依赖人工或定时触发，**存在"忘记跑"的风险**——因此 `09` TS7 明确规定了必须触发的变更类型

**相关约束：**

- `08` EN8：Eval 默认不进常规 CI
- `09` TS7：L3 的触发条件（Prompt 变更、模型档位变更、结构化输出 Schema 变更、阶段 A 派生算法变更、归因规则库增删）

## 一条可复用的判断

> **"确定性的检查"与"统计性的评估"要分开。**

前者是"对/错"，后者是"好一点/差一点"。

**把统计性的评估当作统计性评估来对待**——它本来就有波动，不该套用"变红即阻塞"的处理方式。
