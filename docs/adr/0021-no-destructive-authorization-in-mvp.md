# ADR-0021：MVP 不提供破坏性用例的执行与授权入口

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/TestExecutor.md` TE3 |
| 相关文档 | `03/Guardrail.md` §5、`01-TestFlow_PRD.md` SR-3 |

## 背景

PRD 的 SR-3 原文要求：

> **破坏性方法默认禁用，需用户显式授权该 Operation。**

破坏性方法指 `DELETE`、`PUT`、`PATCH`——它们可能修改或删除目标环境的数据。

实现这条需求时，一个关键问题是：**"显式授权"这个动作如何设计。**

## 决策

**只实现 SR-3 的前半句（默认禁用），刻意不实现后半句（显式授权）。**

具体地：

| 行为 | 是否提供 |
| :--- | :--- |
| 破坏性用例的生成 | ✅ 照常生成 |
| 在 IP-1 中供人工审阅 | ✅ 照常展示 |
| 执行 | ❌ **不执行** |
| 授权执行的入口 | ❌ **不提供** |

界面上明确提示："以下 N 条用例涉及破坏性方法，需在目标环境中手动执行"。

防护仍为**两层**：

| 层 | 位置 | 行为 |
| :--- | :--- | :--- |
| 第一层（主防线） | N4 投递前 | 过滤 `is_destructive = true` 的用例，不投递 |
| 第二层（冗余） | Worker 侧 Guardrail | `method ∈ {DELETE, PUT, PATCH}` 且未授权 → 拒绝发出 + 审计 |

## 被否决的备选

### 备选一：在 IP-1 的确认界面中提供授权

即在用户勾选用例时，一并允许勾选破坏性用例并授权执行。

**否决理由（本决策的核心）：**

**IP-1 的确认界面是批量勾选的。**用户看到一屏用例后，很容易顺手点"全选 → 确认"。

> **如果"授权破坏性操作"也能通过这个批量动作完成，用户会在毫无察觉的情况下授权了一条 `DELETE`。**

用户在批量操作时处于"**快速通过**"的心理状态。**在这种情况下让用户承担高风险的授权决定，是交互设计上的失误**——不是因为用户不谨慎，而是因为界面在鼓励不谨慎。

### 备选二：提供独立的授权页面（流程完整）

先让用户明确地、单独地授权某个 Operation，再执行。

**否决理由（针对 MVP）：**

- 这是一个**独立的交互设计工作**：需要设计授权页、说明风险、记录授权、并保证授权与用例的对应关系可追溯
- **MVP 阶段没有"必须执行破坏性用例"的场景**——用户可以先看生成结果，需要时手动在目标环境执行一次
- 该方案被保留为 **V1.0 项**，而非被永久否决

**若将来实现，必须满足：**

| 约束 | 理由 |
| :--- | :--- |
| 授权必须**按 Operation** 粒度 | SR-3 原文如此；粗粒度授权会连带放行未审阅的操作 |
| 授权必须是**独立步骤** | 不能与"确认用例"共用同一个动作 |
| 授权必须**可审计** | 记录谁在何时授权了哪个 Operation |
| 授权必须**显式说明后果** | 用户需明确知道该操作可能删除数据 |

### 备选三：完全不做防护，交由用户自己注意

**否决理由：**

- 违反 SR-3
- 破坏性用例是**由平台自动生成并自动执行**的，用户可能根本没注意到某条是 `DELETE`

## 两条防线为何都要保留

第一层（投递前过滤）是应用逻辑，可能因 bug、重构或后续改动而失效。

第二层（Guardrail 拦截）由统一通道实施，业务代码无法绕过（ADR-0002）。

**安全设计不应假设应用层永远正确。** 冗余防线的成本很低，而它防御的是不可逆的后果。

## 后果

**正面：**

- 消除了"在批量操作中误授权删除操作"的风险
- 破坏性用例仍然可见，用户知道有哪些操作存在，只是需要手动执行
- 与 ADR-0018 共享同一条原则，设计上自洽

**代价：**

- **只实现了一半需求（SR-3 的后半句）**，需在文档中显式说明，避免被理解为遗漏
- 用户需要手动执行破坏性用例（以 MVP 的使用场景衡量，可接受）
