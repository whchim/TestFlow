# ADR-0001：编排层异步、执行层同步

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `02-架构设计.md` D1 |
| 相关文档 | `06-Agent编排.md` §1.3、`03/TestExecutor.md` §8 |

## 背景

系统有两个运行时，它们的负载性质不同：

| 运行时 | 负载 | 最优并发模型 |
| :--- | :--- | :--- |
| **编排层**（LangGraph 节点） | 调用 LLM，99% 时间在等网络 | 单事件循环 + 异步 I/O |
| **执行层**（Celery Worker） | 打目标 API，需控制对目标服务的压力 | 多进程，每进程内串行 |

朴素做法是让两者用同一个模型，但各自的"自然形态"相反：LangGraph 的节点函数天然是 `async def`，而 Celery 的并发靠 prefork 多进程、任务函数天然是同步的。

若强行统一，必须在一侧做妥协，而两种妥协都有已知问题（见备选）。

## 决策

**编排层节点用 `async def`（事件循环内并发）；执行层用同步函数 + `httpx.Client`（进程级并发）。**

两者的边界是 HTTP 客户端：编排层用异步客户端调 LLM，执行层用同步客户端打目标 API。共享的重试、超时、Guardrail 校验策略抽为独立模块，与客户端形态无关。

## 被否决的备选

### 备选一：Celery + gevent pool

用 gevent 把 Celery 任务变成协程，从而"统一为异步"。

**否决理由：**

- gevent 依赖 monkey patching，而 LLM SDK 与 `httpx` 的异步实现都会与原生的 socket/ssl 交互冲突
- 冲突的表现是"偶发卡死"，且不报错——排查成本极高
- gevent pool 在 Celery 中已被官方标记为不推荐

### 备选二：用纯 asyncio 队列替代 Celery（如 `arq`）

技术上更干净——整条链路都是异步，无需桥接。

**否决理由：**

- 放弃 Celery 的重试语义、`acks_late`、任务可见性、Flower 监控等成熟能力
- 这些能力在本项目中都有明确用途（见 `02` §7 的故障恢复表）
- 与终态架构蓝图不符（架构图中执行层是 Celery）

### 备选三：在 Celery prefork 任务内调用 `asyncio.run()`

保持 Celery，但任务内部启动事件循环来调用异步 LLM 客户端。

**否决理由：**

- 每个任务都要创建并销毁一个事件循环，开销显著
- 与 Celery 的超时机制冲突：`soft_time_limit` 依靠信号，而信号在事件循环运行期间可能无法被正确处理
- 这正是 `03/TestExecutor.md` TE7 要求三层超时严格递增的原因——但那是为 HTTP 超时设计的，不应被事件循环问题额外复杂化

## 后果

**正面：**

- 每层使用最适合自己的并发模型，不需要在任何一侧做妥协
- 避免了 "asyncio in prefork" 这一类已知的、难以排查的陷阱
- 执行层的同步代码更容易写出正确的超时与重试逻辑

**代价：**

- 需要维护两种 HTTP 客户端形态
- 共享策略（重试、超时、Guardrail 校验）必须抽为独立模块，**不能被客户端实例化方式绑住**

**约束（实现时必须遵守）：**

- Guardrail 提供同步与异步两个客户端，但**共用同一套校验实现**（`03/Guardrail.md` GR8）——两份校验逻辑必然漂移，且漂移不会被测试发现，因为两条路径的测试用例不同
