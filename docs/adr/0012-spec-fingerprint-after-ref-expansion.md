# ADR-0012：Spec 指纹在 `$ref` 展开后规范化计算

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `04-数据模型.md` DM2、`03/SpecParser.md` SP5 |
| 相关文档 | `04-数据模型.md` §2.1、`03/SpecParser.md` §4 |

## 背景

系统需要一个"Spec 指纹"来回答一个问题：**用户这次上传的文档，和已有的是不是同一份？**

用途有二：

| 用途 | 说明 |
| :--- | :--- |
| **去重** | 同一份文档重复上传时复用既有解析结果，不重复落库 |
| **变更检测（S2）** | 文档变更后，标记既有用例可能失效并提醒用户 |

最直接的方案是对文档原始内容计算哈希。**但该方案会产生大量伪变更**，原因有二——见下。

## 决策

**指纹 = `sha256(规范化后的文档)`**，计算前依次执行两步转换：

**① 先展开 `$ref`。**

**② 再规范化**：

| 步骤 | 消除的差异 |
| :--- | :--- |
| 解析为程序结构 | 缩进、换行、注释等文本格式差异 |
| 按 key 递归排序 | key 顺序差异 |
| 统一为紧凑序列化 | 空白差异 |
| **保留数组顺序** | 数组顺序在 OpenAPI 中**有语义**（`enum` 允许值、`required` 列表），不可排序 |
| 数值规范化 | `1` 与 `1.0` 的差异 |

## 被否决的备选

### 备选一：直接哈希原始字节

最简单，也最容易误判。

**否决理由——两类伪变更：**

**格式差异。** YAML 对同一语义有多种写法：

```yaml
# 写法 A
properties:
  name: {type: string}

# 写法 B —— 语义完全相同
properties:
    name:
        type: string
```

同一份文档，换个编辑器保存、调整缩进、加一行注释，**字节哈希就变了**。

**`$ref` 写法差异。**

```yaml
# 写法 A：用引用
schema: {$ref: '#/components/schemas/User'}
components:
  schemas:
    User: {type: object, ...}

# 写法 B：内联展开 —— 语义完全相同
schema: {type: object, ...}
```

两种写法**语义等价**，但在展开前计算会得到不同指纹。

**为什么伪变更的后果严重：**

S2 的功能是"文档变了 → 提醒用户旧用例可能失效"。若因格式差异误报，用户会收到大量无意义的提醒。

> **真正的危害不是打扰，而是用户从此不再相信这个提醒**——真正发生变更时也被一并忽略。

### 备选二：用文件名 + 大小判断

**否决理由：**

- 文件名可随意更改，大小相同的不同内容极为常见
- 完全无法反映语义
- 与"变更检测"的需求不匹配

### 备选三：不做去重，每次上传都新建 Spec

**否决理由：**

- S2 的变更检测需要"同一份文档"这个概念作为基础，否则无法判断"变没变"
- 重复解析浪费计算
- 历史 Run 与 Spec 的对应关系会变得混乱

## 后果

**正面：**

- 指纹对**语义变更**敏感、对**格式变更**不敏感，这正是所需的语义
- Spec 因此成为**不可变实体**：内容变了就是另一行记录，不会出现"同一 spec_id 的 server 列表变了"的情况
- 该不可变性使 `specs.declared_targets` 等派生字段可以安全地存储在该表上（`04` §2.1）

**代价：**

- 指纹计算依赖解释器的序列化确定性（字典序、数值格式），实现时需固定这些行为
- 在 `$ref` 展开**之后**计算，意味着指纹依赖于解析器的行为——更换解析库需重新验证
- 展开循环引用时有深度上限（`03/SpecParser.md` SP1），超限处保留字面量，因此**极端递归结构的指纹可能对写法敏感**。这是已知的、可接受的精度损失
