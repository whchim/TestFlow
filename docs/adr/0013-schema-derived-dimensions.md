# ADR-0013：用 schema 派生测试维度，LLM 只负责取值

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `03-模块详细设计/TestCaseGen.md` TG1 |
| 相关文档 | `03/TestCaseGen.md` §2、ADR-0014、ADR-0026 |

## 背景

`TestCaseGen` 的职责是：给定一个接口的 schema，产出测试用例。

最直接的做法是把 schema 交给 LLM，要求它输出用例。

**该做法有一个结构性的失败模式：**

接口文档中写着某个字段"最长 20 个字符"。LLM 生成了 8 条用例，看起来都很合理——**但没有一条测试"超过 20 个字符会怎样"**。

**问题在于：无法发现这个遗漏。** 没有可对照的清单，评审者只能说"这几条看着都挺好"。

这不是提示词写得不好导致的，而是**任务定义本身的问题**：把"决定测什么"和"生成具体内容"两件事交给了同一个不可控的组件。

## 决策

**把生成拆为两个阶段，并明确各自的归属：**

| 阶段 | 归属 | 产出 |
| :--- | :--- | :--- |
| **阶段 A** | **纯算法（无 LLM）** | 测试维度清单（该测哪些方面） |
| **阶段 B** | LLM | 每个维度的具体取值、断言、用例名 |

阶段 A 从 schema 确定性派生七类维度（`required_missing`、`type_mismatch`、`constraint_violation`、`boundary`、`not_found`、`auth_missing`、`value_valid`）。

阶段 B 中，LLM 收到的是"**给定的维度 + 相关 schema 片段**"，只需为该维度填充具体值——**不需要自行判断该测什么**。

**允许 LLM 补充维度**，但补充的维度必须标记 `derived_from: inferred`，且不计入覆盖率的分母、数量设上限。

## 被否决的备选

### 备选一：让 LLM 自由生成用例

**否决理由（本决策的核心）：**

| 问题 | 后果 |
| :--- | :--- |
| **无法发现遗漏** | 没有对照清单，缺失的维度不可见 |
| **无法评估质量** | 只能比对"用例条数"，而条数可以被模型多写废话刷高 |
| **约束依赖模型记忆** | 模型需要"发现"schema 中的约束，而它可能忽略 |

### 备选二：让 LLM 自由生成，再用规则检查覆盖率

看似结合了两者。

**否决理由：**

- **检查的依据是什么？** 若依据是"实际生成结果"，则检查退化为自证；若依据是"schema 派生的清单"，则等于已经实现了阶段 A——不如让它前置，从而**同时约束生成过程**
- 生成后再检查意味着**发现问题时为时已晚**，只能整体重试，成本更高

### 备选三：完全由算法生成，不用 LLM

**否决理由：**

- 算法可以为 `required_missing` 生成"邮箱字段留空"，但**生成不出符合业务语义的具体值**（合法的邮箱地址、角色枚举中合理的那一个）
- 断言中"期望返回什么错误码"这类判断，缺少 schema 声明时只能靠语义推断
- 放弃 LLM 等于放弃了本项目的核心价值

## 后果

**正面：**

| 收益 | 说明 |
| :--- | :--- |
| **可校验** | 维度清单确定，缺哪个一目了然 |
| **抗幻觉** | 模型不需要"发现"约束，约束来自 schema 而非模型记忆 |
| **可评估** | 质量指标基于**维度覆盖**而非用例条数，无法被凑数稀释 |

**代价：**

- 需要实现并维护阶段 A 的派生算法（这是一段纯函数，可独立单测——实际上它是 `TestCaseGen` 中最值得测的部分）
- LLM 的发挥空间被限定，额外的业务语义维度只能通过 $inferred$ 通道补充

**必须注意的局限（与 ADR-0026 直接相关）：**

覆盖率指标为 `已生成维度 ÷ 阶段 A 派生的维度清单`。

**分母是平台自己算的，因此该指标是自我参照的**：若阶段 A 漏掉了某类约束，分母中就不含它，生成结果中也不含它，覆盖率**仍显示 100%**。

因此本决策**不能单独保证覆盖完备性**，必须配合人工标注的独立基准（ADR-0026）。
