# ADR-0003：确定性任务不引入 LLM

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `02-架构设计.md` D3、D5 |
| 相关文档 | `03/SpecParser.md` §1.1、`03/ReportAgent.md` §1.1 |

## 背景

系统中有两个环节**看起来**需要"理解语义"，因而适合交给 LLM：

| 环节 | 表面理由 |
| :--- | :--- |
| **解析 OpenAPI 文档** | 文档是人写的，格式千变万化 |
| **生成测试报告** | 报告需要组织成一段给人看的文字 |

但两者实质上都是**确定性问题**：给定输入，正确答案唯一，且可用代码精确计算。

本项目在多个环节使用 LLM（用例生成、归因兜底），因此需要一条明确的边界规则来决定"哪些环节不用"。

## 决策

**能用确定性算法解决的任务，不引入 LLM。**

具体地：

| 环节 | 实现方式 |
| :--- | :--- |
| Spec 解析 | `prance` + `openapi-spec-validator`，纯算法 |
| 报告生成 | Jinja2 模板渲染确定性聚合结果 |
| 测试维度派生 | 纯算法（`03/TestCaseGen.md` 阶段 A） |

**LLM 的使用范围限定为三处**：用例生成（`TestCaseGen` 阶段 B）、归因兜底（`LogAnalyzer`）、以及 V1.0 的报告结论摘要。前两处都建立在确定性算法**已经划定范围**的基础上。

## 被否决的备选

### 备选一：用 LLM 解析 OpenAPI 文档

理由看起来合理：LLM 对格式差异的容忍度更高，可能处理更"脏"的文档。

**否决理由：**

- **违反可承诺的指标**。PRD M3 要求 Spec 解析成功率 ≥ 99%。LLM 无法承诺这一确定性——它今天解析正确，明天可能漏掉一个字段
- **幻觉会污染下游**。模型可能"补全"文档中不存在的字段。该错误会经用例生成传递到执行，最终表现为"测试失败"，而排查方向完全不会指向解析层
- **不可复现**。同一份文档两次解析结果不同，那么"同一个 Spec 的两次测试结果为何不同"将无法回答

对格式较脏的文档，正确的应对是**增强解析器的容错并显式标注降级**（`03/SpecParser.md` SP4 区分"文档缺陷"与"信息不全"），而不是引入一个不可控的组件。

### 备选二：用 LLM 生成报告叙述

**否决理由：**

- **可复现性**。报告会被引用（评审材料、问题工单）。同一份数据两次生成的文字不同，用户无法确认"我上次看到的是不是这个"
- **成本**。违反 M8 的预算约束，且这笔支出没有换来新信息——数据层的聚合是确定的
- **可信度**。PRD §1.2 的痛点"AI 生成内容不可控"同样适用于报告。报告是给人做决策用的，数字必须确定

**部分保留**：V1.0 可在模板骨架之上增加一段 LLM 生成的"结论摘要"，但**必须是可单独关闭的附加段落，且不参与任何数字的产生**。

## 后果

**正面：**

- 解析层成为**纯函数**，可缓存、幂等、独立单测（`06` §3 的 N1 是唯一真正可重放的节点）
- 报告数字确定、可复现，可被引用
- 减少了 LLM 调用面，直接降低成本与不确定性

**代价：**

- 解析器对"脏文档"的容忍度低于 LLM，需要显式设计降级路径（`03/SpecParser.md` §7）
- 报告在"可读性"上做出让步——V1.0 的摘要增强属于补偿措施

**边界说明：**

- 若某类任务既需要语义理解、又需要确定性，则**优先改变任务定义使其确定**（例如 `TestCaseGen` 把"生成用例"拆为"派生维度（确定）+ 填充取值（LLM）"，见 ADR-0013），而不是接受 LLM 的不确定性
