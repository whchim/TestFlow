# ADR-0008：回调唤醒：内部 HTTP 端点 + 查库判定完成

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `06-Agent编排.md` G7、G8、G9 |
| 相关文档 | `06-Agent编排.md` §6、`05-API契约.md` §4.7 |

## 背景

IP-2 中断挂起后（ADR-0007），图需要知道"所有测试任务都执行完了"，才能继续推进。

问题在于**如何判定"全部完成"**：

- 一个 Run 可能分发数百个 Celery 任务
- 任务由不同 Worker 进程执行，完成顺序不可预测
- 通知机制本身可能丢消息、重复投递、乱序到达

## 决策

分四个部分：

**① 唤醒路径**：每个任务完成后，Worker 调用 Gateway 的内部端点 `POST /internal/runs/{run_id}/wake`。

**② 完成判定**：该端点**查询 PostgreSQL** 统计已到终态的用例数，与预期总数比对。相等才投递推进指令。

**③ 并发保护**：per-Run 分布式锁（Redis `SET NX EX`），保证同一 Run 的图推进串行。

**④ 兜底轮询**：Celery Beat 定期扫描 `AWAITING_RESULTS` 且超时的 Run，标记未完成用例并按部分失败推进。

## 被否决的备选

### 备选一：由"最后一个完成的任务"触发唤醒

最朴素的做法，也是第一直觉。

**否决理由：竞态。**

"最后一个"这个判断本身不安全：

| 竞态 | 后果 |
| :--- | :--- |
| 两个任务同时完成、同时认为自己是最后一个 | 唤醒两次 |
| 两个任务同时完成、同时认为对方才是最后一个 | 都不唤醒，**图永久停滞** |

判定"谁是最后一个"需要一次原子性的计数操作，而如果已经做了这次计数，就等价于本决策的 ②——**不如让每个任务都通知，由接收方统一判定**。

### 备选二：用 Redis 发布/订阅替代 HTTP 端点

更轻量，不需要暴露端口。

**否决理由：**

- **无失败可见性**。发布/订阅是"发出即忘"，发送方不知道接收方是否收到，无法重试
- **需要常驻消费者循环**。Orchestrator 必须持续订阅，而 HTTP 端点由 Gateway 被动接收即可
- **排查困难**。无法手动重放一次唤醒来定位问题

而 HTTP 有状态码，失败可重试、可观测、可手动复现，这对排查"图为什么不推进"这类问题价值很高。

### 备选三：取消推送，由 Orchestrator 纯轮询数据库

**否决理由：**

- 轮询间隔与响应延迟直接耦合——间隔短则空转浪费，间隔长则流程变慢
- 该方案的合理部分已被纳入本决策的 ④：**轮询只作为兜底**，不作为主路径

## 后果

**正面：**

- 通知丢失、重复、乱序**均不影响正确性**——只要最终有一次到达且数据库状态完整，图必然推进
- 判定依据是唯一事实来源（PostgreSQL），不受通知内容影响（与 ADR-0009 一致）
- 唤醒端点可手动调用，便于排查

**代价：**

- 每个用例产生一次多余的 HTTP 调用（N 次而非 1 次）。可优化为"每完成 K 个或每 T 秒聚合一次"，但**先做对，再做快**
- 需要维护 per-Run 分布式锁

**实现约束：**

| 约束 | 理由 |
| :--- | :--- |
| 唤醒端点必须**幂等** | 重复调用不得产生副作用 |
| 锁必须设 TTL 且**不自动续期** | 持锁进程崩溃后，下一次唤醒能接管。宁可偶发重复推进（幂等保证安全），不可永久死锁 |
| 端点必须验证"全部到终态" | 部分完成时直接返回，不做任何操作 |
| 结果**先落库、后唤醒** | 顺序颠倒会导致图在结果未持久化时被唤醒（ADR-0009） |
