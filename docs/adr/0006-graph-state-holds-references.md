# ADR-0006：GraphState 只存引用不存大对象

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `06-Agent编排.md` G3 |
| 相关文档 | `06-Agent编排.md` §2、`04-数据模型.md` §6 |

## 背景

系统是一个状态机：LangGraph 每推进一个节点就把当前状态序列化进 Redis Checkpoint，以支撑中断恢复（PRD F8）。

一个 Run 的规模（PRD §5 假设）：
- 单 Spec ≤ 200 个 Operation
- 单 Run ≤ 2000 条测试用例

若状态对象中直接持有这些实体的**完整内容**（用例的请求体、断言列表、执行结果、响应体），该对象会达到数 MB 量级，而它**每一步都要全量读写一次**。

此外，实体内容同时存在于 PostgreSQL 中，直接放进状态会产生**第二个事实来源**。

## 决策

**GraphState 只存轻量引用与聚合值；实体（Spec、Operation、Case、结果、日志）只存于 PostgreSQL。**

| 状态中保留 | 状态中不保留 |
| :--- | :--- |
| 各类实体的 ID 列表 | 实体的字段内容 |
| 聚合计数（含明确标注为"缓存"的） | 响应体、日志正文、Spec 原文 |
| 节点级的失败与重试记录 | — |

**唯一的例外**是 `node_failures` 与 `retry_counts`——它们描述"本次推进过程"的临时状况，不落库（`04` §6）。

## 被否决的备选

### 备选一：状态中直接持有实体

实现上更直接——节点之间传递完整对象，不需要额外的数据库读取。

**否决理由：**

- **Checkpoint 体积随用例数线性增长**。2000 条用例的完整内容可达数 MB，而每次节点转换都要序列化、写入 Redis、再读回
- **产生第二事实来源**。实体在 PostgreSQL 与 Redis 中同时存在，一致性问题立即出现（与 ADR-0009 的原则冲突）
- **症状是渐进劣化**，不存在"突然坏掉"的时刻，因此难以察觉

### 备选二：状态中持有实体，但为大对象设置大小上限

**否决理由：**

上限无法可靠设定——用例的请求体大小由被测 API 的契约决定，差异可达数个数量级。设定上限后仍需一套截断与降级逻辑，复杂度接近正确方案。

## 后果

**正面：**

- Checkpoint 体积与用例数**基本解耦**（只随数量线性增长的是 ID 列表）
- 状态转换的成本可预测
- 实体只有一个存放处，与 ADR-0009 一致

**代价：**

- 节点需要额外查询数据库来获取实体内容
- 节点实现必须遵守"先查后算"的模式，不能假设状态中已有数据

**关联影响：**

- `orchestrator` 进程的内存占用因此可控（`10-部署运维.md` §9）——若状态中持有实体，该数字需要上调一个量级
- `04` DM5 的**状态计数仅作展示缓存**、权威判定一律查库，是同一原则在计数字段上的体现
