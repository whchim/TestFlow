# ADR-0026：覆盖率指标必须有人工独立基准

| 字段 | 值 |
| :--- | :--- |
| 状态 | 已接受 |
| 日期 | 2026-10-13 |
| 来源决策 | `09-测试策略.md` TS5 |
| 相关文档 | `09-测试策略.md` §5.2、`03/TestCaseGen.md` §5.2 |

## 背景

`TestCaseGen` 把生成拆为两阶段（ADR-0013）：

1. **阶段 A（纯算法）**：从 schema 派生"该测哪些维度"
2. **阶段 B（LLM）**：为每个维度生成具体取值与断言

由此产生一个自然的覆盖率指标：

```
维度覆盖率 = 实际生成的维度 ÷ 阶段 A 派生的维度清单
```

**该指标看起来完备——100% 即代表全部覆盖。**

## 问题：分母是平台自己算的

**分母（"阶段 A 派生的维度清单"）由平台自己的算法产生。**

假设阶段 A 的派生算法漏掉了某一类约束。例如**字符串最大长度**（`maxLength`）——它藏在 `type: string` 的兄弟字段中，比数值范围（`minimum` / `maximum`）更不显眼：

```
分母中不含 boundary:name 这一项
                ↓
生成结果中自然也不含
                ↓
覆盖率 = 100%        ← 显示完全覆盖
```

**指标显示完美，而实际覆盖是缺失的。**

**没有任何自动检查能发现这一点**——因为错误位于分母本身。

## 决策

**覆盖率指标必须配合一个人工标注的独立基准，不能单独依赖自动计算。**

覆盖率的验证分两层：

| 层次 | 验证内容 | 基准来源 |
| :--- | :--- | :--- |
| **第一层：派生正确性** | 该测的维度是否都被派生出来了 | **人工标注的维度清单** |
| **第二层：生成完整性** | 派生出的维度是否都生成了用例 | 阶段 A 的输出（自动） |

**第一层只能在人工标注的数据集上完成**，因此 Golden Set 必须包含人工撰写的"期望维度清单"。

## 被否决的备选

### 备选一：只依赖自动指标

**否决理由：**

见上述"分母是平台自己算的"。该指标**永远显示 100%**，无论派生算法有多少盲区。

### 备选二：用第三方库推导维度作为交叉验证

例如用成熟的 JSON Schema 处理库枚举约束，与自研的派生算法比对。

**部分有效，但不能替代人工基准：**

| 问题 | 说明 |
| :--- | :--- |
| **覆盖范围不同** | 第三方库只处理 schema 语法层，而我们的维度还包括 `not_found`（路径参数）、`auth_missing` 等语义层维度 |
| **库的完整性同样需要验证** | 若库漏了某类约束，交叉验证会同时漏掉——**回到同一个问题** |
| **基准仍非独立** | 选择哪个库、相信它的哪个输出，仍是我们的判断 |

可以作为**辅助手段**（发现自研算法与成熟库的差异），但**不能作为独立性来源**。

### 备选三：先上线，发现问题后再补基准

**否决理由：**

- 没有基准，就**无法发现问题**——这正是本决策要解决的困境
- 基准的价值随时间递减：越晚建立，已有数据的可信度越难回溯评估

## 这条原则的推广

> **任何以自己输出为分母的指标，都需要一个外部基准来校准。**

本项目中的另一处应用是——**M4（归因认可率）**：

```
归因认可率 = 人工认可数 ÷ 平台判定为失败的用例数
```

**分母是"平台判定为失败的用例"**。如果"失败"这个判定本身有问题（例如 ADR-0015 的三态被合并，导致某些"无法求值"被错误计入），那么认可率再高也没有意义。

## 后果

**正面：**

- 覆盖率指标获得独立于自身算法的校准点
- Golden Set 的定位被明确：**它不是用来测 AI 的，而是用来测我们自己的派生算法的**

**代价：**

- 需要人工标注 10 个接口的期望维度清单（`09` §5.3 给出了选型原则，确保覆盖容易出错的接口特征）
- 人工标注会随维度分类法的演进而需要更新

**Golden Set 的选型要求（关键）：**

10 个接口的选择不是随意的，需覆盖**会让算法出错的特征**。其中两个是刻意挑选的边界：

| # | 特征 | 检验的能力 |
| :--- | :--- | :--- |
| 5 | 含 `minLength` / `maxLength` | **最容易漏的一类**——只测数值边界会误以为边界维度已覆盖 |
| 9 | 无参数、无请求体、无 4xx 声明 | 验证 `TG5` 的纯规则路径**不应产生任何 LLM 调用** |
