## 1. 模块定位

| | 内容 |
| :--- | :--- |
| **输入** | 失败的 `case_results` 记录（状态码、响应体、`error_kind`）+ 对应 `cases` 的断言与置信度 + 该 Operation 的 spec 片段 |
| **输出** | 每条失败用例一条归因记录，落库至 `attributions`（`04` §2.7） |
| **LLM** | ✅ 使用（**仅兜底路径**，`qwen3.5-plus`） |
| **触发条件** | 仅对 `status ∈ {failed, timeout, error}` 的用例执行。**通过的用例不产生归因** |

### 1.1 职责边界

**做**：回答"**这条用例为什么失败**"，并把答案收敛到有限的类别集合中，使下游可按类别聚合、按类别统计、按类别追踪趋势。

**不做**：

- 不修改测试结论——`case_results.status` 是事实，归因只是解释，**不能反过来改变它**
- 不修复任何东西（不重试用例、不调整断言）
- 不做趋势分析或告警（`ReportAgent` 与 V1.0 的监控）
- 不判断"这个失败重不重要"

### 1.2 它服务的用户问题

PRD 场景 S3 定义的诉求是：**知道"是参数问题还是服务问题"**。

因此归因的第一性要求不是"分类得细"，而是**分类结果能直接指向排查方向**。一个判得很准但用户看完仍不知道下一步做什么的类别体系，是失败的。§3 的类别表因此显式包含"责任归属"与"排查方向"两列。

## 2. 核心策略：规则优先，LLM 兜底

### 2.1 主张

**能用规则判定的，绝不调用 LLM。**

这与 `TestCaseGen` 的 TG1 是同一思想的两面：那边是"用确定性算法界定 LLM 的发挥范围"，这边是"用确定性规则缩小 LLM 的调用面"。

规则优先的四个理由：

| 理由 | 说明 |
| :--- | :--- |
| **确定性** | 同一条失败日志永远得到同一归因。这是可测试的前提——LLM 归因无法写断言测试 |
| **可解释** | 能明确说出"命中了第 7 条规则"，而不是"模型认为"。归因结论会被用来排查生产问题，不能是黑盒 |
| **零成本零延迟** | 直接压降 M8 的成本预算 |
| **可回归** | 规则库是代码，可评审、可版本化、可单测（M6） |

**LLM 只处理规则覆盖不到的模糊地带**——主要是"HTTP 层看起来正常但语义不对"这类需要理解业务含义的场景。

### 2.2 规则覆盖率：本模块的第一指标

**规则覆盖率 = 被规则确定性归因的失败数 / 总失败数**

这个指标必须作为一等公民被采集和展示，理由有三：

1. **它直接决定成本。** `02` §5.4 的成本测算（≈ ¥0.37 / Run）建立在"仅 20% 的失败需要 LLM"这一假设上。若规则覆盖率远低于预期，M8 会被击穿——而这个偏离在成本报表上只表现为"数字变大了"，看不出根因
2. **它是规则库质量的唯一度量。** 没有它，"要不要补规则"只能凭感觉
3. **它是 V1.0 引入检索的决策依据。** 见 §10

因此 `attributions.method`（`04` §2.7）字段不是可选的元数据，而是这个指标的分母来源。

> **反面情形**：若规则覆盖率长期偏低（如 < 50%），正确的反应是**补规则**，而不是"反正 LLM 能判"就放任。放任的结果是成本随失败数线性增长，且归因质量从确定性滑向概率性。

## 3. 归因类别体系

本节定义 `attributions.category` 的**权威枚举**，解答 `04-数据模型.md` §7 的 Q2。

### 3.1 类别表

| 类别 | 责任归属 | 典型触发 | 排查方向 |
| :--- | :--- | :--- | :--- |
| `request_invalid` | **请求侧** | 400 / 422 | 看请求参数是否符合接口契约——**很可能是用例本身写错了** |
| `auth_error` | 凭证侧 | 401 / 403 | 检查凭证是否有效、是否过期、权限是否足够 |
| `resource_not_found` | **测试资产侧** | 404 | 依赖的资源不存在——**通常是测试数据未准备，而非服务缺陷** |
| `conflict` | 测试资产侧 | 409 | 状态冲突，常见于用例重复执行或数据未清理 |
| `rate_limited` | 环境侧 | 429 | 被限流；检查并发配置或目标服务的配额 |
| `server_error` | **服务侧** | 5xx | 被测服务异常——**这是最需要报告的类别** |
| `response_schema_mismatch` | **服务侧** | 任意 | 响应结构与 spec 声明不符（字段缺失、类型错误） |
| `assertion_mismatch` | **服务侧或用例侧** | 2xx | HTTP 通过但内容不符。**归属需人工判断**，见 §3.3 |
| `network_error` | 环境侧 | — | 连接失败、DNS、TLS、超时——请求未到达或未返回 |
| `blocked_by_policy` | **平台策略侧** | `error_kind = 'guardrail_denied'` | 请求被平台安全策略拦截——**检查 Guardrail 白名单 / 内网例外配置**（`Guardrail.md` §8.2）。注意其排查方向与 `network_error` 完全不同 |
| `unknown` | — | — | 无法归类。**是缺陷信号，不是正常输出**，见 §5.4 |

### 3.2 为什么是这十一类

- **覆盖 HTTP 语义的主要分支**：2xx 正常 / 4xx 各类 / 5xx / 传输层失败
- **责任归属可分辨**：用户能立刻知道该去查自己的用例、测试数据、被测服务、还是平台配置
- **互斥**：每个失败至多命中一个一级类别（规则按优先级短路，§4.2）
- **不引入"重要性"维度**：优先级/严重程度是报告层的聚合逻辑（`ReportAgent`），不是归因的职责。混在一起会让两者都无法单独演进

**`blocked_by_policy` 是后补的第 11 类**，由 `Guardrail.md` §8 反向暴露：被 Guardrail 拒绝的请求没有产生任何测试结论，但用户**必须被告知**。最初考虑复用到 `network_error`，但二者的排查方向完全不同——一个去查网络连通性，一个去查白名单配置。把策略拦截伪装成网络错误，用户会朝错误的方向排查很久。这个缺口说明：**类别体系的完整性无法一次设计到位，需要下游模块的反馈来补**。

### 3.3 `assertion_mismatch` 的固有歧义

这个类别天然是二义的：HTTP 2xx 但内容断言失败，可能是

- **服务行为与 spec 不符** → 真缺陷
- **用例的断言本身就写错了** → 用例缺陷

规则无法区分，需要语义判断，因此：

1. 它**必然**走 LLM 兜底路径（或其他需要判断的类别）
2. 归因时**必须参考用例的 `confidence`**（`04` §2.5）——见 §6
3. 输出为 `assertion_mismatch` 时，归因置信度**最高只能到 `medium`**，除非有额外证据

> 不为了让类别表"看起来干净"而拆成 `service_mismatch` 与 `test_assertion_error` 两类。这个区分（若需要）应由证据得出，而不是由模型猜测——猜出来的分类和 `unknown` 一样不可用。

### 3.4 `unknown` 是缺陷信号

`unknown` 的占比需要被**主动监控**。

它不是"正常的兜底输出"，而是"规则覆盖不到、且 LLM 也判不出"的信号。占比升高意味着：规则库有缺口，或出现了新的失败模式。把它当作正常值会让整个归因体系在无人察觉的情况下退化。

## 4. 规则库设计

### 4.1 规则的形态

规则是**对持久化记录的确定性谓词**，可用一条 SQL `CASE` 表达式或一段 Python 函数表达：

```python
class AttributionRule(Protocol):
    rule_ref: str  # 稳定标识，落库供追溯
    priority: int

    def match(self, ctx: FailureContext) -> bool: ...
    def category(self, ctx: FailureContext) -> AttributionCategory: ...
```

### 4.2 按优先级短路

规则**有序**，首个命中即返回（`priority` 升序）——因此规则集天然是"从特殊到一般"排列：

| 优先级段 | 规则族 | 示例 |
| :--- | :--- | :--- |
| 1–99 | **传输层**（最高优先级） | `error_kind == "dns_failure"` → `network_error`；连接被拒 → `network_error` |
| 100–199 | **具体状态码** | `429` → `rate_limited`；`409` → `conflict` |
| 200–299 | **状态码段 + 响应体特征** | `4xx` 且响应体匹配校验错误结构 → `request_invalid` |
| 300–399 | **状态码段**（宽泛） | `5xx` → `server_error`；`404` → `resource_not_found` |
| 400–499 | **断言级** | 2xx 且 `schema_valid` 断言失败 → `response_schema_mismatch` |

传输层规则优先级最高的理由：**连请求都没发出去（或没收到响应）时，任何基于状态码的判断都不适用**。

### 4.3 规则库的维护

- **每条规则必须可单测**：给定一条构造的失败记录，断言归因结果（M6 覆盖率要求）
- **规则的增补由人工纠错驱动**：见 §8.2
- **规则删除需谨慎**：删掉一条规则可能让一批归因从确定性掉到 LLM 路径，成本与质量双降。删除前应确认无历史数据依赖它

## 5. LLM 兜底设计

### 5.1 触发条件

仅当**所有规则均未命中**时调用。触发次数应被记录，作为 §2.2 指标的观测手段。

### 5.2 输入构造

| 输入项 | 来源 | 说明 |
| :--- | :--- | :--- |
| HTTP 状态码 | `case_results.http_status` | |
| 响应体 | `case_results.response_body` | **截断后的**；若 `truncated = true` 必须显式告知模型（`04` DM6） |
| 断言失败详情 | `cases.assertions` + 求值结果 | 哪条断言、期望什么、实际什么 |
| 期望响应结构 | `operations.responses_schema` | 让模型能判断"是否与 spec 不符" |
| 用例置信度 | `cases.confidence` | 见 §6 |
| 传输层错误 | `case_results.error_kind` | |

**告知截断事实不可省**（`04` DM6 的同一条原则）：模型不知道响应体被截断时，会把"字段在截断部分之后"误判为"字段缺失"，得出 `response_schema_mismatch` 的错误结论。

### 5.3 输出约束

**LA2：类别是封闭枚举，模型只能在其中选择。**

用 JSON Schema 的 `enum` 约束 `category` 字段（`02` §5.2 的结构化输出机制），**禁止模型自由生成类别名**。

理由：自由生成的类别会迅速漂移成同义词（`server_error` / `backend_error` / `internal_error`），使按类别聚合的统计彻底失效，且这些脏数据会沉淀进 `attributions` 表无法回收。

```python
class FallbackAttribution(BaseModel):
    category: AttributionCategory  # 封闭 enum
    confidence: Literal["high", "medium", "low"]
    evidence: list[str]  # 关键信号，逐条列出
    reasoning: str  # 判定理由，供人工复核
```

若模型认为**无法归入任何类别**，允许其返回 `unknown` 并说明理由——必须保留这条路径，否则模型会被迫在都不合适时强行选一个（与 `TestCaseGen` §6.2 的"承认不知道"是同一设计）。

### 5.4 `unknown` 不重试

| 情况 | 处理 |
| :--- | :--- |
| LLM **调用失败**（网络、限流、超时） | 重试 1 次（与其他模块一致的上限） |
| LLM 成功返回但结论为 `unknown` | **不重试**，直接落库 |

理由：`unknown` 意味着"信息不足以判断"，重试同一输入只会得到同样的结果，纯属烧钱。它应该作为 §3.4 的监控信号进入人工视野，而不是靠重试碰运气。

## 6. 与 TestCaseGen 的交叉影响

这是本模块与 `TestCaseGen` 之间的一个非平凡耦合点，**实现时必须处理**：

归因的结论依赖用例本身的可靠性。一个 `assertion_mismatch` 的失败，其根因可能是：

- 服务行为确实与 spec 不符 → `assertion_mismatch` 成立，是**服务缺陷**
- 该用例的断言来自推断（`derived_from: inferred`，`TestCaseGen` §3.1）且本身就是错的 → 是**用例缺陷**

而 `TestCaseGen` §7 已经把这一信息编码在 `cases.confidence` 中。因此：

| 用例置信度 | `assertion_mismatch` 的归因置信度上限 | 附加提示 |
| :--- | :--- | :--- |
| `high`（断言全部来自 spec） | `medium` | — |
| `low`（含推断断言） | `low` | 显式提示"该用例的断言为推断所得，失败可能是用例本身的问题" |

**LA3：归因必须读取用例置信度，不得无视。**

若不做这个耦合，低置信度用例的失败会与服务缺陷**混在同一类别里**，污染 `assertion_mismatch` 的统计——用户在报告里看到"服务缺陷 N 条"，其中一部分其实是自己用例的问题。这会让整个归因结果失去可信度。

## 7. 输出契约

映射到 `attributions` 表（`04` §2.7）：

| 字段 | 规则路径 | LLM 路径 |
| :--- | :--- | :--- |
| `category` | 规则判定 | 模型从封闭枚举中选择 |
| `method` | `"rule"` | `"llm"` |
| `rule_ref` | 命中的规则标识 | `NULL` |
| `llm_model` | `NULL` | `qwen3.5-plus` |
| `confidence` | 按规则族的确定性给出（见下） | 模型输出，受 §6 上限约束 |
| `evidence` | `{"rule_ref": ..., "http_status": ..., "error_kind": ...}` | `{"signals": [...], "reasoning": ..., "truncated": bool}` |

**规则路径的置信度**：`high` 当且仅当规则基于**强信号**（具体状态码、传输层错误）；基于响应体特征匹配的规则给 `medium`。

## 8. 置信度与人工纠错

### 8.1 人工纠错（PRD §4.2）

`attributions.human_verdict` 取 `agree` / `disagree`（`04` §2.7）。人可在界面上对任一条归因表态。

### 8.2 纠错必须记录正确类别

**LA6：人工表态为 `disagree` 时，必须同时记录正确的类别。**

这是规则库能否自我改进的关键。若只记录"同意/不同意"：

- 你知道判错了 100 条，但**不知道错在哪里**
- 无法回答"该补哪条规则"，规则改进只能靠猜

若记录正确类别，就能得到一份**直接可用的规则 backlog**：

```
人工判为 server_error，但规则未命中（走了 LLM / unknown）：37 条
  → 检查这 37 条的共同特征，提炼新规则
```

> **对 `04-数据模型.md` 的修订需求**：`attributions` 表需增加 `human_category TEXT` 列（可为空，仅当 `human_verdict = 'disagree'` 时填写）。见该文档 v0.3。

## 9. 成本控制落点

`02` §5.4 的成本测算假设"100 个失败 Case 中仅 20% 需要 LLM 调用"（即规则覆盖 80%）。本模块的实现必须让这个假设可验证：

| 手段 | 落点 |
| :--- | :--- |
| 提高规则覆盖率 | §4 的规则库；这是降低成本最有效的手段，且**同时提升质量** |
| 单次调用输入受控 | 响应体已截断（`04` DM6）；spec 片段按需裁剪（`04` §2.10） |
| 上下文缓存 | `enable_thinking` 关闭（`02` §5.3）——兜底归因无需深度推理，开的只是 token 成本 |
| 不重试 `unknown` | §5.4 |
| 指标可观测 | 记录规则覆盖率与 LLM 调用次数，随报告一并产出 |

**规则覆盖率必须随报告输出**，而不是埋在日志里。理由是它同时是成本和质量的先行指标——用户看到它下滑时，问题还没体现在账单上。

## 10. V1.0 演进：为什么不现在引入检索

`02` §3.1 把向量库与 BM25 排在 V1.0。本模块是它们唯一的消费方，这里说明这个排序的依据。

**RAG 归因的价值是"这个错误以前出现过，当时的结论是 X"。也就是说，它复用已知，不解决未知。**

这个性质决定了：

| 阶段 | 主要失败模式 | 有效手段 |
| :--- | :--- | :--- |
| **MVP（冷启动）** | 绝大多数失败是**首次遇到** | 规则（确定）+ LLM 兜底（理解）。检索库里没有可复用的历史，检索结果不可信，反而引入噪声 |
| **V1.0（有积累）** | 相当比例的失败是**已知模式的重复** | 检索历史归因 + 人工纠错结论，此时检索才真正降低 LLM 调用量并提升一致性 |

因此顺序是：**先让规则和 LLM 跑起来 → 积累归因数据与人工纠错 → 检索才有物料**。若把检索前置，MVP 会花大量成本维护一个检索质量无法评估的组件。

V1.0 的检索引入时机与验证方式：当**历史归因样本量足够**且**规则覆盖率进入平台期**（补规则不再能提升覆盖）时，用 Golden Set（`04` §4 / `TestCaseGen` §9）验证混合检索是否真的降低了 LLM 调用量且未降低准确率。

## 11. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **LA1** | 规则优先，LLM 兜底 | 能用规则判定的绝不调 LLM；规则覆盖率作为一等指标采集 |
| **LA2** | 类别是封闭枚举 | LLM 只能在预定义类别中选择，禁止自由生成类别名 |
| **LA3** | 归因读取用例置信度 | 低置信度用例的 `assertion_mismatch` 必须降级并提示，避免污染服务缺陷统计 |
| **LA4** | 通过的用例不产生归因 | 归因只解释失败，不改写测试结论 |
| **LA5** | 不引入检索（V1.0） | RAG 复用已知而非解决未知；冷启动阶段无物料可检索 |
| **LA6** | 人工纠错记录正确类别 | 只记"同意/不同意"无法生成规则 backlog |
| **LA7** | `unknown` 不重试且需监控 | 重试对信息不足无效；占比升高是规则库缺口的信号 |
