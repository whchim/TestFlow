## 1. 定位

| | 内容 |
| :--- | :--- |
| **输入** | 该 Run 的 `case_results` + `attributions` + `cases`（维度与置信度）+ 执行完整性信息 |
| **输出** | `reports` 一行：`content`（结构化聚合）+ `rendered`（Markdown 快照） |
| **LLM** | ❌ 不使用（`02` D5） |

### 1.1 为什么不调用 LLM

报告的数据层是**确定性集合运算**的结果——通过率、错误分布、维度覆盖，都是 `GROUP BY` 能算出来的。引入 LLM 只会带来三个损失：

| 损失 | 说明 |
| :--- | :--- |
| **可复现性** | 同一份数据两次生成的报告文字不同，用户无法确认"我上次看到的是不是这个" |
| **成本** | 违反 M8 的预算约束（`02` §5.4），且这笔钱完全没有换来新信息 |
| **可信度** | PRD §1.2 的痛点"AI 生成内容不可控"同样适用于报告——**报告是给人做决策用的，数字必须确定** |

V1.0 可在模板骨架之上增加一段 LLM 生成的"结论摘要"（`02` D5）。**摘要必须是可单独关闭的附加段落**，绝不参与任何数字的产生。

### 1.2 它是 M1~M8 中产品指标的呈现载体

| 指标 | 是否出现在单次报告 |
| :--- | :--- |
| M1 用例采纳率 | ✅（本次 Run 的 `approved / total`） |
| M2 生成耗时、M5 端到端耗时 | ✅ |
| M3 Spec 解析成功率 | ❌（跨 Run 的平台指标） |
| M4 归因认可率 | ✅（本次 Run 的 `agree` 比例） |
| M6 平台单测覆盖率 | ❌（工程指标，见 `09-测试策略.md`） |
| M8 LLM 成本 | ✅（本次 Run 的实际用量） |

报告需要**同时呈现本次结果与成本**——把成本藏进日志，用户不会去看，M8 就失去了约束力。

## 2. 报告结构

### 2.1 主结构：按责任归属分组，而非按类别平铺

**RA1：错误分布按"责任归属"分组呈现，不按 11 个类别平铺。**

`LogAnalyzer.md` §3 已经为每个类别定义了责任归属（请求侧 / 服务侧 / 环境侧 / 测试资产侧 / 平台策略侧）。报告应当利用这个结构：

```
## 执行结果
通过 82 / 100  ·  失败 18

## 失败分布（按责任归属）

### ① 服务侧  —— 6 条，最需要关注
  server_error              4
  response_schema_mismatch  2

### ② 请求侧  —— 5 条，大概率是用例本身的问题
  request_invalid           5

### ③ 测试资产侧  —— 4 条，检查测试数据
  resource_not_found        4

### ④ 环境侧  —— 2 条
  network_error             2

### ⑤ 平台策略侧  —— 1 条，检查 Guardrail 配置
  blocked_by_policy         1
```

这样做直接兑现了 PRD 场景 S3 的诉求（"知道是参数问题还是服务问题"）：用户**第一眼就看到该去找谁**。若按 11 个类别平铺，用户要先理解分类学才能行动。

**⚠️ M3 实现回写——分组从 5 个补齐到 8 个。**

上面的示例只列了 5 组，而 `LogAnalyzer.md` §3.1 的 11 类里还有三个无处安放。
实现时补成：

| 组 | 类别 |
| :--- | :--- |
| 请求侧 | `request_invalid` |
| **凭证侧** | `auth_error`——排查方向是"令牌过期/权限不足"，与"参数写错"完全不同 |
| 测试资产侧 | `resource_not_found`、`conflict` |
| 环境侧 | `rate_limited`、`network_error` |
| 服务侧 | `server_error`、`response_schema_mismatch` |
| **需人工判断** | `assertion_mismatch`——天然二义，假装能自动归类等于把不确定性藏起来 |
| 平台策略侧 | `blocked_by_policy` |
| **未归类** | `unknown`——它是缺陷信号，必须可见 |

**零值的组也会列出**。"环境侧 0 条"本身就是信息：它告诉用户不用去查网络。

### 2.2 报告章节清单

| 章节 | 内容 | 数据来源 |
| :--- | :--- | :--- |
| 执行概览 | 通过/失败/超时计数、耗时、Run 元信息（Spec 指纹、时间） | `runs` / `case_results` |
| 失败分布 | 按责任归属分组（§2.1） | `attributions` + `cases` |
| 维度覆盖 | 各测试维度的覆盖情况与失败率 | `cases.dimension` |
| 置信度分布 | 高/低置信度用例的通过率对比 | `cases.confidence` |
| 执行完整性 | 未完成用例、被拒绝的用例、部分失败说明 | `case_results.status` |
| 质量与成本 | 规则覆盖率、LLM 调用次数与成本、生成采纳率 | `attributions.method`、调用记录 |
| 未执行用例 | 破坏性用例（被 N4 跳过）、未确认用例 | `cases.is_destructive` / `review_status` |

### 2.3 两个必须出现的"负面信息"章节

**RA2：报告必须显式列出"没有测到的东西"。**

| 类别 | 为什么必须出现 |
| :--- | :--- |
| **被跳过的破坏性用例** | 用户看到"通过率 100%"却不知道有 5 条 `DELETE` 用例根本没跑，会得出完全错误的结论（`TestExecutor.md` TE3） |
| **未完成的用例** | 部分失败时（`TestExecutor.md` §9），通过率的分母必须让用户看得见 |

**只有被测量的部分才会出现在通过率里**——这条原则不写进报告，通过率就是一个会误导人的数字。

### 2.4 维度覆盖章节的价值

`cases.dimension`（`04` §2.5）是 `TestCaseGen` 阶段 A 的产物。报告呈现维度覆盖，使两件事变得可验证：

- **生成的完备性**：某接口声明的 4xx 状态码是否有对应用例？某字段的边界维度是否生成？
- **失败集中在哪类维度**：若失败全部集中在 `boundary` 维度，这本身就是一个关于被测服务的有价值发现

## 3. 聚合逻辑

### 3.1 通过率的定义

**RA3：通过率 = `passed / (passed + failed + timeout + error)`，分母含所有已执行用例。**

不使用"`passed / 总数`"的写法，因为总数里可能含未执行、未确认、被拒绝的用例——把它们算进分母会让通过率被未执行的部分稀释，看不出真实质量。

**未执行的用例单独呈现**（§2.3），不混入通过率。

**⚠️ M3 实现回写——`timeout` 只指"真超时"，补记的超时单列为"未完成"。**

`results.mark_unfinished_as_timeout` 在兜底轮询里把"结果没回来"补记成
`status='timeout'`（`error_kind='executor_stall'`），目的是让流程能往下走。
它不是"我们发了请求但没等到回应"，而是"我们根本没拿到结果"。

若它按字面进了 `timeout`，RA3 的公式会让它进分母——于是一次"平台丢了 8 条、
其余 1 过 1 败"的运行会显示成 10%，而真实通过率是 50%。**报告把平台故障
说成了被测服务大面积失败。**

因此实现口径是：

| 字段 | 含义 |
| :--- | :--- |
| `summary.timeout` | **真超时**（`error_kind = timeout`）——测试结论，进分母 |
| `summary.unfinished` | **补记超时**（`error_kind = executor_stall`）——不进分母，单列一节 |

不变式：`executed == passed + failed + timeout + error + unfinished`。

### 3.2 规则覆盖率必须出现在报告中

`LogAnalyzer.md` §2.2 与 §9 明确要求规则覆盖率随报告输出。理由是它同时是**成本与质量的先行指标**——它下滑时，问题还没体现在账单上。

因此报告的质量章节必须包含：

```
规则覆盖率  78%   （18 条失败中 14 条由规则确定性归因）
LLM 兜底     4 次
```

**⚠️ M4 实现回写——"质量与成本"是独立章节，且零失败时也必须出现。**

M3 的实现把这段包在 `{% if rule_coverage is not none %}` 里。后果：
**零失败 Run 的成本完全不显示**——而它仍然调用了 LLM 生成用例，钱照花。
"没有失败"不等于"没有成本"。

M4 起报告固定包含 `## 质量与成本`，字段来自 `ReportContent.llm_usage`
（`domain/report.py`）：

| 字段 | 含义 | 空值语义 |
| :--- | :--- | :--- |
| `calls` / `generation_calls` / `attribution_calls` | 真实调用次数（含重试） | 0 |
| `prompt_tokens` / `completion_tokens` / `cached_tokens` | token 用量 | 0 |
| `cache_hit_rate` | `cached / prompt` | 无输入时 `None` |
| `cost_cny` | 按单价表算出的金额 | **未知模型 → `None`**，并列出 `unpriced_models` |
| `p95_latency_ms` | 单次调用耗时 P95 | 无调用时 `None` |
| `generation_acceptance_rate` | 被批准用例 / 生成用例 | 未生成时 `None` |
| `usage_missing_calls` | 提供商没回 usage 的调用数 | >0 时报告显示"成本被低估" |

**三条"不知道就说不知道"的规则**：

1. 没有调用 → 成本 `0.0`（纯规则 Run 确实没花钱），不是 `None`。
2. 有调用但某个模型没有单价 → 成本 `None`。只算了一部分模型的金额
   看起来最权威，也最容易误导。
3. 命中率的分母为 0 → `None`，不是 `0%`。

`content.llm_calls` **保留原语义**（归因表中 `method='llm'` 的行数）。
它是 M3 的既有契约，且不等于真实调用次数——真实数字看 `llm_usage`。

## 4. 可复现性

**RA4：`rendered` 存为快照，历史报告不随模板变更而重新渲染。**

`04` §2.8 已决定存储 `rendered`。这里说明其必要性：

报告会作为**测试记录**被引用——出现在评审材料、问题工单、回归对比中。若模板在三个月后调整了措辞或分组方式，历史报告应当保持原样，而不是被追溯性地改写。**被引用的证据不应变化。**

实现上，`rendered` 在 N7 生成时写入并只读。重新生成报告是一个**显式操作**（产出新的 report 记录或覆盖并记录时间），不是渲染时的隐式行为。

## 5. 渲染

| 项 | 内容 |
| :--- | :--- |
| 模板引擎 | Jinja2（`02` D5） |
| 输出格式 | Markdown（MVP）；`content` 为结构化 JSON，供前端与导出复用 |
| 数据来源 | **只读 `content`**，模板中不做任何聚合计算 |

**RA5：模板只做呈现，不做计算。**

所有聚合在生成 `content` 时完成，模板只负责把已有数字排版出来。理由：若模板里写 `|selectattr(...)|list|length` 这类逻辑，同一份数据的两个渲染入口（Markdown 与前端）会各自计算一遍，**必然漂移**，且模板中的计算无法被单测覆盖。

### 5.1 数字的呈现原则

| 原则 | 说明 |
| :--- | :--- |
| 百分比附原始计数 | 只给"82%"不如给"82%（82/100）"——小样本下百分比会误导 |
| 零值显式呈现 | "服务侧 0 条"应显示，而不是省略该分组。**用户需要确认你检查过了** |
| 部分失败显式标注 | 执行不完整时，概览区必须出现显著提示，而不是只在细节里体现 |

## 6. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **RA1** | 失败分布按责任归属分组 | 兑现 S3 的"是参数问题还是服务问题"，用户第一眼知道该找谁 |
| **RA2** | 必须列出"没测到的东西" | 通过率 100% 但 5 条 DELETE 没跑，是会误导人的结论 |
| **RA3** | 通过率分母只含已执行用例 | 未执行/未确认/被拒绝的用例不允许稀释通过率 |
| **RA4** | `rendered` 存快照，不随模板变更重渲 | 被引用的证据不应变化 |
| **RA5** | 模板只呈现，不计算 | 两个渲染入口各自计算必然漂移，且模板逻辑无法单测 |
| **RA6** | 报告中必须含成本与规则覆盖率 | 把它藏进日志，M8 就失去约束力；覆盖率是成本与质量的先行指标 |
