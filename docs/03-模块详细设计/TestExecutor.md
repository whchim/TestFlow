## 1. 模块定位

这是唯一**横跨两个进程**的模块，先明确其边界：

| 位置 | 组件 | 职责 |
| :--- | :--- | :--- |
| 编排层（Orchestrator） | 节点 **N4** `dispatch_cases` | 过滤可执行集合、组装并投递 Celery 任务 |
| 执行层（Celery Worker） | **Worker 侧执行逻辑** | 读用例、组装请求、经 Guardrail 发出、求值断言、落库结果 |
| 编排层（Orchestrator） | 节点 **N5** `collect_results` | 校验结果完整性、判定部分失败 |

两个节点与 Worker 侧共同构成"执行"这件事，因此合为一份模块设计。**IP-2 中断点横亘在 N4 与 N5 之间**（`06` §3），这是它们必须分开的原因。

| | 内容 |
| :--- | :--- |
| **输入** | `approved_case_ids`（N4）；`(run_id, case_id)`（Worker） |
| **输出** | `case_results` 记录；`run_operations.gen_status` 之外的执行状态 |
| **LLM** | ❌ 完全不使用 |

### 1.1 与 Guardrail 的边界

```
TestExecutor（本模块）          Guardrail（独立模块）
─────────────────────           ──────────────────────
决定"发什么请求"                 决定"这个请求允不允许发出"
组装 URL / headers / body        白名单校验（SR-1）
注入凭证（SR-6）                 内网地址阻断（SR-2）
解析并求值断言                   破坏性方法拦截（SR-3）
                                 重定向控制（SR-4）
                                 限流熔断（SR-5）
                                 写审计日志
```

**关键约束**：TestExecutor **不持有 HTTP 客户端的直接构造权**。所有出站请求必须经由 Guardrail 提供的客户端发出（`02` D2）。这不是风格约定——若本模块能自行构造客户端，SR-1 的白名单就形同虚设。

## 2. 执行流水线

单个 Case 的完整路径：

```
① 投递（N4，编排层）
   过滤 → 组装任务 → 投递到 exec 队列

② 消费（Worker）
   读 case + operation + 凭证          ← 全部从 PG 读，任务载荷不含数据
   ↓
③ 组装请求
   解析路径参数 → 拼 URL → 注入凭证 → 组装 headers/body
   ↓
④ 出站（经 Guardrail）
   SR-1...SR-5 校验 → 发出 → 写审计日志
   ↓
⑤ 求值断言
   status_code → json_path → header → schema_valid → ...
   ↓
⑥ 落库
   INSERT ... ON CONFLICT (run_id, case_id) DO UPDATE
   ↓
⑦ 回调
   POST /internal/runs/{id}/wake（`06` §6.1）

⑧ 汇集（N5，编排层）
   校验完整性 → 判定部分失败 → 推进图
```

**TE1：Celery 任务载荷只带 ID。**

任务参数仅为 `(run_id, case_id)`，Worker 从 PG 读取全部数据。理由有三：

- **消息体积**：Case 可能含较大的 request body，塞进 broker 消息会让 Redis 内存与网络开销随用例规模线性增长
- **避免陈旧数据**：投递与执行之间可能间隔较久（HITL 中断期间），载荷里的快照可能与库中现状不符
- **便于重试**：Worker 崩溃重投时，重新读取的是最新状态，而非当初投递时的旧值

## 3. 断言求值引擎

### 3.1 求值语义

输入是 `cases.assertions`（结构见 `TestCaseGen.md` §3），输出是**逐条断言的结果**。

| 断言类型 | 求值方式 |
| :--- | :--- |
| `status_code` | `http_status` 是否等于 `expected`（`expected` 为列表时判断是否包含） |
| `json_path` | 响应体解析为 JSON，按 JSONPath 取值后按 `operator` 比较 |
| `header` | 从响应头取值后按 `operator` 比较（header 名大小写不敏感） |
| `schema_valid` | 用 `operations.responses_schema[status]` 校验响应体 |
| `body_contains` | 在响应原文中做子串匹配 |
| `response_time` | `elapsed_ms` 与 `expected_ms` 比较 |

### 3.2 断言级结果有三个，不是两个

**TE2：必须区分"断言不符"与"断言无法求值"。**

| 断言级 `outcome` | 含义 | 例子 |
| :--- | :--- | :--- |
| `passed` | 断言成立 | 状态码 200 == 期望 200 |
| `failed` | 断言求值成功，但不成立 | 状态码 500 != 期望 200；`$.data.id` 不存在 |
| `error` | **断言无法求值** | 响应体不是合法 JSON，`json_path` 无从取值；响应体被截断导致 `schema_valid` 无法判定；JSONPath 语法非法 |

把这个区分丢掉，`LogAnalyzer` 就无法分辨两种截然不同的情形：

- `json_path` 判 `failed`（字段确实缺失）→ 指向 `response_schema_mismatch`（服务侧）
- `json_path` 判 `error`（响应体根本不是 JSON）→ 更可能指向 `request_invalid` 或服务返回了错误页

`04` §2.6 的 `status` 字段只有 `passed`/`failed`/`timeout`/`error` 四档（其中 `error` 指请求层失败），**粒度不足以承载这个区分**。因此：

> **对 `04-数据模型.md` 的修订需求**：`case_results` 表需增加 `assertion_outcomes JSONB` 列。见该文档 v0.4。

```json
[
  {"index": 0, "type": "status_code", "outcome": "passed"},
  {"index": 1, "type": "json_path", "path": "$.data.id", "outcome": "failed",
   "expected": "exists", "actual": "missing"},
  {"index": 2, "type": "schema_valid", "outcome": "error",
   "reason": "response_truncated"}
]
```

### 3.3 用例状态的判定

`case_results.status` 的判定顺序（**先看请求是否完成，再看断言**）：

| 顺序 | 条件 | `status` |
| :--- | :--- | :--- |
| 1 | 请求超时 | `timeout` |
| 2 | 请求层失败（连接被拒、DNS、TLS） | `error` + `error_kind` |
| 3 | 请求完成，全部断言 `passed` | `passed` |
| 4 | 请求完成，其余情况（含 `failed` 与 `error` 的任意组合） | `failed` |

**第 4 条刻意不区分 `failed` 与 `error`**：对"用例是否通过"这个问题，答案都是"否"。区分留在断言级（§3.2），由 `LogAnalyzer` 按需取用。若在 `status` 上再分一档，会让所有下游判断都要处理第四个分支，而它并不改变任何结论。

## 4. 破坏性用例防护（SR-3）

### 4.1 MVP 立场

**TE3：MVP 不提供破坏性用例的执行能力，也不提供授权入口。**

- 破坏性用例（`is_destructive = true`）**照常生成、照常进入 IP-1 供人工审阅**，但不会被执行
- N4 直接跳过它们，并在界面上明确告知："以下 N 条用例涉及破坏性方法，需在目标环境中手动执行"
- **不设计"一键授权"入口**

理由是安全设计上的一条判断：**授权一个可以删除生产数据的操作，不应该和"确认用例"共用一个动作。** IP-1 的操作是批量勾选，用户很容易在"全选 → 确认"的惯性中放过一条 `DELETE`。把授权做成独立步骤（V1.0）能显著降低误操作概率，而 MVP 阶段没有必须执行破坏性用例的场景。

SR-3 的完整表述是"默认禁用，需用户显式授权"——MVP 实现了前半句，并**刻意不实现后半句**，直到有独立、显式、可审计的授权 UI。

### 4.2 两层防护

即便 MVP 不执行破坏性用例，防护仍然是两层的（对应 `06` §3）：

| 层 | 位置 | 行为 |
| :--- | :--- | :--- |
| **第一层** | N4 投递前 | 过滤掉 `is_destructive = true` 的用例，**不投递** |
| **第二层** | Worker 侧 Guardrail | 若 `method ∈ {DELETE, PUT, PATCH}` 且未被授权 → 拒绝发出 + 写审计日志 |

**第一层是主防线，第二层是冗余**。冗余存在的意义是：第一层是应用逻辑，可能因 bug 或后续改动而失效；第二层由 Guardrail 统一实施，无法被业务代码绕过（`02` D2）。安全设计不应假设应用层代码永远正确。

**⚠️ M1 实现回写——第一层过滤之后，有一个下游副作用必须处理。**

被 N4 跳过的破坏性用例**永远不会有结果**。而 §9 的"部分失败判定"会把"该有结果却没有"的用例补记为 `timeout`——**若不排除它们，就会把"我们故意没发"记成"我们发了但没等到回应"**。

事实正好相反：

```
用例被跳过的真实原因：按设计就不该执行（TE3）
被补记成 timeout 后表达的意思：我们发了请求，但目标在时限内没回应
```

后果不只是报告失真：一份"12 条超时"的报告会让用户去查**目标服务为什么慢**，而真相是那些用例根本没被投递。

**处理**：`06` §6.4 的补记逻辑必须排除 `is_destructive = true` 的用例。它们应当出现在报告的"**未执行的用例**"一节（`03/ReportAgent.md` RA2 要求报告显式列出"没测什么"），而不是"失败清单"里。

## 5. 凭证注入（SR-6）

### 5.1 注入时机

**凭证在任何持久化中都不出现**（`04` §2.5 的 `cases.request_headers` 明确不含凭证），仅在 Worker 组装请求时按 host 从 `credentials` 表解密注入。

路径：

```
① 从 case.request_path 解析出目标 host
② 按 host 查 credentials.scope_host
③ 解密 encrypted_value（Fernet，密钥经环境变量注入）
④ 按 auth_type 注入到 header / query
⑤ 请求发出后，凭证不进入任何日志或落库字段
```

### 5.2 需要鉴权与否是一个用例属性

`TestCaseGen` 的 `auth_missing` 维度生成的用例**必须故意不带凭证**——否则平台会把凭证注入进去，用例收到 200 而非预期的 401/403，测试结果完全错误。

因此：

> **对 `04-数据模型.md` 的修订需求**：`cases` 表需增加 `requires_auth BOOLEAN NOT NULL DEFAULT true` 列；`TestCaseGen.md` 的 `GeneratedCase` 契约需同步增加该字段。见两文档的最新版本。

| `requires_auth` | Worker 行为 |
| :--- | :--- |
| `true`（默认） | 按 host 注入凭证 |
| `false` | 不注入任何凭证（用于 `auth_missing` 维度） |

### 5.3 凭证缺失的处理

若 `requires_auth = true` 但目标 host 无对应凭证，**不在 Worker 阶段静默发出**——那会得到一堆 401，被归因成 `auth_error`，误导用户去找服务端问题。

正确做法是在 **N4 投递前检查**：对缺失凭证的 host 记录警告，在界面上提示"以下接口缺少凭证配置，其执行结果可能为 401"。**仍然执行**（401 本身是有效信息），但用户能看到这是配置缺失而非服务缺陷。

## 6. 超时与重试

**TE7：超时分三层，且必须严格递增。**

| 层级 | 默认值 | 作用 |
| :--- | :--- | :--- |
| HTTP 请求超时 | **10s**（PRD F4，可配） | 单个请求的等待上限 |
| Celery `soft_time_limit` | 30s | 抛出可捕获的软超时，让任务有机会清理并落一条 `timeout` 结果 |
| Celery `hard_time_limit` | 45s | 强制终止 Worker 进程 |

三层递增是必需的：若 HTTP 超时 ≥ soft limit，任务会在请求返回前被中断，**连"超时"这条结果都来不及写**，Case 会永久悬空，进而让 N5 的完整性校验永远等不到它。

**重试策略**：

| 情况 | 是否重试 | 理由 |
| :--- | :--- | :--- |
| Worker 崩溃（进程被杀） | ✅ Celery `acks_late` 重投 | 未产生任何结果，重投是唯一办法 |
| 请求超时 | ❌ 不重试 | **超时是测试结果**，不是系统故障。重试会拖延整个 Run 且结论相同 |
| 连接被拒 / DNS 失败 | ❌ 不重试 | 同上，这是环境的真实状态 |
| 凭证解密失败 | ❌ 不重试 | 配置问题，重试无意义；记为 `error` 并审计 |

> **这条与直觉相反但很重要**：目标 API 超时、连不上，是"被测系统/环境有问题"的**结论**，不是"我们的执行出了问题"。把它当系统故障去重试，会让一个已经明确的问题在报告里被掩盖成"重试后成功"。

## 7. 幂等写入

结果落库一律：

```sql
INSERT INTO case_results (run_id, case_id, ...)
VALUES (...)
ON CONFLICT (run_id, case_id) DO UPDATE SET ...
```

这是 `04` DM1 的落点——`UNIQUE (run_id, case_id)` 保证：

- `acks_late` 重投后不产生重复行
- IP-2 恢复时重放不产生重复行
- 并发写同一 Case 时后者覆盖前者（同一 Case 不应被并发执行，因此可接受）

**写入与回调的顺序不可颠倒**（`02` D4 / `06` §6.1）：先落库，后回调。若先回调，图可能在结果尚未持久化时被唤醒，N5 读到不完整的结果。

## 8. Celery 任务设计

| 配置 | 取值 | 理由 |
| :--- | :--- | :--- |
| `acks_late` | `True` | Worker 崩溃时任务可重投（`02` §7） |
| `task_time_limit` | 45s | 见 §6 |
| `soft_time_limit` | 30s | 见 §6 |
| `max_retries` | 0（应用层不重试） | 见 §6 的重试策略 |
| 池类型 | `prefork` | 执行层为同步代码（`02` D1） |
| 任务载荷 | `(run_id, case_id)` | TE1 |
| 队列 | `exec` | 与 `orchestrate` 分离（`02` §1.3 / `06` G2） |

**并发度**：MVP 默认 8（`02` §5）。并发度直接决定对目标 API 的压力，因此必须与 Guardrail 的限流配置（SR-5）协调——限流阈值应低于并发度能产生的 QPS，否则限流形同虚设。

## 9. N5 汇集与部分失败判定

N5 `collect_results` 的职责：

1. 查询 `case_results` 中该 Run 的终态记录数，与 `run_operations` 的预期总数比对
2. 若存在未到终态的 Case：
   - 正常情况：图不应被唤醒（`06` §6.2 的完成判定会拦住）
   - 被兜底轮询唤醒时：将这些 Case 标记为 `timeout` 终态，**按部分失败推进**（`06` §6.4）
3. 记录 `settled_case_count`（**仅作展示缓存**，权威判定一律查 `case_results`，`04` DM5）
4. 判定是否有失败 Case，决定是否进入 N6 归因（`06` §4 路由表）

**"部分失败"不是错误状态**，而是一种正常结果：报告中显式标注"本次执行有 N 条用例未完成"，归因与聚合照常进行。把它当成 Run 级失败会让用户拿不到已有的结果。

## 10. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **TE1** | 任务载荷只带 ID | Worker 从 PG 读数据，避免消息膨胀与陈旧快照 |
| **TE2** | 断言级区分"不符"与"无法求值" | `passed` / `failed` / `error` 三态；不区分会让归因无法分辨服务缺陷与响应非 JSON |
| **TE3** | MVP 不执行破坏性用例，也不提供授权入口 | 授权删除类操作不应与"确认用例"共用同一个批量勾选动作 |
| **TE4** | 凭证仅在执行时按 host 注入 | 任何持久化中都不出现凭证 |
| **TE5** | 结果写入用 `ON CONFLICT DO UPDATE` | 幂等由数据库约束保证，应用层判断只是优化（`04` DM1） |
| **TE6** | 破坏性防护分两层 | N4 过滤是主防线，Guardrail 拦截是冗余，不假设应用层永远正确 |
| **TE7** | 超时分三层且严格递增 | 否则任务被中断前来不及写"超时"结果，Case 永久悬空 |
