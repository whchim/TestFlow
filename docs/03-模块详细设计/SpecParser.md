## 1. 定位

| | 内容 |
| :--- | :--- |
| **输入** | OpenAPI 3.0 / 3.1 文档原文（JSON 或 YAML） |
| **输出** | `specs` 一行 + 若干 `operations`；产出 `fingerprint` 与 `declared_targets` |
| **LLM** | ❌ **完全不使用**（`02` D3） |

### 1.1 为什么不用 LLM

OpenAPI 是有严格语法的机器可读格式，**解析是确定性问题**。用 LLM 解析会引入三个不可接受的代价：

- **幻觉**：模型可能"补全"文档里不存在的字段，而这类错误在下游表现为用例失败，排查时根本想不到源头在解析
- **不可复现**：同一份文档两次解析结果不同，"同一个 Spec 的两次测试结果为什么不一样"将无法回答
- **违反 M3**：PRD 要求 Spec 解析成功率 ≥ 99%。**LLM 无法承诺 99% 的确定性**——这个指标本身就排除了 LLM 方案

### 1.2 它是唯一真正可重放的节点

`06` §3 给出 N1 的幂等键是 `spec_fingerprint`。这里要说明这个幂等性与 N2 **性质完全不同**：

| 节点 | 幂等语义 | 原因 |
| :--- | :--- | :--- |
| **N1 SpecParser** | **真幂等**——同输入必得同输出，可安全重放 | 纯函数，无随机性 |
| N2 TestCaseGen | **跳过式**——已完成则跳过，不可重放 | LLM 输出非确定性（`04` DM4、`06` §5.3） |

因此 N1 在恢复、重试、重跑任何场景下都可以放心执行，只需按指纹去重。

## 2. 解析流水线

```
① 语法加载         JSON / YAML → Python dict
        ↓
② 规范校验         openapi-spec-validator（版本、必需字段、结构）
        ↓
③ $ref 解析展开    见 §3
        ↓
④ 规范化           递归排序 key，见 §4
        ↓
⑤ 指纹计算         sha256(规范化结果)
        ↓
⑥ 按指纹去重       已存在则直接复用，不重复落库
        ↓
⑦ 提取 Operations  逐 method+path，落 operations 表
        ↓
⑧ 提取 declared_targets  servers[].url → scheme://host:port 集合，见 §5
```

**工具选型**：`prance`（负责 `$ref` 解析）+ `openapi-spec-validator`（负责规范校验）。二者都是成熟的确定性库。

## 3. `$ref` 解析与循环引用

### 3.1 为什么必须在解析阶段展开

`TestCaseGen` 组装提示时需要**自包含的 schema 片段**（`04` §2.10 的裁剪在组装时进行）。若 schema 中残留 `$ref`，要么消费方需要再实现一套解析器（重复劳动且会漂移），要么把整个文档塞进提示（触发 Qwen 阶梯计费跳档，`02` §5.1）。

因此 `$ref` 在**解析阶段**展开，`operations` 表中存的是展开后的自包含结构。

### 3.2 循环引用

OpenAPI 文档中循环引用是合法的，且常见：

```yaml
TreeNode:
  type: object
  properties:
    children:
      type: array
      items:
        $ref: '#/components/schemas/TreeNode'   # 自引用
```

无限展开不可行。**SP1：设展开深度上限（默认 10 层），超限处保留 `$ref` 字面量。**

超限的处理不是报错，而是**标记降级**：

| 项 | 处理 |
| :--- | :--- |
| 超限的 `$ref` | 原样保留字面量 |
| 该 Operation | 标记 `has_unresolved_ref = true` |
| 下游影响 | `TestCaseGen` 将该 Operation 生成的用例全部标 `low` 置信度（`TestCaseGen.md` §7） |

这样做的理由是：一个 10 层嵌套的递归结构，其深层字段对测试用例设计的边际价值很低；**为它中断整个解析不值得**，但必须让下游知道信息不完整。

**⚠️ M1 实现回写——深度上限单独挡不住指数爆炸，必须再加一道"展开预算"。**

一个 schema 如果含 *n* 个指向自己的引用，展开 10 层就会产生 **n¹⁰** 个节点：

```
n = 2   →  1,024                   无所谓
n = 5   →  约 1000 万               开始吃内存
n = 20  →  1.02 × 10¹³             进程被打死
```

而这是**用户上传的文档**——必须当成不可信输入对待。

**补充规则：给 `$ref` 的**解引用次数**设一个预算（默认 10,000），超了就停止展开、保留字面量。**

实测（同一份文档，不同的自引用分支数）：

```
分支数=  2   耗时  83 ms
分支数=  5   耗时 117 ms
分支数= 10   耗时 212 ms
分支数= 20   耗时 354 ms      ← 原本是 10¹³ 个节点
分支数= 50   正常完成          ← 原本是 10¹⁷ 个节点
```

**计的是"解引用次数"而不是"结果节点数"**：正常文档里绝大多数节点是普通字段，把它们也计入会让额度在大文档上被无谓地耗掉。而**能导致爆炸的恰恰只有解引用**。

**⚠️ 顺带一个性能坑**：预算耗尽之后，如果只在"进递归函数时"检查，外层循环仍会把整棵树走完（每次都立刻返回，但仍是 10¹⁷ 次函数调用）。必须在**进入下一次递归之前**检查，把剩下的兄弟节点原样拷过去。

## 4. 规范化与指纹

`04` DM2 规定指纹为 `sha256(规范化内容)`，本节定义"规范化"的具体含义。

### 4.1 规范化步骤

| 步骤 | 说明 |
| :--- | :--- |
| 1. **在 `$ref` 展开之后**进行 | 见 §4.2 |
| 2. 递归按 key 排序 | 消除 key 顺序差异 |
| 3. 统一为紧凑 JSON（无多余空白） | 消除缩进与换行差异 |
| 4. 保留数组顺序 | 数组顺序在 OpenAPI 中**有语义**（如 `enum` 允许值列表、`required` 列表），不可排序 |
| 5. 数值规范化 | 避免 `1` 与 `1.0` 产生不同指纹 |

### 4.2 为什么在展开之后

两份语义等价但组织方式不同的文档应得到**相同**指纹：

```yaml
# 文档 A
paths:
  /users:
    get:
      responses:
        '200':
          content:
            application/json:
              schema: {$ref: '#/components/schemas/User'}
components:
  schemas:
    User: {type: object, properties: {id: {type: integer}}}

# 文档 B：把 schema 内联写进去，语义完全相同
```

若在展开**前**计算指纹，A 与 B 会得到不同指纹，进而被当成两份不同的 Spec——S2 场景（`02` Q3，文档变更后用例失效）会误报"Spec 变了"，而实际只是重构了写法。

**⚠️ M1 实现回写——光"在展开之后计算"还不够。**

初稿写到 §4.2 就停了。实现时按它做完，测试**当场就红了**：

```
内联版：  paths → 一份内容
$ref 版： paths → 同一份内容  +  components.schemas.User → 多出一整块
                                          ↑
                            展开**不会删掉**这里，它只是把内容抄进了 paths
```

展开是"把被引用的内容抄到引用点"，**而不是"把源头的定义删掉"**。于是 `$ref` 版比内联版多一整个 `components` 区块，指纹必然不同——SP5 的目标落空。

**补充规则：算指纹之前，剔除 `components` 里那些内容已被抄走的子节。**

| 剔除 | 保留 |
| :--- | :--- |
| `schemas` / `responses` / `parameters` / `examples` / `requestBodies` / `headers` / `links` / `callbacks` / `pathItems` | **`securitySchemes`** 以及任何自定义的 `x-` 扩展 |

**`securitySchemes` 必须保留**——它不被抄进 `paths`，而是由 `security` 需求按**名字**引用。剔掉它会让"改了认证方式"检测不到。

**剔除范围刻意收窄**——只删已知的那九节，其余一律保留。因为：

> **漏检测比误报难发现。** 误报立刻表现为"用例失效了"，漏检测则表现为"该失效的没失效"，**没有任何提示**。

### 4.3 指纹的唯一性约束

`specs.fingerprint` 上是 `UNIQUE`（`04` §2.1）。因此：

- 重复上传同一份文档 → **复用既有 `specs` 行**，不重复解析、不重复落 `operations`
- 这正是 SP 幂等性的落点（§1.2）

## 5. `declared_targets` 提取

这是本模块**安全相关**的输出——它直接喂给 Guardrail 的白名单（`Guardrail.md` §3.1）。提取错误会导致合法请求被拒（漏提取）或白名单过宽（多提取）。

**提取单位是 `scheme://host:port` 三元组，不是 host**（`Guardrail.md` GR3）：白名单必须含 scheme 与 port，否则"允许 `http` 等于允许明文传输凭证"、"允许 `host:any` 等于把平台变成端口扫描器"这两条规则无法执行。若变量占位的是 host 之外的部分（如 scheme），按 §5.2 的 `default` 规则同样实例化。

### 5.1 提取范围

OpenAPI 允许在**三个层级**声明 `servers`，必须全部提取：

| 层级 | 说明 |
| :--- | :--- |
| 根级 `servers` | 最常见 |
| 路径级 `servers` | 覆盖根级 |
| 操作级 `servers` | 优先级最高 |

**只提取根级是不够的**——若某 Operation 用操作级的 `servers` 指向另一台主机，该主机会被漏掉，导致请求被 Guardrail 拒绝（`Guardrail.md` §3.3：不在白名单即拒绝）。

### 5.2 Server 变量

`servers[].url` 可以含变量：

```yaml
servers:
  - url: https://{region}.api.example.com/v1
    variables:
      region:
        default: cn-hangzhou
        enum: [cn-hangzhou, cn-beijing]
```

**SP2：用变量的 `default` 值实例化，得到一个具体 host。**

不取 `enum` 的全部取值——那会不必要地放大白名单。

**⚠️ M1 实现回写——"变量无 `default` 时记警告跳过"这条是错的，实际是硬失败。**

原文写的是"规范要求必填，但文档可能不合规，所以降级处理"。但 §5.1 的 SP4 又写着"不符合 OpenAPI 规范 → 硬失败"。**这两条在同一种输入上不可能同时成立**——而 `default` 恰恰是规范的必填字段。

实测：

```
$ 上传一份 variables: {region: {}} 的文档
openapi_spec_validator: 'default' is a required property
```

校验器（流水线第 ② 步）**先一步硬失败了**，那条降级分支永远走不到。

**而硬失败才是对的**：一个无法确定主机名的 server，意味着"这个接口该访问哪里"根本没有答案。静默跳过会让用户后面收到一堆 `blocked_by_policy` 归因，而真正的原因（文档里那个变量没填默认值）在解析阶段就被掩盖了——正是 SP4 说的那种"该让用户修的没让他修"。

实现里保留了那条降级分支作为**纵深防御**（若将来放宽校验它仍然正确），但它的可达性依赖校验器的行为，因此由一条直接调用该函数的测试覆盖，而不是假装能从 `parse_spec` 触发。

### 5.3 相对 URL

OpenAPI 3.0 允许相对 `servers[].url`（如 `/api/v1`），此时主机名由**文档自身的位置**决定。

但 TestFlow 的用户上传的是**文档内容而非可访问的 URL**，没有可解析的基准地址。因此：

**SP3：相对 URL 无法确定 host → 记警告，不产出白名单条目。**

后果是这些 Operation 的请求会被 Guardrail 拒绝（`Guardrail.md` §3.3）。**这个后果必须明确告知用户**，而不是静默地产生一堆 `blocked_by_policy` 归因——否则用户会以为是平台 bug。

### 5.4 端口规范化

`host:port` 三元组是白名单的匹配单位（`Guardrail.md` GR3），端口必须显式化：

- URL 含端口 → 取显式值
- URL 不含端口 → 按 scheme 填默认值（`http` → 80，`https` → 443）

若不做这一步，`https://api.example.com` 与 `https://api.example.com:443` 会被当作两个不同的条目。

## 6. 结构化产出与裁剪设计

`operations` 表存**整块 JSONB** 而非按 parameter 拆行（`04` §2.10）。本节说明这如何满足 N2 的裁剪需求。

N2 组装提示时（`TestCaseGen.md` §6.1）需要的是"当前 Operation 的 schema 片段"，抽取逻辑是：

| 目标片段 | 抽取来源 |
| :--- | :--- |
| 参数清单 | `parameters_schema` 中该 `in`（path/query/header/cookie）的部分 |
| 请求体结构 | `request_body_schema` |
| 期望响应 | `responses_schema` 中该状态码的部分 |

抽取在 `TestCaseGen` 侧进行（`04` §2.10 明确），本模块只保证**存储的结构便于抽取**：三个字段各自独立、按 `in` 与状态码分好组，不揉成一个大 blob。

## 7. 错误与降级

| 情况 | 处理 | 是否终止 Run |
| :--- | :--- | :--- |
| YAML/JSON 语法错误 | **硬失败**，返回带行列号的错误 | ✅ 终止 |
| 不符合 OpenAPI 规范 | **硬失败**，返回校验器的结构化错误列表 | ✅ 终止 |
| `$ref` 无法解析（指向不存在的组件） | **硬失败**——这是文档真实缺陷，静默跳过会导致下游生成错误用例 | ✅ 终止 |
| `$ref` 循环/超深 | 降级：保留字面量 + 标记（§3.2） | ❌ 继续 |
| 某 Operation 的 schema 缺失 | 降级：该 Operation 仍产出，但字段为空 | ❌ 继续 |
| 某 server 相对 URL 或无 default | 降级：记警告，不产出白名单条目（§5.3） | ❌ 继续 |
| 文档无 `servers` | 降级：`declared_targets` 为空 → 所有请求将被 Guardrail 拒绝，需明确告知 | ❌ 继续 |

**SP4：区分"文档缺陷"与"信息不全"。**

- **文档缺陷**（语法错误、`$ref` 悬空）→ 硬失败。这类问题用户能修，且不修就必然产生错误结果
- **信息不全**（缺 example、缺 schema、相对 URL）→ 降级继续。用户可能无法补齐（第三方提供的 Spec），平台应尽力而为并如实标注

`02` 路由表规定 N1 出口的 `node_failures` 含解析错误则终止 Run，对应的就是上表中的硬失败项。

## 8. 决策汇总

| 编号 | 决策 | 要点 |
| :--- | :--- | :--- |
| **SP1** | `$ref` 展开深度上限 10 层，超限保留字面量并标记 | 递归结构合法且常见；为深层字段中断解析不值得，但必须让下游知道信息不完整 |
| **SP2** | Server 变量用 `default` 实例化 | 不取 `enum` 全部取值，避免白名单不必要放大 |
| **SP3** | 相对 `servers[].url` 无法确定 host，记警告 | 用户上传的是文档内容而非可访问 URL，没有解析基准；后果需明确告知 |
| **SP4** | 区分文档缺陷（硬失败）与信息不全（降级） | 能修的必须让用户修；不能修的尽力而为并如实标注 |
| **SP5** | 指纹在 `$ref` 展开后计算**并剔除已内联的 `components` 子节** | 语义等价、写法不同的文档应得到相同指纹，否则 S2 会误报变更。**M1 补充**：见 §4.2 |
